Capítulo 1

Qué es la observabilidad

Observabilidad es poder entender qué está haciendo tu app desde afuera, sin abrir el código ni ponerle pausa. Cuando algo falla a las 3 AM y vos estás durmiendo, lo que dejaste registrado es lo único que tenés para saber qué pasó.

Los tres pilares

PilarResponde
Logs¿Qué pasó, y cuándo? El diario de la app.
Métricas¿Cuánto? Cantidad de pedidos, tiempo de respuesta, uso de CPU.
Trazas¿Por dónde pasó un pedido? Su recorrido por el sistema.

Para una app normal, con logs bien hechos y captura de errores ya cubrís el 90% de lo que necesitás. Métricas y trazas suman cuando el sistema es grande. Este librito arranca por lo esencial: los logs.

El cambio de mentalidad

En desarrollo, si algo falla, lo ves y lo depurás. En producción no estás mirando, y no podés reproducir cada situación de cada usuario. Entonces preparás la app para que te cuente qué le pasa. Ese cambio (de "yo depuro" a "la app me avisa") es lo que separa un proyecto de hobby de uno serio.

Capítulo 2

Logs que sirven: estructurados

Un print("algo pasó") no sirve en producción: no se puede buscar ni filtrar. Los logs útiles son estructurados: cada uno es un dato con campos (JSON), no un texto suelto.

print vs log estructurado

comparación
print:  "pedido 201 de carlos falló"
        -> ¿cómo buscás todos los errores? ¿los de un usuario? imposible

JSON:   {"nivel":"ERROR","mensaje":"pago falló","pedido":201,"usuario":"carlos"}
        -> filtrás por nivel=ERROR, por pedido, por usuario. Buscable.
app.py · logs en JSON
def logear(nivel, mensaje, **campos):
    log.log(nivel, mensaje, extra={"extra": campos})

logear(logging.INFO, "consulta de catálogo", cantidad=3)
salida real✓ salida real
{"ts":"2026-09-05T10:51:59","nivel":"INFO","mensaje":"consulta de catálogo","cantidad":3}
Niveles de log

Usá los niveles: DEBUG (detalle para depurar), INFO (eventos normales), WARNING (algo raro pero no roto), ERROR (algo falló). En producción mostrás de INFO para arriba y filtrás por ERROR cuando buscás problemas. Un log sin nivel es ruido; con nivel, es una herramienta.

Capítulo 3

Request id: seguir un pedido

Un pedido genera varios logs (llegó, consultó la base, respondió). Con muchos usuarios a la vez, los logs se mezclan. El request id le pone a cada pedido una etiqueta única, así podés seguir todo su recorrido.

app.py · middleware
@app.middleware("http")
async def observar(request, call_next):
    rid = str(uuid.uuid4())[:8]          # id único para este pedido
    inicio = time.time()
    respuesta = await call_next(request)
    ms = round((time.time() - inicio) * 1000)
    logear(logging.INFO, "request", request_id=rid,
           metodo=request.method, ruta=request.url.path,
           status=respuesta.status_code, ms=ms)
    respuesta.headers["X-Request-ID"] = rid   # se lo devolvés al cliente
    return respuesta
salida real✓ salida real
{"nivel":"INFO","mensaje":"request","request_id":"7e3d7336","metodo":"GET","ruta":"/productos","status":200,"ms":1}

El middleware corre en cada pedido: genera el id, mide cuánto tardó, y lo loguea. Además mide el tiempo de respuesta (ms), que ya es una métrica gratis para detectar lo lento.

El id que le das al usuario

Fijate que el request id vuelve en un header (y en el cuerpo del error, próximo capítulo). Cuando un usuario reporta "no me anda", le pedís ese id, y con él encontrás en los logs exactamente su pedido, entre millones. Es la diferencia entre "buscá aguja en pajar" y "acá está".

Capítulo 4

Capturar errores sin perder nada

Cuando algo revienta, pasan dos cosas mal por defecto: el usuario ve un error feo (o los detalles internos), y vos no te enterás. Un manejo central de errores arregla las dos.

app.py · atrapar todo en el middleware
try:
    respuesta = await call_next(request)
except Exception as e:
    logear(logging.ERROR, "excepción no manejada",
           request_id=rid, ruta=request.url.path, error=str(e))
    return JSONResponse(status_code=500,
        content={"detail": "error interno", "request_id": rid})
salida real (un bug atrapado)✓ salida real
# en los logs (para vos):
{"nivel":"ERROR","mensaje":"excepción no manejada","request_id":"e09ac39e","ruta":"/romper","error":"division by zero","ms":1}

# lo que recibe el usuario:
500 {"detail":"error interno","request_id":"e09ac39e"}
Nunca muestres el error interno al usuario

Fijate: al usuario le decís "error interno" y el id; el detalle real (division by zero) queda en tus logs. Mostrar el error técnico al usuario es feo y peligroso: puede revelar cómo está hecho tu sistema (nombres de tablas, rutas), información que un atacante aprovecha. El detalle para vos, un mensaje genérico con id para el usuario.

Capítulo 5

Healthcheck: ¿está viva la app?

Un endpoint chiquito que responde "estoy bien". Parece tonto y es clave: el hosting lo llama cada pocos segundos para saber si tu app está viva, y si no responde, la reinicia solo.

app.py
@app.get("/health")
def health():
    return {"estado": "ok"}

Eso solo ya sirve para que el hosting (librito 20) sepa que la app arrancó. Una versión más completa chequea también las dependencias: que la base de datos responda, por ejemplo. Si la base está caída, el health falla, y te enterás antes de que se quejen los usuarios.

healthcheck que también chequea la base
@app.get("/health")
def health():
    try:
        conectar().execute("SELECT 1")
        return {"estado": "ok", "base": "ok"}
    except Exception:
        return JSONResponse(status_code=503,
            content={"estado": "degradado", "base": "caída"})
Liveness y readiness

Dos matices que vas a cruzar: liveness ("¿el proceso está vivo?") y readiness ("¿está listo para recibir tráfico?", ej. ya conectó a la base). En apps chicas alcanza con un health simple; en sistemas grandes (Kubernetes) se separan. Bueno saber que existen.

Capítulo 6

Sentry, métricas y dashboards

Los logs son la base. Cuando el proyecto crece, hay herramientas que te avisan de los errores al instante y te muestran la salud del sistema en gráficos. Un panorama para saber qué buscar.

Sentry: que el error te llame a vos

Con logs, tenés que ir a buscarlos. Sentry da vuelta la cosa: captura cada error automáticamente, lo agrupa (100 veces el mismo error es una sola alerta), te muestra la línea exacta y el contexto, y te avisa (email, Slack) apenas pasa. Se integra en dos líneas.

integrar Sentry (requiere tu DSN)
import sentry_sdk
sentry_sdk.init(dsn=os.getenv("SENTRY_DSN"))
# listo: cada excepción no manejada se reporta sola, con todo el contexto

Métricas y dashboards

Para el "¿cuánto?" (pedidos por minuto, tiempo de respuesta, errores por hora, uso de recursos), están herramientas como Prometheus + Grafana, o las que trae tu hosting. Te dan gráficos en tiempo real y alertas cuando algo se dispara. La mayoría de los servicios de deploy (librito 20) ya traen métricas y logs básicos sin configurar nada.

Empezá simple

No necesitás todo esto el día uno. Con logs estructurados, request id y captura de errores (lo que armamos acá) ya estás mejor que la mayoría. Sumá Sentry cuando tengas usuarios reales, y métricas cuando el volumen lo pida. La observabilidad crece con el proyecto; lo importante es arrancar con la base bien puesta.

Fin del librito

Checklist y cierre

Ya sabés preparar una app para saber qué le pasa en producción. Corto y al hueso.

Con IA

"Agregá logging estructurado en JSON y un middleware de request id + captura de errores a esta app FastAPI." Sale bien. Pedile que nunca exponga el detalle del error al cliente, solo el id.

Checklist de observabilidad

  • Logs estructurados (JSON), no print.
  • Niveles bien usados (INFO, WARNING, ERROR).
  • Request id en cada pedido, devuelto al cliente.
  • Captura central de errores: log completo para vos, mensaje genérico + id para el usuario.
  • Nunca exponer detalles internos del error.
  • Healthcheck (mejor si chequea la base).
  • Sentry cuando haya usuarios; métricas cuando el volumen lo pida.
