Backend · Bases de datos SQL

Backend SQL, de 0 hasta el deploy

Una aplicación de verdad guarda datos: usuarios, productos, pedidos. Ese trabajo lo hace una base de datos. En este librito armás un backend con base de datos relacional desde cero, hasta dejar una base funcionando en internet. Todo por pasos, con código real y probado, en Python y en Node.

Código real y probado

El CRUD de este libro se construyó y se corrió de verdad. Los bloques con ✓ salida real son lo que devolvió el programa. El código completo está en ejemplos/: backend en Python (FastAPI + SQLAlchemy) y en Node (Express + SQLite).

Qué vas a poder hacer al terminar

Diseñar un esquema de tablas, escribir SQL, conectar un backend a la base, exponer un CRUD por API, protegerlo de inyección SQL, y publicar una base Postgres real y gratuita para que tu app la use en producción.

Capítulo 1

Qué es una base de datos relacional

Una base de datos relacional guarda la información en tablas, como planillas conectadas entre sí. Es el modelo más usado del mundo para datos con estructura clara, y el "SQL" del título es el lenguaje para hablarle.

Tablas, filas y columnas

Una tabla es como una hoja de cálculo con un tema: una tabla usuarios, una tabla productos. Cada columna es un dato (email, precio) con un tipo fijo (texto, número). Cada fila es un registro completo (un usuario, un producto). El conjunto de tablas y columnas se llama esquema.

tabla usuarios
id │ email          │ nombre
───┼────────────────┼────────
 1 │ carlos@x.com   │ Carlos
 2 │ ana@x.com      │ Ana

La clave primaria

Cada fila necesita un identificador único: la clave primaria (primary key), casi siempre una columna id. Es cómo la base distingue una fila de otra y cómo otras tablas la referencian.

Las relaciones

Acá está la magia del modelo. Si una tabla pedidos tiene una columna usuario_id que apunta al id de usuarios, quedan relacionadas: cada pedido sabe de quién es, sin repetir los datos del usuario. Esa columna que apunta a otra tabla se llama clave foránea (foreign key).

La idea central

En vez de repetir la info del usuario en cada pedido, la guardás una vez y la referenciás con un id. Menos repetición, menos errores, datos consistentes. Ese principio (no duplicar) se llama normalización, y es el corazón del modelo relacional.

Capítulo 2

SQL: el lenguaje para hablarle a la base

SQL (Structured Query Language) es cómo pedís y modificás datos. Son cuatro verbos que cubren casi todo, y se leen casi como inglés.

Los cuatro verbos (CRUD)

Verbo SQLQué haceCRUD
INSERTAgrega una filaCreate
SELECTLee filasRead
UPDATEModifica filasUpdate
DELETEBorra filasDelete

Ejemplos

SQL
CREATE TABLE usuarios (id INTEGER PRIMARY KEY, email TEXT, nombre TEXT);

INSERT INTO usuarios (email, nombre) VALUES ('carlos@x.com', 'Carlos');

SELECT id, email FROM usuarios WHERE nombre = 'Carlos';

UPDATE usuarios SET nombre = 'Carlitos' WHERE id = 1;

DELETE FROM usuarios WHERE id = 1;

El WHERE es el filtro: qué filas afecta la operación. Sin WHERE en un UPDATE o DELETE, tocás todas las filas. Es el error más caro del SQL, así que cuidado con eso.

SQL es casi universal

Este lenguaje lo entienden SQLite, PostgreSQL, MySQL, SQL Server y más. Hay pequeñas diferencias entre motores, pero el 90% de lo que escribas anda igual en todos. Aprendés SQL una vez y te sirve en cualquiera.

Capítulo 3

Diseñar el esquema

Antes de escribir código, pensás qué tablas necesitás y cómo se conectan. Un buen esquema te ahorra problemas para siempre; uno malo te persigue todo el proyecto.

Los tipos de dato

Cada columna tiene un tipo. Los que más vas a usar:

TipoPara
INTEGERNúmeros enteros (ids, cantidades)
TEXT / VARCHARTexto (nombres, emails)
BOOLEANVerdadero o falso (activo, pagado)
TIMESTAMPFecha y hora (creado_en)
DECIMALNúmeros con decimales exactos (dinero)
El dinero nunca es float

Para plata usá DECIMAL, no float. Los float tienen errores de redondeo (0.1 + 0.2 no da exactamente 0.3) y con dinero eso es inaceptable. Otra opción común es guardar centavos como enteros.

Un esquema de ejemplo

Un mini ecommerce: usuarios que hacen pedidos.

esquema
CREATE TABLE usuarios (
  id       INTEGER PRIMARY KEY,
  email    TEXT NOT NULL UNIQUE,
  nombre   TEXT NOT NULL
);

CREATE TABLE pedidos (
  id          INTEGER PRIMARY KEY,
  usuario_id  INTEGER NOT NULL REFERENCES usuarios(id),
  total       DECIMAL NOT NULL,
  creado_en   TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

NOT NULL obliga a que haya valor. UNIQUE impide emails repetidos. REFERENCES arma la relación (la clave foránea). DEFAULT pone un valor si no lo das. Estas reglas viven en la base: aunque tu código tenga un bug, la base defiende la integridad de los datos.

Capítulo 4

Qué motor de base de datos elegir

"Base de datos SQL" es una categoría; el motor concreto es el programa que la corre. Estos tres son los que vas a cruzar todo el tiempo.

MotorCuándo
SQLiteLa base es un solo archivo, sin servidor. Perfecta para aprender, para desarrollo y para apps chicas. La usamos en este libro para los ejemplos.
PostgreSQLEl motor serio por defecto para producción. Robusto, gratis, potente, con todo lo que un proyecto real necesita. A lo que vamos a hacer el deploy.
MySQLOtro clásico de producción, muy usado también. Postgres y MySQL son intercambiables para la mayoría de los casos.
La estrategia práctica

Desarrollás con SQLite (cero configuración, es solo un archivo) y desplegás a Postgres. Con un ORM (próximo capítulo), pasar de uno al otro es cambiar una línea: la URL de conexión. Tu código no se entera.

La URL de conexión

Cada base se identifica con una cadena de conexión. Vas a ver este formato mil veces:

connection strings
SQLite:    sqlite:///./tareas.db
Postgres:  postgresql+psycopg://usuario:clave@host:5432/basededatos

La de Postgres lleva usuario, clave, host, puerto y nombre de la base. Esa cadena es un secreto (tiene la contraseña), así que nunca va en el código: va en una variable de entorno, como viste en el librito de conexión front-back.

Capítulo 5

Conectar el backend: ORM o SQL crudo

Tu backend habla con la base de dos maneras: escribiendo SQL a mano, o usando un ORM que traduce objetos de tu lenguaje a filas de la base. Conviene entender las dos.

SQL crudo

Escribís las consultas vos mismo y las mandás con la librería del motor. Control total, pero más verboso y hay que tener cuidado con la seguridad (capítulo 9).

ORM (Object-Relational Mapping)

Un ORM te deja definir tus tablas como clases y trabajar con objetos; él genera el SQL. En Python el más usado es SQLAlchemy; en Node, Prisma o Sequelize. Ventajas: menos código repetido, cambio de motor casi gratis, y protección contra inyección SQL por defecto.

definir una tabla con SQLAlchemy
class Tarea(Base):
    __tablename__ = "tareas"
    id: Mapped[int] = mapped_column(Integer, primary_key=True)
    titulo: Mapped[str] = mapped_column(String(200))
    hecha: Mapped[bool] = mapped_column(Boolean, default=False)

Esa clase es la tabla. Base.metadata.create_all(engine) la crea en la base si no existe. Después trabajás con objetos Tarea y SQLAlchemy escribe los INSERT y SELECT por vos.

Cuál usar

Para empezar y para la mayoría de los proyectos, un ORM. Es más productivo y más seguro. El SQL crudo lo sacás para consultas muy específicas o de mucho rendimiento. Saber leer SQL siempre sirve, aunque uses ORM: cuando algo va lento, mirás el SQL que genera.

Capítulo 6

Construir el CRUD paso a paso (Python)

Ahora lo armamos de verdad: una API con FastAPI y SQLAlchemy que crea, lee, actualiza y borra tareas en la base. Este es el ejemplos/backend/app.py, corrido de verdad.

Un endpoint por operación

backend/app.py (recorte)
@app.post("/tareas", response_model=TareaOut)
def crear(t: TareaIn, s: Session = Depends(db)):
    fila = Tarea(titulo=t.titulo, hecha=t.hecha)
    s.add(fila); s.commit(); s.refresh(fila)
    return TareaOut(id=fila.id, titulo=fila.titulo, hecha=fila.hecha)

@app.get("/tareas", response_model=list[TareaOut])
def listar(s: Session = Depends(db)):
    return [TareaOut(id=f.id, titulo=f.titulo, hecha=f.hecha)
            for f in s.query(Tarea).all()]

@app.put("/tareas/{tid}", response_model=TareaOut)
def actualizar(tid: int, t: TareaIn, s: Session = Depends(db)):
    f = s.get(Tarea, tid)
    if not f: raise HTTPException(404, "no existe")
    f.titulo, f.hecha = t.titulo, t.hecha
    s.commit(); s.refresh(f)
    return TareaOut(id=f.id, titulo=f.titulo, hecha=f.hecha)

Cada endpoint HTTP se traduce a una operación SQL: POST inserta, GET lee, PUT actualiza, DELETE borra. El Session es la conexión a la base; commit confirma el cambio en el disco.

Probado de verdad

prueba real✓ salida real
== crear dos tareas ==
{'titulo': 'Aprender SQL', 'hecha': False, 'id': 1}
{'titulo': 'Deploy a Postgres', 'hecha': False, 'id': 2}
== marcar la 1 como hecha (PUT) ==
{'titulo': 'Aprender SQL', 'hecha': True, 'id': 1}
== borrar la 2 ==
{'borrada': 2}
== listar final ==
[{'titulo': 'Aprender SQL', 'hecha': True, 'id': 1}]
== ver una que no existe ==
404 {'detail': 'no existe'}

Los datos quedan guardados en el archivo tareas.db: si apagás el servidor y lo prendés, siguen ahí. Eso es persistencia, la razón de ser de una base de datos.

Capítulo 7

El mismo CRUD en Node

Misma idea, otro lenguaje: Express con better-sqlite3. Para que veas que el concepto es el mismo y solo cambia la sintaxis. Este es el ejemplos/backend/server.js, corrido de verdad.

backend/server.js (recorte)
app.post("/tareas", (req, res) => {
  const { titulo, hecha = false } = req.body;
  const r = db.prepare("INSERT INTO tareas (titulo,hecha) VALUES (?,?)")
              .run(titulo, hecha ? 1 : 0);
  const f = db.prepare("SELECT * FROM tareas WHERE id=?").get(r.lastInsertRowid);
  res.json(aSalida(f));
});

app.get("/tareas", (_req, res) => {
  res.json(db.prepare("SELECT * FROM tareas").all().map(aSalida));
});

Acá vemos SQL crudo (los SELECT y INSERT escritos a mano) en vez de un ORM. Fijate en el ?: es el marcador de parámetro que evita la inyección SQL. Los valores nunca se pegan a la cadena, se pasan aparte.

Probado de verdad

prueba real (curl)✓ salida real
== crear ==
{"id":1,"titulo":"Aprender SQL","hecha":false}
== listar ==
[{"id":1,"titulo":"Aprender SQL","hecha":false},{"id":2,"titulo":"Deploy","hecha":false}]

== delete 2 ==
{"borrada":2}
== 404 ==
404
El mismo mapa mental

Python o Node, ORM o SQL crudo: siempre es lo mismo. Un endpoint recibe una petición, la traduce a una operación en la base, y devuelve el resultado como JSON. Si entendiste uno, entendiste todos.

Capítulo 8

Migraciones: cambiar el esquema sin romper

Tu app va a cambiar: vas a querer agregar una columna, una tabla nueva. Pero la base ya tiene datos reales. Una migración es el cambio de esquema hecho de forma ordenada y reversible.

El problema

En desarrollo borrás la base y la recreás sin drama. En producción no podés: hay datos de usuarios que no se pueden perder. Necesitás una forma de decir "agregá esta columna a la tabla que ya existe, sin tocar lo que hay".

La solución: herramientas de migración

Cada cambio de esquema se guarda como un archivo de migración, numerado y versionado (junto a tu código, en Git). La herramienta las aplica en orden y sabe cuáles ya corrieron. En Python el estándar es Alembic (compañero de SQLAlchemy); en Node, las migraciones de Prisma.

flujo típico con Alembic
# genera la migración comparando tus modelos con la base
alembic revision --autogenerate -m "agrega columna prioridad"

# aplica las migraciones pendientes a la base
alembic upgrade head
Nunca cambies el esquema a mano en producción

Editar tablas directo en la base de producción es la receta para el desastre: no queda registro, no se puede revertir, y el próximo deploy puede pisarlo. Toda modificación de esquema pasa por una migración versionada. Es disciplina que se agradece.

Capítulo 9

Seguridad: inyección SQL y secretos

La base guarda lo más valioso de tu app. El ataque clásico contra ella es la inyección SQL, y la defensa es simple una vez que la entendés. Lo vemos con una demo real.

Qué es la inyección SQL

Pasa cuando pegás la entrada del usuario dentro de una consulta como texto. Un atacante manda algo que no es un dato sino código SQL, y la base lo ejecuta. Mirá la diferencia, corrida de verdad:

demo real de inyección✓ salida real
entrada del atacante:  no@existe.com' OR '1'='1

== MAL: concatenando la entrada ==
query armada: SELECT email FROM usuarios WHERE email = 'no@existe.com' OR '1'='1'
resultado: [('carlos@x.com',), ('ana@x.com',)]   <- devolvió TODOS los usuarios

== BIEN: parametrizado (?) ==
resultado: []   <- vacío, la entrada se trató como dato, no como código

Con la consulta concatenada, el OR '1'='1' se volvió parte de la lógica y la condición siempre da verdadero: la base entregó todo. Con parámetros, la misma entrada se trató como un texto a buscar, y no encontró nada.

La defensa: consultas parametrizadas

Nunca armes SQL pegando strings. Usá los marcadores de parámetro (? o :nombre) y pasá los valores aparte. La librería se encarga de que la entrada jamás se interprete como código. Si usás un ORM, esto ya viene por defecto: es otra razón para usarlo.

Los otros dos musts

Uno: la cadena de conexión (con la contraseña de la base) va en una variable de entorno, nunca en el código ni en Git. Dos: el usuario de base que usa tu app tiene solo los permisos que necesita, no es administrador. Si algo se filtra, el daño queda acotado.

Capítulo 10

Índices: que no sea lento

Con pocos datos todo vuela. Con millones de filas, una consulta mal hecha puede tardar segundos. El índice es la herramienta número uno para que la base sea rápida.

Qué es un índice

Es como el índice de un libro. Sin él, buscar un email es leer la tabla entera fila por fila. Con un índice sobre la columna email, la base salta directo. El costo: ocupa espacio y hace las escrituras un poco más lentas, así que se ponen donde sirven.

crear un índice
CREATE INDEX idx_usuarios_email ON usuarios(email);

Dónde ponerlos

En las columnas por las que filtrás o unís seguido: las que aparecen en tus WHERE y en las claves foráneas. La clave primaria ya tiene índice automático. No indexes todo por las dudas: cada índice tiene un costo.

Regla práctica

Empezá sin pensar en rendimiento. Cuando una consulta va lenta, mirala con EXPLAIN (te dice cómo la resuelve la base) y agregá el índice que falta. Optimizar antes de tener el problema suele ser tiempo perdido.

Capítulo 11

Deploy de una base funcional

Tu base vive en tu compu como un archivo. Para que tu app en producción la use, necesitás una base Postgres en internet, funcionando las 24 horas. Hoy eso es gratis y toma minutos.

Bases gestionadas (managed)

No vas a instalar y mantener un servidor Postgres a mano. Usás un servicio gestionado: ellos corren la base, hacen backups y la mantienen; vos solo la usás. Los más usados con plan gratis:

ServicioNota
NeonPostgres gestionado, plan gratis generoso, muy simple para empezar.
SupabasePostgres más un montón de extras (auth, storage, API automática). Muy popular.
RailwayLevanta Postgres (y tu backend) con pocos clics.

Los pasos, con Neon o Supabase

  1. Creás una cuenta gratis y un proyecto nuevo. Se levanta una base Postgres vacía.
  2. El servicio te da una cadena de conexión (empieza con postgresql://). Ese es el dato clave.
  3. En tu backend, ponés esa cadena en una variable de entorno DATABASE_URL. En local va en un archivo .env (que no subís a Git); en el hosting, en su panel de variables.
  4. Tu código lee DATABASE_URL en vez de la ruta de SQLite. Como usás un ORM, no cambia nada más.
  5. Corrés las migraciones apuntando a la base nueva (alembic upgrade head) para crear las tablas.
  6. Listo: tu backend, esté donde esté, se conecta a esa base y guarda datos reales.
leer la URL del entorno
import os
DATABASE_URL = os.getenv("DATABASE_URL", "sqlite:///./tareas.db")
engine = create_engine(DATABASE_URL)
# en local usa SQLite; en producción, la Postgres de Neon. Mismo código.
La cadena de conexión es un secreto

Tiene la contraseña de tu base. Nunca en el código, nunca en Git, nunca en el frontend. Solo en variables de entorno del servidor. Si se filtra, cualquiera entra a tu base. Si alguna vez se te escapa a un repo, rotala (cambiá la clave) enseguida.

Capítulo 12

Backups y qué no hacer

La base tiene los datos que no se pueden perder. Un par de cuidados que separan a un aficionado de alguien que sabe lo que hace.

Backups

Los servicios gestionados hacen backups automáticos, y podés restaurar a un punto en el tiempo. Igual, conviene saber exportar la base vos mismo (pg_dump para Postgres) y guardar una copia cada tanto. El día que la necesites, la vas a agradecer.

Errores clásicos a evitar

  • UPDATE o DELETE sin WHERE: afecta todas las filas. Antes de correr uno a mano, probalo como SELECT para ver qué toca.
  • La contraseña de la base en el código: siempre en variables de entorno.
  • Probar en producción: tené una base de desarrollo separada. No experimentes con los datos reales.
  • Confiar en la entrada del usuario: validá en el backend y parametrizá siempre las consultas.
  • No tener migraciones: el esquema de producción tiene que ser reproducible, no fruto de cambios manuales que nadie recuerda.
La base es el activo

El código lo reescribís; los datos, no. Un frontend roto se arregla en una tarde. Una base corrupta o borrada sin backup puede terminar un proyecto. Tratala con el respeto que merece.

Capítulo 13

Bases de datos con ayuda de IA

Las herramientas de IA de hoy son buenísimas para el trabajo con bases: diseñar esquemas, escribir consultas complejas y explicar SQL ajeno. Bien usadas, te ahorran horas. Mal usadas, te meten bugs sutiles.

Para qué son excelentes

  • Diseñar el esquema: "Necesito un esquema para un blog con usuarios, posts y comentarios. Dame las tablas con sus tipos y relaciones." Te da un punto de partida sólido en segundos.
  • Escribir consultas difíciles: los JOIN de varias tablas y las agregaciones son justo donde la IA brilla. "Dame el SQL para el total vendido por usuario el último mes."
  • Explicar y traducir: pegás un SQL que no entendés y pedís que lo explique, o pedís la versión con ORM de una consulta cruda.
  • Optimizar: "Esta consulta va lenta, ¿qué índice le falta?"

Cómo pedirlo bien

Dale contexto: qué motor usás (Postgres, SQLite), tu esquema actual, y qué querés lograr. Cuanto más concreto, mejor sale. Pegá tus CREATE TABLE para que trabaje con tus tablas reales.

Revisá siempre, sobre todo lo destructivo

Nunca corras un UPDATE o DELETE que te dio la IA sin leerlo y sin un WHERE que entiendas. Un borrado mal hecho no se deshace. Y verificá que las consultas usen parámetros, no concatenación. La IA acelera; la responsabilidad sobre tus datos sigue siendo tuya.

Fin del librito

Checklist y cierre

Fuiste de no saber qué es una tabla a tener un backend con CRUD real y una base lista para producción. Este es el resumen para tener a mano.

Checklist de un backend SQL

  • Esquema pensado: tablas, tipos correctos, claves primarias y foráneas.
  • Reglas en la base: NOT NULL, UNIQUE, DEFAULT donde corresponde.
  • Backend conectado con un ORM (o SQL crudo bien parametrizado).
  • CRUD completo por API: crear, leer, actualizar, borrar.
  • Consultas siempre parametrizadas (nunca concatenar entrada).
  • Cadena de conexión en variable de entorno, fuera de Git.
  • Migraciones versionadas para todo cambio de esquema.
  • Índices en las columnas que filtrás seguido.
  • Base de producción gestionada (Neon, Supabase) con backups.
