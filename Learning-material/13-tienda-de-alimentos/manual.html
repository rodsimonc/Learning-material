Quién hace qué

El frontend es lo que ve el cliente: el catálogo y el carrito. El dashboard es una interfaz aparte, solo para el dueño. Los dos hablan con la misma API, que es el único que toca la base de datos y el único que habla con los servicios de pago. Esa es la arquitectura SPA + API del librito 09, aplicada a un negocio.

La regla que ordena todo

El frontend nunca toca la base de datos ni los servicios de pago directamente. Todo pasa por la API. Así hay un solo lugar donde validar, cobrar y guardar, y el navegador (que no se puede controlar) nunca tiene las llaves. Es la regla de oro de la conexión front-back llevada a un sistema completo.

Capítulo 2

El modelo de datos

Todo negocio es, en el fondo, sus datos. Las tablas que elijamos definen qué puede hacer el sistema. Estas cinco sostienen toda la tienda.

La relación clave: pedido y sus items

Un pedido tiene muchos items, y cada item apunta a un producto. Esa separación (del librito 10) es la que después deja calcular todo: qué se vende, con qué, cuánto entra. Sin pedido_items como tabla aparte, el dashboard sería imposible.

las tablas del núcleo (db.py)
CREATE TABLE pedidos (
  id INTEGER PRIMARY KEY, cliente TEXT NOT NULL,
  creado_en TEXT NOT NULL, estado TEXT DEFAULT 'pendiente',
  total REAL NOT NULL DEFAULT 0 );

CREATE TABLE pedido_items (
  id INTEGER PRIMARY KEY,
  pedido_id   INTEGER NOT NULL REFERENCES pedidos(id),
  producto_id INTEGER NOT NULL REFERENCES productos(id),
  cantidad INTEGER NOT NULL, precio_unit REAL NOT NULL );
Guardar el precio en el item

Fijate en precio_unit dentro del item. ¿Por qué, si el producto ya tiene precio? Porque los precios cambian, y un pedido de hace un mes tiene que conservar lo que costó ese día. Guardar el precio al momento de la venta es un detalle que separa un sistema serio de uno de juguete.

Capítulo 4

El catálogo y el carrito

La primera pieza que ve el cliente. El backend expone los productos; el frontend los muestra y arma el carrito. El carrito vive en el navegador hasta que el cliente confirma.

El endpoint del catálogo

main.py
@app.get("/productos")
def listar_productos():
    con = conectar()
    r = [dict(x) for x in con.execute(
        "SELECT * FROM productos ORDER BY categoria, nombre")]
    con.close()
    return r

El carrito, del lado del cliente

El carrito es estado del frontend: una lista de {producto_id, cantidad} que el cliente arma agregando cosas. No necesita tocar el servidor hasta el final. Cuando confirma, el frontend manda todo junto a POST /pedidos.

frontend · agregar al carrito
let carrito = [];
function agregar(id) {
  const item = carrito.find(i => i.producto_id === id);
  if (item) item.cantidad++;
  else carrito.push({ producto_id: id, cantidad: 1 });
  render();
}
El precio final lo pone el servidor

El carrito muestra precios para el cliente, pero el total que se cobra lo calcula el backend leyendo los precios de la base. Nunca confíes en un total que llega del navegador: un atacante lo edita y te paga lo que quiera. El frontend propone; el servidor dispone. Otra vez la regla del librito 09.

Capítulo 5

Crear un pedido con control de stock

El corazón de la tienda. Acá pasa lo importante: se valida el stock, se calcula el total del lado seguro, se guarda el pedido y se descuenta el inventario. Todo en un solo paso, o nada.

Los pasos, en orden

Uno: por cada item, buscar el producto y verificar que haya stock. Dos: si falta stock de algo, rechazar todo antes de cobrar. Tres: calcular el total con los precios de la base. Cuatro: guardar el pedido y sus items, y descontar el stock.

main.py · validar y descontar
for it in p.items:
    prod = cur.execute("SELECT * FROM productos WHERE id=?",
                       (it.producto_id,)).fetchone()
    if not prod:
        raise HTTPException(404, f"producto {it.producto_id} no existe")
    if prod["stock"] < it.cantidad:
        raise HTTPException(409, f"sin stock de {prod['nombre']} "
                                 f"(quedan {prod['stock']})")
    total += prod["precio"] * it.cantidad
# ... guardar pedido e items, y por cada uno:
cur.execute("UPDATE productos SET stock = stock - ? WHERE id=?",
            (cant, prod["id"]))

Stock y concurrencia

Si dos clientes compran el último producto al mismo tiempo, mal hecho, los dos "ganan" y quedás en negativo. En producción esto se resuelve con una transacción y un chequeo atómico (UPDATE ... SET stock = stock - ? WHERE id=? AND stock >= ?). Con una base Postgres (librito 10) y una transacción, el control de consumo es a prueba de simultáneos.

Capítulo 6

Pagos con MercadoPago

El método más usado en Argentina. La idea de MercadoPago Checkout Pro es elegante: vos no cobrás, vos creás una "preferencia" con los items y MP te da un link. El cliente paga en el entorno de MP, y vos nunca tocás una tarjeta.

El flujo

Checkout Pro, paso a paso
1. Tu backend arma la preferencia (items, monto, referencia del pedido)
2. La manda a la API de MP con tu ACCESS_TOKEN
3. MP devuelve un "init_point" = el link de pago
4. Mandás al cliente a ese link (MP muestra su checkout)
5. El cliente paga (tarjeta, dinero en cuenta, etc.) EN MP
6. MP te avisa el resultado por un webhook (próximo capítulo)

Crear la preferencia

pagos.py
def crear_preferencia_mp(items, pedido_id):
    cuerpo = {
        "items": items,
        "external_reference": str(pedido_id),   # para reconocer el pedido
        "back_urls": {"success": "...", "failure": "..."},
        "notification_url": "https://tutienda.com/api/webhook/mp",
    }
    req = urllib.request.Request(
        "https://api.mercadopago.com/checkout/preferences",
        data=json.dumps(cuerpo).encode(),
        headers={"Authorization": f"Bearer {MP_ACCESS_TOKEN}",
                 "Content-Type": "application/json"}, method="POST")
    data = json.load(urllib.request.urlopen(req))
    return {"pref_id": data["id"], "init_point": data["init_point"]}

Nunca toques datos de tarjeta

La gran ventaja de Checkout Pro: los datos de la tarjeta se cargan en MercadoPago, no en tu sitio. Vos nunca los ves, ni los guardás, ni los transmitís. Eso te saca de encima casi toda la responsabilidad legal y de seguridad (PCI). Manejar tarjetas en tu propio frontend está prohibido de hecho por la regla de seguridad de esta colección, y con razón.

Sobre las credenciales

Este ejemplo necesita tu ACCESS_TOKEN de MercadoPago (se saca gratis en tu cuenta de MP, hay uno de prueba y uno de producción). Va en una variable de entorno, nunca en el código. Sin token, el ejemplo muestra el body que se enviaría, que es lo que ves arriba, para que entiendas el flujo sin tener que crear una cuenta.

Capítulo 7

El webhook: confirmar el pago del lado seguro

Acá está el error más peligroso de los pagos, y cómo se evita. La pregunta es: ¿cómo sabés que el cliente realmente pagó? La respuesta correcta no es "porque volvió a la página de éxito".

Por qué el redirect no alcanza

Cuando el cliente termina en MP, vuelve a tu back_url de éxito. Pero esa vuelta la controla el navegador, y el navegador se puede falsear: cualquiera puede entrar a mano a tu URL de éxito sin haber pagado. Confiar en el redirect para dar por pagado un pedido es cómo te vacían el negocio.

La forma correcta: el webhook

MercadoPago llama a tu notification_url desde sus servidores cuando un pago cambia de estado. Tu backend recibe ese aviso, le pregunta a MP por el pago (server-to-server, con tu token) y recién ahí marca el pedido como pagado. El dato viene de MP, no del navegador.

pagos.py + main.py
def procesar_webhook_mp(cuerpo):
    pago_id = cuerpo.get("data", {}).get("id")
    # le preguntamos a MP por el pago, con nuestro token
    req = urllib.request.Request(
        f"https://api.mercadopago.com/v1/payments/{pago_id}",
        headers={"Authorization": f"Bearer {MP_ACCESS_TOKEN}"})
    pago = json.load(urllib.request.urlopen(req))
    return pago.get("external_reference"), pago.get("status")

@app.post("/webhook/mp")
def webhook_mp(cuerpo: dict):
    ref, estado = procesar_webhook_mp(cuerpo)
    if ref and estado == "approved":       # solo si MP dice "approved"
        # marcar el pedido como pagado
        ...
    return {"ok": True}
La regla de oro de los pagos

Un pedido se marca como pagado solo cuando el proveedor de pago te lo confirma del lado del servidor. Nunca por lo que diga el navegador, nunca por un total que llegue del frontend. Esta única regla evita el fraude más común en tiendas online. Vale para MercadoPago, Stripe, y cualquiera.

Capítulo 8

Pago con QR

El QR es comodísimo: el cliente lo escanea con la app del banco o de MP y paga sin tipear nada. Y generar un QR es sorprendentemente simple. Este es un QR real, generado por el sistema.

Qué es, en el fondo

Un QR es solo una forma de codificar un texto en una imagen. Para un pago, ese texto lleva los datos: a quién pagar (tu alias), cuánto, y la referencia del pedido. La app que lo escanea lee ese texto y precarga la transferencia.

pagos.py · generar el QR
import qrcode

def generar_qr_pago(monto, pedido_id, ruta_png):
    contenido = (f"PAGO|alias={ALIAS_TIENDA}|monto={monto:.2f}"
                 f"|ref=PEDIDO-{pedido_id}")
    img = qrcode.make(contenido)   # crea el QR
    img.save(ruta_png)
    return contenido

El QR real de un pedido

Este es el QR que generó el sistema para el pedido #201 (total $22.600). Se escanea de verdad: al leerlo, devuelve exactamente el texto de pago.

QR estático vs dinámico

Este es un QR que armamos nosotros con los datos del pedido. Para cobrar de verdad con acreditación automática, MercadoPago tiene su propia API de QR que genera un QR "oficial" y te avisa por webhook cuando se paga (igual que Checkout Pro). El concepto es el mismo; la diferencia es quién confirma el pago. Para empezar, un QR con tu alias ya deja cobrar por transferencia.

Capítulo 10

El sistema de reservas

La tienda tiene mesas. Reservar parece simple, pero tiene una trampa clásica: no superar la capacidad. Dos reservas para la misma hora no pueden sumar más gente de la que entra.

La regla: capacidad por franja

Cada franja horaria tiene un cupo (digamos 20 personas). Antes de confirmar una reserva, el backend suma cuánta gente ya hay reservada en esa fecha y hora, y solo confirma si entra. Es el mismo patrón del control de stock: verificar antes de comprometer.

main.py
@app.post("/reservas")
def crear_reserva(r: ReservaIn):
    ocupadas = con.execute(
        "SELECT COALESCE(SUM(personas),0) c FROM reservas"
        " WHERE fecha=? AND hora=? AND estado='confirmada'",
        (r.fecha, r.hora)).fetchone()["c"]
    if ocupadas + r.personas > CAPACIDAD_POR_HORA:
        raise HTTPException(409, f"sin lugar a las {r.hora} "
                                 f"(ocupadas {ocupadas}/{CAPACIDAD_POR_HORA})")
    # ... confirmar

Fijate que reservar y comprar comparten la lógica: verificar disponibilidad, y solo entonces comprometer. Stock de productos o cupos de mesas, es el mismo problema. Reconocer patrones así es lo que te hace más rápido: ya sabés resolverlo.

Ventas: top productos y facturación

Las dos preguntas más básicas: qué se vende más, y cuánto entra. Dos consultas SQL con GROUP BY y SUM, y ya tenés el pulso del negocio.

Unidades no es lo mismo que facturación

Mirá el dato: la gaseosa lidera en unidades, pero la milanesa, con la mitad de unidades, factura casi tres veces más. Vender mucho no es facturar mucho. Un dashboard que muestra las dos columnas te salva de optimizar lo que no conviene. Ese es el valor de medir bien.

Facturación por día

Un GROUP BY DATE(creado_en) te da la serie diaria, que en el panel es el gráfico de línea de arriba. Sirve para ver la tendencia y detectar el bajón de un martes o el pico de un finde.

Capítulo 13

Combos: qué se pide junto con qué

Esta es la consulta más jugosa del dashboard, y la más ingeniosa. Descubre qué productos aparecen juntos en el mismo pedido. Es la base de las promos, los combos y el "¿querés sumar...?".

La idea: un pedido consigo mismo

Para encontrar pares, unimos la tabla de items con ella misma (un self-join): por cada pedido, cruzamos cada item con los otros items del mismo pedido. La condición producto_id < producto_id evita contar el par dos veces y evita cruzar un producto consigo mismo.

stats.py · el self-join
SELECT a.nombre AS producto_a, b.nombre AS producto_b,
       COUNT(*) AS veces
FROM pedido_items ia
JOIN pedido_items ib
  ON ia.pedido_id = ib.pedido_id       -- mismo pedido
 AND ia.producto_id < ib.producto_id   -- pares, sin repetir
JOIN productos a ON a.id = ia.producto_id
JOIN productos b ON b.id = ib.producto_id
GROUP BY ia.producto_id, ib.producto_id
ORDER BY veces DESC
LIMIT 5
salida real✓ salida real
  47 pedidos   Empanada de carne + Gaseosa 500ml
  34 pedidos   Pizza napolitana + Cerveza artesanal
  34 pedidos   Pizza napolitana + Flan casero
  34 pedidos   Cerveza artesanal + Flan casero
  27 pedidos   Milanesa con papas + Flan casero
De un dato a una decisión

"Empanadas + gaseosa" es el par más pedido, 47 veces: ahí hay un combo natural con descuento. "Napolitana + cerveza + flan" aparecen los tres cruzados entre sí: es un combo de tres. Esto es lo mismo que hace Amazon con su "quienes compraron esto también compraron". Vos lo tenés, gratis, con un self-join sobre tus propios pedidos.

Capítulo 15

Inventario y control de consumo

El stock no es una foto: baja con cada venta. El sistema ya lo descuenta solo (capítulo 5). Lo que falta es que avise cuándo reponer, antes de quedarte sin vender algo.

Consumo automático

Cada pedido descuenta el stock de lo que se vendió. Eso ya lo hace el endpoint de pedidos: UPDATE productos SET stock = stock - cantidad. Así el inventario refleja siempre lo que realmente queda, sin que nadie lo cargue a mano. Ese es el control de consumo.

Alerta de reposición

Cada producto tiene un stock_min. El dashboard lista los que llegaron o bajaron de ese mínimo: la lista de compras del dueño, calculada sola.

stats.py
SELECT nombre, stock, stock_min
FROM productos
WHERE stock <= stock_min
ORDER BY stock ASC

Capítulo 16

La seguridad de todo el sistema

Un sistema que cobra y guarda datos de clientes tiene que ser seguro. Repasemos, todo junto, las decisiones de seguridad que fuimos tomando. Ninguna es opcional.

El repaso

  • Nunca tocar datos de tarjeta: el cobro lo hace MercadoPago en su entorno. Tu sistema jamás ve una tarjeta.
  • El pago se confirma del lado del servidor: por webhook o a mano, nunca por el redirect del navegador.
  • El total lo calcula el backend: con los precios de la base, nunca lo que manda el frontend.
  • El stock se valida y descuenta en el servidor: el navegador no decide si hay o no disponibilidad.
  • Las credenciales van en variables de entorno: el token de MP, la conexión a la base, nunca en el código ni en Git.
  • Toda entrada se valida: Pydantic tipa lo que llega; las consultas van parametrizadas contra inyección SQL (librito 07).
  • El dashboard es solo del dueño: en producción, detrás de login con rol de admin (el JWT del librito 09).
El frontend nunca se confía

Si tuvieras que quedarte con una sola idea de todo el librito, es esta: el navegador está en manos del usuario y se puede manipular entero. Precios, totales, stock, "ya pagué": nada de eso se cree si viene del frontend. El servidor valida, calcula y confirma todo. Esa desconfianza sana es lo que separa un sistema que se puede vaciar de uno que aguanta.

Capítulo 17

Construir un sistema así con IA

Un proyecto de este tamaño es justo donde la IA de hoy más te acelera, si la sabés dirigir. La clave es no pedir "haceme una tienda", sino ir pieza por pieza, como hicimos en el librito.

Cómo encararlo

  • Empezá por el modelo de datos: "Diseñá las tablas para una tienda de comida con productos, pedidos, items, pagos y reservas." Revisá el esquema antes de seguir; es el cimiento.
  • Pedí un endpoint a la vez: "Hacé el endpoint de crear pedido en FastAPI que valide stock, calcule el total del lado servidor y descuente inventario." Concreto y acotado sale bien.
  • Integraciones con su documentación: "Integrá MercadoPago Checkout Pro con webhook de confirmación." La IA conoce estas APIs, pero verificá contra la doc oficial de MP.
  • Las consultas del dashboard: "Dame el SQL para los pares de productos que más se piden juntos." El self-join es difícil de recordar y la IA lo resuelve al toque.

Herramientas de hoy

Un editor con IA (Cursor, Claude Code, Copilot) te acompaña escribiendo cada módulo con contexto de tu proyecto. Para el frontend y el dashboard, herramientas como v0 o Lovable generan la interfaz a partir de una descripción. El backend, por el dinero y la seguridad que maneja, conviene entenderlo bien, no solo generarlo.

Lo que cobra plata, revisalo dos veces

La IA acelera muchísimo, pero acá hay pagos y stock de por medio. Todo lo que toca dinero (el cálculo del total, la confirmación del pago, el descuento de stock) revisalo línea por línea y probalo, como probamos todo en este libro. Un bug en un formulario es molesto; un bug en el cobro te cuesta plata real. La IA propone, vos validás.

Fin del librito

Lo que construiste

Un sistema completo para un negocio real: cobra de tres formas, toma reservas sin superponerlas, y le da al dueño un panel que le dice qué vender, cuándo y con qué. Eso es software que resuelve un problema de verdad.

El sistema, de una mirada

  • Catálogo y carrito, con precios del lado seguro.
  • Pedidos con control de stock y descuento automático.
  • Pagos con MercadoPago (con webhook), QR real y transferencia.
  • Reservas con control de capacidad por franja.
  • Dashboard: top productos, facturación, combos, picos por hora, y reposición.
  • Seguridad en cada capa: nunca confiar en el frontend.
