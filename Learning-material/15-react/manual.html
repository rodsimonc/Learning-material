Frontend · React con TypeScript

React, reconstruyendo la tienda

Ya sabés HTML, CSS, JavaScript y TypeScript. React es el paso que junta todo: construir interfaces con piezas reutilizables (componentes) que se actualizan solas cuando cambian los datos. Para que se vea de verdad, en este librito reconstruimos el frontend de la tienda de alimentos (catálogo + carrito) en React, con TypeScript, y lo probamos corriendo.

Código real y probado

La app de la tienda en React se compiló, se buildeó con Vite y se probó en un navegador: agregar al carrito, calcular el total, quitar productos. Los bloques con ✓ salida real son esas corridas. El proyecto completo está en ejemplos/.

Qué vas a poder hacer al terminar

Armar componentes con JSX, pasarles datos con props, manejar estado con useState, renderizar listas, responder a eventos, reutilizar lógica con custom hooks, consumir una API, y entender por qué se usa TanStack Query. En resumen: construir una app React de verdad.

Capítulo 1

Qué es React y por qué

React es una librería para construir interfaces. Su idea central: describís cómo se ve la UI según los datos, y React se encarga de actualizar la pantalla cuando esos datos cambian. Vos no tocás el DOM a mano; declarás el resultado.

Declarativo vs imperativo

En JavaScript puro (librito del DOM) actualizás la pantalla a mano: buscás un elemento, le cambiás el texto, agregás una fila. Es imperativo: das los pasos. En React describís "el carrito muestra estos items", y cuando los items cambian, React redibuja lo necesario, solo. Es declarativo: describís el qué, no el cómo.

DOM a mano (imperativo)React (declarativo)
Buscás el elemento y lo modificás en cada cambioDescribís la UI según el estado; React actualiza
Fácil que la pantalla y los datos se desincronicenLa pantalla siempre refleja el estado actual
Mucho código repetido para actualizarComponentes reutilizables
Componentes: la idea de fondo

Una app React es un árbol de componentes: piezas independientes que combinás, como los web components del librito 12 pero con superpoderes. Una tarjeta de producto, un carrito, un header. Cada uno tiene su UI y su lógica, y los reusás. Pensar en componentes es el corazón de React.

Capítulo 2

Componentes y JSX

Un componente es una función que devuelve interfaz. Esa interfaz se escribe en JSX: HTML dentro de JavaScript. Suena raro y se vuelve natural en cinco minutos.

un componente simple
export default function App() {
  return (
    <div className="app">
      <header><h1>Sabores del Barrio</h1></header>
    </div>
  );
}

JSX: HTML con JavaScript adentro

Dentro del JSX podés meter JavaScript entre llaves: {producto.nombre}, {precio * 2}. Un par de diferencias con el HTML normal: se escribe className en vez de class (porque class es palabra reservada de JS), y los atributos van en camelCase (onClick).

JavaScript dentro del JSX
<p className="precio">${producto.precio.toLocaleString("es-AR")}</p>
Un componente, un archivo

La convención: cada componente en su archivo .tsx, con la primera letra en mayúscula (TarjetaProducto.tsx). La mayúscula no es capricho: React distingue tus componentes de las etiquetas HTML por eso. <div> es HTML; <TarjetaProducto> es tuyo.

Capítulo 3

Props: pasarle datos a un componente

Un componente reutilizable necesita recibir datos: la tarjeta de producto tiene que servir para cualquier producto. Eso son las props: los parámetros de un componente. Y con TypeScript, van tipadas.

componentes/TarjetaProducto.tsx
interface Props {
  producto: Producto;
  onAgregar: (p: Producto) => void;
}

export function TarjetaProducto({ producto, onAgregar }: Props) {
  return (
    <div className="tarjeta">
      <span className="cat">{producto.categoria}</span>
      <h3>{producto.nombre}</h3>
      <p className="precio">${producto.precio.toLocaleString("es-AR")}</p>
      <button onClick={() => onAgregar(producto)}>Agregar</button>
    </div>
  );
}

La interface Props (del librito 14) dice qué recibe: un producto y una función onAgregar. Si el padre se olvida de pasar una prop, o pasa el tipo equivocado, no compila. El componente y quien lo usa quedan sincronizados por el compilador.

Datos hacia abajo, eventos hacia arriba

Fijate el patrón: el producto baja como prop, y cuando el usuario aprieta "Agregar", el componente avisa hacia arriba llamando onAgregar. Los datos fluyen hacia abajo (padre → hijo) y las acciones suben (hijo → padre). Ese flujo de una dirección es lo que hace a React predecible.

Capítulo 4

Estado: useState

El estado es lo que cambia con el tiempo en tu app: el contenido del carrito, un contador, un formulario. Cuando el estado cambia, React vuelve a dibujar. El hook useState es cómo se guarda estado en un componente.

useState
const [items, setItems] = useState<ItemCarrito[]>([]);
//     ^valor  ^para cambiarlo        ^tipo        ^inicial

useState devuelve dos cosas: el valor actual (items) y una función para cambiarlo (setItems). Nunca modificás items a mano; siempre usás setItems, y ahí React sabe que tiene que redibujar. El <ItemCarrito[]> es el genérico del librito 14: le dice a React qué tipo de estado es.

actualizar estado sin mutarlo
function agregar(producto: Producto) {
  setItems((prev) => [...prev, { producto, cantidad: 1 }]);
}
No mutes el estado, creá uno nuevo

Fijate el [...prev, nuevo]: creamos un array nuevo en vez de hacer items.push(). React detecta el cambio comparando referencias, así que si mutás el array viejo, no se entera y no redibuja. Siempre devolvé un valor nuevo. Es el error número uno de quien arranca con React.

Capítulo 5

Renderizar listas

El catálogo es una lista de productos, el carrito una lista de items. En React, una lista se dibuja recorriendo el array con map y devolviendo un componente por elemento.

App.tsx · el catálogo
<section className="catalogo">
  {CATALOGO.map((p) => (
    <TarjetaProducto key={p.id} producto={p} onAgregar={agregar} />
  ))}
</section>

La prop key

Cada elemento de una lista necesita una key única (acá, p.id). React la usa para saber qué cambió cuando la lista se modifica, y actualizar solo eso en vez de rehacer todo. Sin key, React te avisa con un warning, y puede redibujar de más o mezclar elementos.

La key tiene que ser estable y única

Usá el id de tus datos como key, no el índice del array. Si usás el índice y la lista se reordena o se borra un item del medio, React se confunde. El id de la base de datos (librito 10) es la key perfecta: único y estable.

Capítulo 6

Eventos: responder al usuario

Un clic, un texto que se tipea, un formulario que se envía. En React, los eventos se manejan con props como onClick, pasándoles una función. Es lo que conecta la interfaz con tu lógica.

manejar un clic
<button onClick={() => onAgregar(producto)}>Agregar</button>

Cuando el usuario aprieta, se llama la función, que actualiza el estado (setItems), y React redibuja con el carrito nuevo. Ese es el ciclo completo de React: evento → cambia el estado → se redibuja la UI. Todo lo demás son variaciones de eso.

Probado de verdad

interacción real en el navegador✓ salida real
productos renderizados: 6
carrito inicial: Vacío
-- agrego 2× Milanesa ($9.500) + 1× Pizza napolitana ($9.800) --
items en carrito: 2
total: $28.800          (9500×2 + 9800 = 28.800 ✓)
-- quito la milanesa --
total tras quitar: $9.800   (✓)
errores de consola: ninguno
El ciclo, funcionando

Esa salida es el ciclo de React de punta a punta: el clic en "Agregar" cambió el estado del carrito, y React recalculó el total y redibujó, sin que toquemos el DOM ni una vez. Vos describís el resultado; React hace el trabajo sucio.

Capítulo 7

Custom hooks: reutilizar lógica

Toda la lógica del carrito (agregar, quitar, calcular total) la sacamos a un "custom hook": una función que empieza con use y encapsula estado y comportamiento. Es cómo React reutiliza lógica entre componentes.

useCarrito.ts
export function useCarrito() {
  const [items, setItems] = useState<ItemCarrito[]>([]);

  function agregar(producto: Producto) { /* ... setItems ... */ }
  function quitar(id: number) {
    setItems((prev) => prev.filter((i) => i.producto.id !== id));
  }

  const total = items.reduce(
    (acc, i) => acc + i.producto.precio * i.cantidad, 0);

  return { items, agregar, quitar, total };
}

Y el componente queda limpísimo: solo pide lo que necesita.

App.tsx
const { items, agregar, quitar, total } = useCarrito();
Separar la lógica de la vista

El hook maneja el "qué hace" el carrito; el componente, el "cómo se ve". Esa separación (que ya viste en el librito de arquitectura) hace el código más fácil de entender, testear y reusar. Si mañana querés el mismo carrito en otra pantalla, importás useCarrito y listo.

Capítulo 8

useEffect y consumir una API

En la app real, el catálogo no está escrito a mano: viene del backend (GET /productos, librito 09). Para pedir datos cuando el componente aparece, se usa el hook useEffect.

pedir datos al montar el componente
const [productos, setProductos] = useState<Producto[]>([]);

useEffect(() => {
  fetch("http://localhost:8000/productos")
    .then((r) => r.json())
    .then((data: Producto[]) => setProductos(data));
}, []);   // el [] vacío = correr una sola vez, al aparecer

useEffect corre código después de que el componente se dibuja. Ese array vacío al final ([]) dice "una sola vez, al montar". Cuando llegan los datos, setProductos actualiza el estado y React redibuja el catálogo con lo real.

Los tres estados, de nuevo

Como en el librito 12, una carga de datos tiene tres momentos: cargando, éxito y error. En React eso son estados: const [cargando, setCargando] = useState(true). Mostrás un "cargando…", y cuando llega o falla, actualizás. Manejar los tres siempre es la diferencia entre una app pulida y una que parpadea o se cuelga.

Capítulo 9

TanStack Query: pedir datos, en serio

Hacer fetch con useEffect funciona, pero a mano tenés que manejar loading, error, recargas, caché y datos repetidos. TanStack Query resuelve todo eso, y es lo que se usa en proyectos reales para hablar con el backend.

Lo mismo, pero resuelto

con TanStack Query
const { data, isLoading, error } = useQuery({
  queryKey: ["productos"],
  queryFn: () => fetch("/api/productos").then((r) => r.json()),
});

if (isLoading) return <p>Cargando…</p>;
if (error) return <p>Error al cargar</p>;
// data tiene los productos

En pocas líneas tenés los tres estados resueltos (isLoading, error, data), y además: caché automática (no vuelve a pedir lo que ya tiene), recarga en segundo plano, y reintentos. Ese queryKey identifica el dato en la caché.

Estado del servidor vs estado local

La idea clave de TanStack Query: los datos del servidor no son lo mismo que el estado de tu UI. El carrito es estado local (useState); el catálogo que viene del backend es "estado del servidor", y para eso TanStack Query es la herramienta. Distinguir los dos ordena cualquier app que consume una API.

Estructura de un proyecto React

Un proyecto React no es un archivo suelto: es un proyecto con su estructura y sus herramientas. La más usada para armarlo es Vite, que da el servidor de desarrollo y el build de producción.

Capítulo 11

El resultado: la tienda en React

Juntando todo (componentes, props, estado, listas, eventos y el hook del carrito), esta es la tienda funcionando. Catálogo a la izquierda, carrito a la derecha que se actualiza solo con cada clic.

Cómo se conecta todo

El App usa useCarrito para el estado, recorre el catálogo con map pintando una TarjetaProducto por producto, y le pasa al Carrito los items y el total. Cuando apretás "Agregar", el evento actualiza el estado del hook, y React redibuja el carrito y el total. Cada pieza hace su parte.

Comparado con vanilla

La misma tienda en JavaScript puro (librito del DOM) sería mucho más código, actualizando el carrito y el total a mano en cada cambio. En React, describís cómo se ve según el estado y listo. Esa es la ganancia que justifica aprender React: menos código de "actualizar la pantalla", más foco en la lógica.

Capítulo 12

Buenas prácticas y errores comunes

React tiene un par de trampas que todo el mundo pisa al principio. Conocerlas de antemano te ahorra horas de "por qué no se actualiza".

Errores clásicos

  • Mutar el estado: items.push(x) en vez de setItems([...items, x]). React no detecta la mutación y no redibuja. Siempre creá un valor nuevo.
  • Listas sin key o con el índice como key: causa bugs raros al reordenar. Usá un id estable.
  • Demasiado en un componente: si un componente hace mil cosas, partilo. Componentes chicos y enfocados.
  • useEffect para todo: muchas cosas que la gente mete en useEffect se calculan directo al renderizar (como el total del carrito). Usá useEffect solo para efectos externos (pedir datos, suscripciones).

Buenas costumbres

  • Componentes chicos, con una responsabilidad clara.
  • Props tipadas con TypeScript (librito 14).
  • Lógica reutilizable en custom hooks.
  • Datos del servidor con TanStack Query; estado de UI con useState.
El siguiente escalón

Cuando la app crece, aparecen: un router (TanStack Router o React Router) para varias páginas, y manejo de estado global si muchos componentes comparten datos. Pero no corras: con componentes, props, estado y hooks, ya construís aplicaciones reales completas. Lo demás se suma cuando el proyecto lo pide.

Fin del librito

Con IA, checklist y cierre

React es de lo que más rápido se genera con IA: hay herramientas que te arman una interfaz entera a partir de una descripción o una imagen. La clave es entender lo que te dan para poder ajustarlo.

React con IA

  • Generar componentes: "Hacé un componente React con TypeScript de una tarjeta de producto con props tipadas." Sale listo.
  • De diseño a código: herramientas como v0 o Lovable convierten una descripción o un mockup en componentes React funcionales.
  • Refactorizar: "Sacá esta lógica a un custom hook", "convertí este componente de clase a función". Tareas mecánicas que la IA hace bien.
  • Entender errores: pegá el warning de React o de TypeScript y pedí la explicación.

Checklist

  • Pensá en componentes: piezas chicas y reutilizables.
  • Props tipadas; datos bajan, eventos suben.
  • Estado con useState; nunca mutar, siempre valor nuevo.
  • Listas con map y key estable.
  • Lógica en custom hooks.
  • Datos del servidor con TanStack Query.
