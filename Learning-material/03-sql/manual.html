Bases de datos y SQL, de cero

Casi toda aplicación guarda datos en una base de datos, y SQL es el idioma para hablarles. Este libro te lleva de no saber qué es una tabla a escribir consultas con joins, agrupaciones e índices. Los bloques con ✓ salida real se ejecutaron contra una base de verdad (SQLite).

Cómo está armado

  • Parte 1, fundamentos. Qué es una base relacional, cómo crear tablas e insertar y leer datos.
  • Parte 2, consultas de verdad. Filtrar fino, combinar tablas con JOIN, agrupar y agregar, y modificar datos con cuidado.
  • Parte 3, que ande bien. Índices y performance, transacciones, y cómo consultar desde tu código sin abrir agujeros de seguridad.
  • Parte 4, a producción. Normalización, migraciones, backups y una cheatsheet.

Capítulo 1

Qué es una base de datos relacional

Una base de datos relacional guarda la información en tablas: filas y columnas, como una planilla, pero con reglas estrictas y la capacidad de relacionar tablas entre sí. Postgres, MySQL, SQLite y SQL Server son todas de este tipo.

El vocabulario

  • Tabla. Un conjunto de datos del mismo tipo. Una tabla usuarios, una tabla pedidos.
  • Fila (o registro). Un elemento. Un usuario concreto.
  • Columna (o campo). Un atributo. El nombre, la ciudad.
  • Esquema. La definición de qué columnas tiene cada tabla y de qué tipo. La estructura, fijada de antemano.

Claves: cómo se identifican y se relacionan

Cada fila tiene una clave primaria (primary key), un valor único que la identifica, casi siempre un id. Y una tabla puede apuntar a otra con una clave foránea (foreign key): la tabla pedidos guarda el usuario_id del usuario que hizo el pedido. Así se relacionan las tablas, de ahí el nombre "relacional".

SQL: el idioma

SQL (Structured Query Language) es cómo le hablás a la base. Es declarativo: describís qué querés, no cómo buscarlo. Decís "dame los usuarios de Rosario" y el motor se encarga de encontrarlos rápido.

Relacional vs NoSQL

Existen bases no relacionales (MongoDB, Redis) que guardan documentos o pares clave-valor, útiles para otros casos. Este libro es sobre relacionales, que siguen siendo el default para la mayoría de las apps porque garantizan estructura y consistencia.

SQL es casi el mismo en todos los motores, así que lo que aprendas acá sirve en cualquiera. Pero conviene saber cuál elegir según el proyecto.

Para empezar, SQLite

SQLite no necesita instalar un servidor: es una librería, y la base es un solo archivo .db. Python ya lo trae incluido. Todo lo de este libro corre con esto:

python
import sqlite3
con = sqlite3.connect("mi_base.db")   # crea el archivo si no existe
cur = con.cursor()
cur.execute("SELECT 1")
print(cur.fetchone())                 # (1,)

Cuando pases a Postgres, cambia la forma de conectarte y poco más. Las consultas SQL son casi idénticas.

Capítulo 3

Crear tablas

Antes de guardar datos hay que definir la estructura. Con CREATE TABLE decís qué columnas hay, de qué tipo, y qué reglas cumplen.

Las dos tablas del libro

sql
CREATE TABLE usuarios (
  id      INTEGER PRIMARY KEY,        -- identifica cada fila
  nombre  TEXT NOT NULL,              -- obligatorio
  ciudad  TEXT
);

CREATE TABLE pedidos (
  id          INTEGER PRIMARY KEY,
  usuario_id  INTEGER NOT NULL REFERENCES usuarios(id),  -- clave foránea
  producto    TEXT NOT NULL,
  monto       REAL NOT NULL,
  fecha       TEXT
);

Los pedazos importantes

  • Tipos. INTEGER, TEXT, REAL (decimal). En Postgres tenés más: VARCHAR, TIMESTAMP, BOOLEAN, etc.
  • PRIMARY KEY. Marca la columna que identifica cada fila. Única y no nula.
  • NOT NULL. Esa columna no puede quedar vacía. Es tu primera línea de defensa contra datos incompletos.
  • REFERENCES. Declara la clave foránea: usuario_id tiene que existir en usuarios. La base no te deja crear un pedido de un usuario fantasma.
El esquema te protege

Fijar tipos y reglas de entrada evita basura en la base. Un monto siempre será un número, un pedido siempre tendrá un usuario real. Esas garantías son la razón de ser de las bases relacionales.

Capítulo 4

Insertar y leer datos

Con las tablas creadas, cargamos datos con INSERT y los leemos con SELECT, el comando que más vas a escribir en tu vida.

Insertar filas

sql
INSERT INTO usuarios (id, nombre, ciudad)
VALUES (1, 'Carlos', 'Mar del Plata');

INSERT INTO pedidos (id, usuario_id, producto, monto, fecha)
VALUES (1, 1, 'Teclado', 25000, '2026-08-01');

SELECT: la consulta base

Elegís qué columnas (SELECT nombre, ciudad) y de qué tabla (FROM usuarios):

SELECT nombre, ciudad FROM usuarios;✓ salida real
nombre | ciudad
----------------------
Carlos | Mar del Plata
Ana    | Rosario
Luis   | Rosario
Sofia  | Córdoba

El * trae todas las columnas: SELECT * FROM usuarios. Cómodo para explorar, pero en código conviene nombrar solo lo que usás.

Ordenar y limitar

ORDER BY ordena, DESC de mayor a menor, LIMIT corta la cantidad:

SELECT producto, monto FROM pedidos ORDER BY monto DESC LIMIT 3;✓ salida real
producto | monto
------------------
Monitor  | 90000.0
Monitor  | 90000.0
Teclado  | 25000.0
Capítulo 5

Filtrar con WHERE

WHERE es cómo pedís solo las filas que cumplen una condición. Es el filtro, y tiene varios operadores que conviene tener a mano.

Rangos con BETWEEN

WHERE monto BETWEEN 10000 AND 50000✓ salida real
producto | monto
------------------
Teclado  | 25000.0
Mouse    | 12000.0
Teclado  | 25000.0

Listas con IN

WHERE ciudad IN ('Rosario','Córdoba')✓ salida real
nombre
------
Ana
Luis
Sofia

Texto con LIKE

LIKE busca patrones. El % es "cualquier cosa": 'M%' es "empieza con M".

WHERE producto LIKE 'M%'✓ salida real
producto
--------
Mouse
Monitor
Monitor
NULL es especial

Para preguntar por vacíos no se usa = NULL (eso nunca da verdadero), se usa IS NULL o IS NOT NULL. Es el error de principiante más común con WHERE.

Capítulo 6

Combinar tablas con JOIN

Acá está el corazón de lo relacional. Un JOIN combina filas de dos tablas usando la relación entre ellas. Es lo que te deja preguntar "qué pidió cada usuario" cuando los pedidos viven en otra tabla.

INNER JOIN: lo que coincide

Une cada pedido con su usuario, cruzando pedidos.usuario_id con usuarios.id:

sql✓ salida real
SELECT u.nombre, p.producto, p.monto
FROM pedidos p
JOIN usuarios u ON u.id = p.usuario_id
ORDER BY u.nombre;

nombre | producto | monto
---------------------------
Ana    | Monitor  | 90000.0
Ana    | Cable    | 3000.0
Carlos | Teclado  | 25000.0
Carlos | Mouse    | 12000.0
Carlos | Monitor  | 90000.0
Luis   | Teclado  | 25000.0

Las letras u y p son alias: acortan el nombre de la tabla para no repetirlo. El ON dice cómo se conectan las dos tablas.

LEFT JOIN: incluir los que no tienen match

El INNER JOIN deja afuera a Sofía, que no hizo pedidos. Si querés a todos los usuarios, incluso los que no compraron, usás LEFT JOIN:

sql✓ salida real
SELECT u.nombre, COUNT(p.id) AS pedidos
FROM usuarios u
LEFT JOIN pedidos p ON p.usuario_id = u.id
GROUP BY u.id
ORDER BY pedidos DESC;

nombre | pedidos
----------------
Carlos | 3
Ana    | 2
Luis   | 1
Sofia  | 0

Ahí está Sofía con 0. El LEFT JOIN conserva todas las filas de la tabla izquierda (usuarios) aunque no tengan pareja en la derecha (pedidos).

La diferencia en una línea

INNER JOIN trae solo lo que coincide en ambas tablas. LEFT JOIN trae todo lo de la izquierda, y completa con vacío lo que falta a la derecha.

Capítulo 7

Agregar y agrupar

Las funciones de agregación resumen muchas filas en un número: contar, sumar, promediar. Combinadas con GROUP BY, responden preguntas de negocio reales.

Las funciones

COUNT() cuenta, SUM() suma, AVG() promedia, MAX() y MIN() el mayor y el menor.

GROUP BY: un resultado por grupo

GROUP BY junta las filas que comparten un valor y aplica la agregación a cada grupo. Y HAVING filtra sobre el resultado agrupado (como un WHERE, pero para grupos):

quién gastó más de 30000✓ salida real
SELECT u.nombre, SUM(p.monto) AS total, COUNT(*) AS cantidad
FROM pedidos p JOIN usuarios u ON u.id = p.usuario_id
GROUP BY u.id
HAVING total > 30000
ORDER BY total DESC;

nombre | total    | cantidad
----------------------------
Carlos | 127000.0 | 3
Ana    | 93000.0  | 2

Otro ejemplo: producto más vendido

sql✓ salida real
SELECT producto, COUNT(*) AS veces, AVG(monto) AS promedio
FROM pedidos GROUP BY producto ORDER BY veces DESC;

producto | veces | promedio
---------------------------
Teclado  | 2     | 25000.0
Monitor  | 2     | 90000.0
Mouse    | 1     | 12000.0
Cable    | 1     | 3000.0
WHERE vs HAVING

WHERE filtra filas antes de agrupar. HAVING filtra grupos después de agrupar. Si querés "pedidos mayores a 1000", es WHERE. Si querés "usuarios cuyo total supera 30000", es HAVING.

Capítulo 8

Modificar y borrar datos

UPDATE cambia filas existentes y DELETE las borra. Los dos comparten un detalle que arruinó muchos días: el WHERE.

UPDATE

UPDATE usuarios SET ciudad='Buenos Aires' WHERE id=4;✓ salida real
SELECT id, nombre, ciudad FROM usuarios WHERE id=4;

id | nombre | ciudad
--------------------------
4  | Sofia  | Buenos Aires

DELETE

sql
DELETE FROM pedidos WHERE id = 6;    -- borra un pedido puntual
El error que borra la base entera

Un UPDATE usuarios SET ciudad='X' sin WHERE cambia TODAS las filas. Un DELETE FROM pedidos sin WHERE borra TODO. Antes de un UPDATE o DELETE, escribí primero el SELECT con el mismo WHERE para ver qué filas vas a tocar. Y en producción, andá con transacciones (próximo capítulo), que te dan marcha atrás.

Capítulo 9

Índices: el mismo query, mucho más rápido

Un índice es como el índice de un libro: en vez de leer todas las páginas para encontrar algo, vas directo. Sin índice, la base recorre toda la tabla. Con índice, salta a las filas que importan.

Ver el plan de ejecución

EXPLAIN QUERY PLAN te dice cómo va a resolver el query la base. Sin índice, hace un SCAN: recorre toda la tabla.

sin índice✓ salida real
EXPLAIN QUERY PLAN SELECT * FROM pedidos WHERE usuario_id = 1;

detail
------------
SCAN pedidos

Ahora creamos un índice sobre usuario_id y repetimos:

con índice✓ salida real
CREATE INDEX idx_pedidos_usuario ON pedidos(usuario_id);
EXPLAIN QUERY PLAN SELECT * FROM pedidos WHERE usuario_id = 1;

detail
--------------------------------------------------------
SEARCH pedidos USING INDEX idx_pedidos_usuario (usuario_id=?)

Cambió de SCAN (leer todo) a SEARCH ... USING INDEX (ir directo). Con una tabla de millones de filas, esa diferencia es de segundos a milisegundos.

Cuándo indexar

  • Columnas que usás seguido en WHERE.
  • Columnas de claves foráneas, que se usan en JOINs.
  • Columnas por las que ordenás mucho.
No indexes todo

Cada índice acelera las lecturas pero hace más lentas las escrituras (hay que mantenerlo actualizado) y ocupa espacio. Indexá lo que consultás, no cada columna por las dudas.

Capítulo 10

Transacciones: todo o nada

Una transacción agrupa varias operaciones en una sola unidad: o pasan todas, o no pasa ninguna. Es lo que evita dejar la base a medio camino cuando algo falla.

El ejemplo clásico: una transferencia

Restar plata de una cuenta y sumarla a otra son dos operaciones. Si el sistema se cae entre las dos, la plata desaparece. La transacción garantiza que las dos pasen juntas o ninguna:

sql
BEGIN;
  UPDATE cuentas SET saldo = saldo - 1000 WHERE id = 1;
  UPDATE cuentas SET saldo = saldo + 1000 WHERE id = 2;
COMMIT;     -- confirma las dos juntas

-- si algo salió mal en el medio:
ROLLBACK;   -- deshace todo, como si nada hubiera pasado

ACID, las garantías

Las bases relacionales prometen cuatro cosas, resumidas en la sigla ACID:

LetraGarantía
AtomicityLa transacción pasa entera o no pasa. Nada a medias.
ConsistencyLa base pasa de un estado válido a otro válido, respetando las reglas.
IsolationTransacciones simultáneas no se pisan entre sí.
DurabilityUna vez confirmada, queda guardada aunque se corte la luz.
Cuándo usarlas

Siempre que varias operaciones tengan que pasar juntas para que los datos tengan sentido. Pagos, reservas, cualquier cosa donde un estado intermedio sea inválido.

Capítulo 11

Consultar desde tu código

Rara vez escribís SQL a mano en producción: lo corre tu aplicación. Y ahí hay una regla que no se negocia, porque de ella depende la seguridad de toda tu base.

Python

python
import sqlite3
con = sqlite3.connect("mi_base.db")
cur = con.cursor()

# consulta parametrizada: el ? es un hueco seguro
ciudad = "Rosario"
cur.execute("SELECT nombre FROM usuarios WHERE ciudad = ?", (ciudad,))
for fila in cur.fetchall():
    print(fila[0])

Node

javascript (pg, Postgres)
const { Client } = require("pg");
const client = new Client();
await client.connect();

const ciudad = "Rosario";
const r = await client.query(
  "SELECT nombre FROM usuarios WHERE ciudad = $1", [ciudad]  // $1 es el hueco
);
console.log(r.rows);
La regla que evita el hackeo más común

NUNCA armes SQL pegando texto del usuario: "... WHERE ciudad = '" + ciudad + "'". Eso es una inyección SQL esperando pasar: alguien manda ' OR '1'='1 y se lleva toda tu tabla. Usá siempre parámetros (? en SQLite, $1 en Postgres). La librería se encarga de escaparlos. Esto lo vemos a fondo en el librito de ciberseguridad.

ORMs: SQL sin escribir SQL

Muchos proyectos usan un ORM (SQLAlchemy, Prisma, Django ORM) que traduce objetos de tu lenguaje a SQL. Cómodo y seguro por defecto, pero conviene entender el SQL que genera. Por eso este libro va primero al SQL crudo.

Cierre

Buenas prácticas, migraciones y cheatsheet

Lo que hace a una base mantenible en el tiempo, y una hoja de referencia.

Normalización, en simple

No repitas datos. Si la ciudad de un usuario está en cada uno de sus pedidos, cuando se mude tenés que cambiar diez filas y alguna se te va a escapar. Guardala una sola vez en usuarios y referenciala. Esa idea de "cada dato en un solo lugar" es el corazón de la normalización.

Migraciones

El esquema cambia con el tiempo: agregás una columna, una tabla. Esos cambios se manejan con migraciones: archivos versionados que describen cada cambio, para aplicarlos igual en tu máquina y en producción. Herramientas: Alembic (Python), Prisma Migrate, Flyway. No cambies el esquema de producción a mano.

Backups

Una base sin backup es un accidente esperando pasar. Automatizá copias periódicas y, cada tanto, probá restaurarlas. Un backup que nunca probaste restaurar no es un backup, es una esperanza.
