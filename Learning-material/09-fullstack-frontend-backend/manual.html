Conectar frontend y backend, seguro

Ya tenés APIs (librito 01), frontend (el track completo) y seguridad (librito 07). Este libro los une: cómo conectar bien las dos mitades de una aplicación, con las arquitecturas recomendadas y sin abrir agujeros de seguridad. Todo por pasos, con un ejemplo real y probado, y con un capítulo sobre cómo hacerlo apoyándote en las herramientas de IA de hoy.

Código real y probado

El ejemplo (login con JWT + endpoint protegido) se construyó y se corrió de verdad. Los bloques con ✓ salida real son lo que devolvió el servidor. El código completo está en ejemplos/: backend en Python (FastAPI) y en Node (Express), y el frontend que los consume.

Capítulo 1

Cómo se conectan las dos mitades

Una aplicación moderna tiene dos mitades que corren por separado: el frontend en el navegador del usuario, y el backend en un servidor. Se hablan por HTTP, con una API en el medio.

El modelo

  FRONTEND (navegador)              BACKEND (servidor)
  HTML + CSS + JS                   lógica + base de datos
        │                                  │
        │   fetch("/api/perfil")           │
        │ ──────── request (JSON) ───────▶ │
        │                                  │  valida, consulta la base
        │ ◀─────── response (JSON) ─────── │
        │                                  │
   muestra los datos

El frontend no toca la base de datos ni la lógica de negocio: se los pide al backend a través de la API (librito 01). El backend no sabe de colores ni botones: solo recibe pedidos, valida, y devuelve datos. Esa separación es la base de todo.

Por qué se separan

  • Seguridad: la lógica y los datos sensibles viven en el servidor, lejos del navegador, que el usuario controla por completo.
  • Reutilización: un mismo backend sirve a la web, a una app móvil y a integraciones, todos consumiendo la misma API.
  • Equipos: front y back pueden avanzar en paralelo mientras respeten el contrato de la API.
La regla que ordena todo

Nunca confíes en el frontend para la seguridad. El navegador es territorio del usuario: puede editar el JS, la request, saltarse tu validación. El frontend valida para la experiencia; el backend valida para la seguridad. Este principio vuelve en cada capítulo.

Capítulo 2

Arquitecturas recomendadas

Hay varias formas de organizar la conexión front-back. No hay una mejor para todo; hay una mejor para tu caso. Estas son las que conviene conocer, de la más simple a la más armada.

1. SPA + API separada

El frontend es una aplicación que corre sola en el navegador (una SPA, del librito de APIs), y consume un backend que es solo API. Se despliegan por separado: el front en un hosting estático (librito de deploy), el back en su servidor.

CuándoVentajasCuidados
Apps con mucha interacción; varios clientes (web + móvil)Front y back independientes; una API para todosHay que resolver CORS y auth entre dominios (este libro)

2. Monolito con frontend servido por el backend

El backend sirve las páginas y también la API, todo junto. Más simple para empezar: no hay CORS (mismo origen), un solo despliegue.

CuándoVentajasCuidados
Proyectos chicos o medianos, un solo cliente webSimple, sin CORS, un despliegueMenos flexible si después sumás una app móvil

3. BFF (Backend For Frontend)

Un backend intermedio, hecho a medida del frontend, que se sienta entre la SPA y los servicios o APIs internas. Le simplifica la vida al front (le da justo lo que necesita) y guarda los secretos y tokens del lado del servidor.

CuándoVentajasCuidados
Apps con varios servicios detrás; cuando querés el token fuera del navegadorMás seguro (secretos en el server), API a medida del frontUna capa más para mantener
La recomendación

Empezá con lo más simple que resuelva tu caso (librito de arquitectura). Para aprender y para proyectos chicos, SPA + API o monolito alcanzan y sobran. El BFF aparece cuando la seguridad o la cantidad de servicios lo justifican, no antes.

Capítulo 3

El contrato entre front y back

Lo único que comparten el frontend y el backend es el contrato de la API: qué endpoints hay, qué reciben y qué devuelven. Si los dos respetan el contrato, todo lo demás puede cambiar sin romperse.

Un contrato es esto

el contrato del ejemplo de este libro
POST /login
  recibe:  { "email": "...", "password": "..." }
  devuelve: { "token": "eyJ..." }        (200) o error 401

GET /perfil
  requiere: header Authorization: Bearer <token>
  devuelve: { "email", "nombre", "rol" }  (200) o error 401

El frontend sabe exactamente qué mandar y qué esperar. El backend cumple eso. Ninguno necesita saber cómo está hecho el otro por dentro.

Buenas prácticas del contrato

  • Versioná la API (/v1/...) para poder evolucionar sin romper a los clientes.
  • Documentá con OpenAPI. FastAPI la genera sola en /docs; es documentación viva que front y back comparten.
  • Formatos y errores consistentes: siempre JSON, siempre los mismos códigos de estado para las mismas situaciones.
Acordá el contrato primero

En equipo, definir el contrato de la API antes de programar deja que front y back trabajen en paralelo. El front puede simular respuestas (mock) mientras el back se construye. El contrato es el punto de encuentro.

Capítulo 4

Paso 1: levantar el backend

Construimos un backend con dos endpoints: uno de login que entrega un token, y uno de perfil protegido. Acá va en FastAPI (Python); la variante en Express (Node) está en ejemplos/backend/server.js.

El endpoint de login

backend/main.py
from fastapi import FastAPI, HTTPException
from pydantic import BaseModel
import jwt, datetime, hashlib

SECRET = "clave_de_ejemplo"     # en producción: variable de entorno
app = FastAPI()

def hash_pw(p): return hashlib.sha256(p.encode()).hexdigest()  # demo; real: bcrypt
USUARIOS = {"carlos@ejemplo.com": {"pw": hash_pw("secreto123"),
                                    "nombre": "Carlos", "rol": "user"}}

class Login(BaseModel):
    email: str
    password: str

def crear_token(email, rol):
    payload = {"sub": email, "rol": rol,
               "exp": datetime.datetime.utcnow() + datetime.timedelta(hours=1)}
    return jwt.encode(payload, SECRET, algorithm="HS256")

@app.post("/login")
def login(datos: Login):
    u = USUARIOS.get(datos.email)
    if not u or u["pw"] != hash_pw(datos.password):
        raise HTTPException(401, "credenciales invalidas")   # mensaje genérico
    return {"token": crear_token(datos.email, u["rol"])}

Levantarlo y probarlo

Se corre con uvicorn --app-dir backend main:app --port 8010. Probamos el login con curl:

prueba real✓ salida real
### Login con credenciales correctas -> devuelve token JWT
token (recortado): eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJ...

### Login con contraseña incorrecta -> 401 genérico
HTTP/1.1 401 Unauthorized
{"detail":"credenciales invalidas"}

Con la contraseña correcta devuelve un token JWT; con una incorrecta, un 401 con mensaje genérico (no revela si el usuario existe, buena práctica del librito de seguridad). Todavía falta proteger el perfil: próximo paso.

Capítulo 5

Paso 2: consumir la API desde el frontend

Ahora el frontend le pega al backend. Usa fetch (librito de DOM y de consumir APIs): manda el login, recibe el token, y con él pide el perfil.

El login desde el front

frontend/app.js
const API = "http://localhost:8010";   // en producción: variable de entorno

form.addEventListener("submit", async (e) => {
  e.preventDefault();
  const email = document.querySelector("#email").value.trim();
  const password = document.querySelector("#password").value;

  // 1) login: pedir el token
  const r = await fetch(`${API}/login`, {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ email, password }),
  });
  if (!r.ok) { mostrar("Credenciales inválidas", "error"); return; }
  const { token } = await r.json();

  // 2) guardar el token y usarlo
  sessionStorage.setItem("token", token);
  await cargarPerfil(token);
});

Pedir un recurso protegido

frontend/app.js
async function cargarPerfil(token) {
  const r = await fetch(`${API}/perfil`, {
    headers: { "Authorization": `Bearer ${token}` },   // el token viaja acá
  });
  if (!r.ok) { mostrar("Sesión expirada", "error"); return; }
  const perfil = await r.json();
  datos.textContent = JSON.stringify(perfil, null, 2);
}

El patrón es el del librito de consumir APIs: fetch, chequear r.ok, parsear el JSON. Lo nuevo es el header Authorization: Bearer <token>, que le prueba al backend quién sos en cada pedido.

Si abrís esto ahora, falla

Si servís el front desde otro origen (por ejemplo localhost:5500) y le pegás a la API en localhost:8010, el navegador va a bloquear el pedido. No es un bug tuyo: es CORS, y es el próximo capítulo.

Capítulo 6

Paso 3: CORS, el primer muro

Cuando el frontend y el backend están en orígenes distintos (distinto dominio o puerto), el navegador bloquea el pedido por seguridad, salvo que el backend lo permita explícitamente. Eso es CORS, y frena a todo el que conecta front y back por primera vez.

Por qué el navegador bloquea

Por defecto, una página de un origen no puede leer respuestas de una API de otro origen vía JavaScript. Es una protección: evita que un sitio malicioso use tu sesión para consumir APIs ajenas (librito de seguridad). El backend tiene que declarar qué orígenes autoriza.

Configurarlo bien en el backend

backend/main.py (FastAPI)
from fastapi.middleware.cors import CORSMiddleware

app.add_middleware(
    CORSMiddleware,
    allow_origins=["http://localhost:5500"],   # SOLO el frontend legítimo
    allow_credentials=True,
    allow_methods=["*"],
    allow_headers=["*"],
)
backend/server.js (Express)
const cors = require("cors");
app.use(cors({ origin: "http://localhost:5500", credentials: true }));
Nunca abras CORS a todos

Ver allow_origins=["*"] en producción es una señal de alarma (librito de seguridad). Listá solo los orígenes de tus frontends reales. El * deja que cualquier sitio consuma tu API desde el navegador de tus usuarios.

CORS es del servidor, no del front

Un error común es intentar "arreglar CORS" desde el frontend. No se puede: es el backend el que autoriza. Si ves el error, la configuración va del lado del server.

Capítulo 7

Paso 4: variables de entorno y configuración

La URL de la API, la clave secreta, la cadena de conexión a la base: nada de eso va escrito en el código. Va en configuración, que cambia según el entorno (tu máquina, producción) sin tocar el código.

El problema de hardcodear

En los ejemplos pusimos const API = "http://localhost:8010" para que se entienda. Pero en tu máquina la API está en localhost, y en producción está en https://api.tuapp.com. Si está hardcodeado, tenés que cambiar el código para desplegar. Y peor: un secreto en el código se filtra (librito de seguridad).

Variables de entorno

backend (Python)
import os
SECRET = os.environ["JWT_SECRET"]              # viene del entorno
DB_URL = os.environ["DATABASE_URL"]

Los valores viven en un archivo .env local (que va en el .gitignore, librito de Git) y en el gestor de secretos del proveedor en producción.

Config del frontend

El frontend también necesita saber a qué URL pegarle según el entorno. Con un bundler (Vite, por ejemplo) usás variables de entorno del build; sin bundler, un pequeño archivo de config que cambiás por entorno.

.env (nunca al repositorio)
JWT_SECRET=una_clave_larga_y_aleatoria
DATABASE_URL=postgres://...
El frontend no guarda secretos

Ojo: cualquier cosa que mandes al navegador es pública, el usuario la ve en las DevTools. Las claves de API secretas y las credenciales viven en el backend, nunca en el JS del front. Si el front necesita algo secreto, lo pide al backend, que lo usa por él (ese es uno de los motivos del BFF, capítulo 2).

Capítulo 8

Autenticación: el login y el token

La autenticación es cómo el backend sabe quién manda cada pedido. Como HTTP no recuerda nada entre requests (librito de APIs), después del login el cliente prueba su identidad en cada llamada con un token.

El flujo completo

1. El usuario manda email + contraseña al POST /login
2. El backend verifica contra la base (contraseña hasheada)
3. Si es correcto, emite un token (JWT) firmado y con vencimiento
4. El cliente guarda el token y lo manda en cada pedido protegido
5. El backend verifica la firma del token en cada request

Dónde guardar el token: la decisión clave

OpciónVentajaRiesgo
Cookie HttpOnlyEl JavaScript no puede leerla: un XSS no roba el tokenHay que manejar CSRF (cookies con SameSite)
localStorage / sessionStorageSimple de usar desde el JSAccesible a JavaScript: un XSS lo roba (librito de seguridad)
La recomendación para apps web

Para una app web, el patrón más seguro es que el backend entregue el token en una cookie HttpOnly; Secure; SameSite, fuera del alcance del JavaScript (librito 01 y 07). El localStorage es más simple pero queda expuesto a XSS. En el ejemplo de este libro usamos sessionStorage por claridad didáctica; para producción, cookie HttpOnly.

Apps móviles nativas y clientes servidor-a-servidor sí usan el header Authorization: Bearer, porque no tienen un document.cookie que proteger.

Capítulo 9

Proteger endpoints y autorizar

Un endpoint protegido verifica el token en cada pedido, y además chequea que quien lo manda tenga permiso para eso puntual. Autenticar (quién sos) no es autorizar (qué podés hacer), como viste en el librito de seguridad.

Verificar el token

backend/main.py
from fastapi import Depends, HTTPException
from fastapi.security import HTTPBearer, HTTPAuthorizationCredentials
import jwt

seguridad = HTTPBearer()

def usuario_actual(cred: HTTPAuthorizationCredentials = Depends(seguridad)):
    try:
        return jwt.decode(cred.credentials, SECRET, algorithms=["HS256"])
    except jwt.ExpiredSignatureError:
        raise HTTPException(401, "token expirado")
    except jwt.InvalidTokenError:
        raise HTTPException(401, "token invalido")

@app.get("/perfil")
def perfil(user=Depends(usuario_actual)):     # protegido: exige token válido
    email = user["sub"]
    return {"email": email, "nombre": USUARIOS[email]["nombre"], "rol": user["rol"]}

Probarlo: con y sin token

prueba real✓ salida real
### GET /perfil SIN token -> protegido
HTTP/1.1 401 Unauthorized

### GET /perfil CON token -> 200 + datos del usuario
{"email":"carlos@ejemplo.com","nombre":"Carlos","rol":"user"}

Sin token, 401. Con el token del login, devuelve los datos. Funciona: el endpoint solo responde a quien probó su identidad.

Autorización por rol o por dueño

El token trae el rol. Para acciones sensibles, verificá también el permiso, no solo que esté logueado. Y para recursos de un usuario, verificá que el recurso sea suyo (el IDOR del librito de seguridad):

python
@app.delete("/pedidos/{id}")
def borrar(id: int, user=Depends(usuario_actual)):
    pedido = db.obtener(id)
    if pedido.usuario_id != user["sub"]:
        raise HTTPException(403)      # no es tuyo
    ...
Capítulo 10

Los must de una conexión segura

Más allá del token, hay un conjunto de defensas que toda conexión front-back necesita. Son las del librito de ciberseguridad, aplicadas al punto de contacto entre las dos mitades.

La lista no negociable

  • HTTPS siempre. Sin él, el token y los datos viajan en texto plano. En producción no es opcional.
  • Validar en el servidor. Toda entrada se valida en el backend, aunque el front ya haya validado. El front es para la experiencia; el back, para la seguridad.
  • Consultas parametrizadas. Nunca armar SQL pegando datos del usuario (inyección SQL, librito de seguridad).
  • Rate limiting. Limitar intentos de login y pedidos por cliente, para frenar fuerza bruta y abuso.
  • CORS restringido a tus orígenes (capítulo 6).
  • Cabeceras de seguridad en las respuestas del backend (CSP, HSTS, etc.).
  • Secretos fuera del código (capítulo 7).
  • Errores discretos: no devolver stack traces ni detalles internos al cliente.

CSRF, si usás cookies

Si guardás el token en cookie (lo recomendado para web), sumás protección CSRF: token anti-CSRF o cookies con SameSite=Lax/Strict (librito de seguridad). Si usás el header Authorization con el token en memoria, CSRF no aplica de la misma forma, pero quedás más expuesto a XSS. Es el trade-off del capítulo 8.

Todo esto ya lo viste

Este capítulo es el librito de ciberseguridad web aplicado a la conexión. Si querés el detalle de cada punto (cómo se explota y cómo se corrige), está ahí. Acá lo importante es que ninguna de estas defensas es opcional en producción.

Capítulo 11

Manejar errores y estados en el front

Una conexión real falla a veces: el servidor tarda, no responde, el token venció. Un buen frontend maneja esos casos en vez de quedarse colgado o mostrar datos rotos.

Los tres estados de todo pedido

  • Cargando: mostrar un indicador mientras la respuesta llega. El usuario sabe que algo pasa.
  • Éxito: mostrar los datos.
  • Error: mostrar un mensaje claro y, si aplica, una forma de reintentar.
javascript
async function cargar() {
  mostrarCargando(true);
  try {
    const r = await fetch(`${API}/perfil`, { headers: authHeader() });
    if (r.status === 401) { irALogin(); return; }        // token venció
    if (!r.ok) throw new Error(`HTTP ${r.status}`);
    render(await r.json());
  } catch (err) {
    mostrarError("No pudimos cargar tus datos. Reintentá.");
  } finally {
    mostrarCargando(false);
  }
}

El 401 y la sesión vencida

Un caso clave de la conexión: cuando el token vence, el backend responde 401. El frontend debería detectar ese 401 en sus pedidos y mandar al usuario al login, en vez de mostrar un error genérico. Es la coordinación fina entre las dos mitades.

El estado de carga importa

Una página que no muestra nada mientras carga se siente rota. Un simple "Cargando..." o un esqueleto de contenido cambia por completo la percepción de velocidad. Es de lo que más se nota y menos cuesta.

Cómo pedirle bien (prompting)

La calidad de lo que sale depende de lo que pedís. Un buen pedido para esta conexión sería específico y con las restricciones de seguridad explícitas:

ejemplo de prompt
Creá un endpoint POST /login en FastAPI que:
- reciba email y password
- verifique la contraseña con bcrypt (no texto plano ni sha256)
- devuelva un JWT firmado con expiración de 1 hora
- use la clave secreta desde una variable de entorno, no hardcodeada
- devuelva un 401 genérico si las credenciales son inválidas
Y un endpoint GET /perfil protegido que verifique el token.
Configurá CORS solo para http://localhost:5500.

Fijate que el prompt incluye las buenas prácticas que aprendiste (bcrypt, secreto en entorno, 401 genérico, CORS acotado). La IA no las aplica sola si no se las pedís; tu conocimiento es lo que guía a la herramienta.

La IA acelera, no reemplaza el criterio

Estas herramientas escriben código rápido, pero no saben qué es correcto para tu caso ni tienen tu contexto de seguridad. El valor de todos los libritos anteriores es que te dan el criterio para dirigir a la IA y para darte cuenta cuando se equivoca.

Capítulo 13

Revisar seguridad y calidad con IA

La IA no solo escribe código: también lo revisa. Pedirle que audite lo que generó (o lo que escribiste vos) es una de sus mejores aplicaciones, siempre con la última palabra en tus manos.

Prompts para auditar la conexión

ejemplos de prompt de revisión
Revisá este endpoint buscando problemas de seguridad: inyección,
autorización faltante, secretos hardcodeados, CORS abierto, y manejo
de errores que filtre información. Listá cada hallazgo con su riesgo
y cómo corregirlo.

¿Este código guarda el token de forma segura? ¿Qué pasa si hay un XSS?

¿La validación de este formulario está también en el backend, o solo
en el frontend?

Qué revisar siempre en el código generado

La IA tiende a generar código que "funciona" pero que a veces saltea seguridad. Revisá especialmente:

  • Secretos: ¿quedó alguna clave hardcodeada?
  • Contraseñas: ¿usa un hash lento (bcrypt/argon2) o algo inseguro?
  • SQL: ¿las consultas están parametrizadas?
  • CORS: ¿quedó en *?
  • Autorización: ¿verifica permisos, o solo que esté logueado?
  • Validación: ¿valida en el servidor, no solo en el front?
Nunca confíes ciego

La IA puede afirmar con seguridad algo incorrecto, o generar código con un bug sutil. Todo lo que genera pasa por tu revisión antes de ir a producción, sobre todo lo de seguridad. Es una herramienta poderosa con un humano al mando, no un reemplazo del humano. Y podés potenciarla con herramientas de análisis (SAST/SCA, librito de seguridad) que revisan automáticamente en cada cambio.

Checklist, arquitectura de referencia y glosario

Arquitectura de referencia (segura)

  [ Frontend (SPA) ]  ── HTTPS ──▶  [ Backend / API ]  ──▶  [ Base de datos ]
   - valida (UX)                     - valida (seguridad)      - accesos parametrizados
   - token en cookie                 - CORS acotado            - mínimo privilegio
     HttpOnly                        - auth + autorización
                                     - rate limiting
                                     - secretos en entorno
                                     - HTTPS forzado

Checklist de la conexión front-back

  • Contrato de API claro, versionado y documentado (OpenAPI).
  • CORS restringido a los orígenes de tus frontends.
  • HTTPS forzado en toda la comunicación.
  • Login con contraseñas hasheadas (bcrypt/argon2) y token con vencimiento.
  • Token en cookie HttpOnly para web (o Bearer para clientes no navegador).
  • Endpoints protegidos verifican token y autorización (no solo login).
  • Validación en el servidor, siempre; consultas parametrizadas.
  • Rate limiting en login y endpoints sensibles.
  • Secretos y URLs en variables de entorno, nunca en el código.
  • Frontend maneja los tres estados: cargando, éxito, error (y el 401).
  • Código generado por IA revisado, sobre todo en seguridad.
