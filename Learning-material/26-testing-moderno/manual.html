Testing del frontend moderno

El librito 04 te enseñó a testear lógica con pytest y jest. Este va al testing del frontend real: probar componentes de React y probar la app entera como la usa una persona (end-to-end). Es lo que te deja cambiar código sin miedo, porque si rompés algo, un test te avisa al instante.

Código real y probado

Los tests de este librito se corrieron de verdad sobre la tienda React del librito 15. Los bloques con ✓ salida real son las corridas reales: 5 tests de componente (Vitest + React Testing Library) y 5 de end-to-end (Playwright), todos en verde. El código está en ejemplos/.

Qué vas a poder hacer al terminar

Escribir tests unitarios de tu lógica, tests de componentes de React (que rendericen y respondan a clics), y tests end-to-end que manejan un navegador de verdad. Y entender qué testear con cada uno, sin perder tiempo probando lo que no hace falta.

Requisito

Conviene venir del librito 04 (testing base), el 14 (TypeScript) y el 15 (React), porque testeamos la tienda que armamos ahí. Si no los hiciste, igual se entiende la idea; el código te va a resultar más familiar si sí.

Capítulo 1

La pirámide de testing

No todos los tests son iguales. Hay tres niveles, y la clave es tener muchos de los baratos y pocos de los caros. Esa proporción se llama la pirámide de testing, y es la guía para no perder tiempo ni dejar agujeros.

la pirámide (muchos abajo, pocos arriba)
        /\
       /E2E\        pocos: lentos, prueban el flujo completo
      /------\
     /  Comp. \     algunos: prueban componentes de UI
    /----------\
   /  Unitarios \   muchos: rápidos, prueban lógica pura
  /--------------\
NivelQué pruebaVelocidadHerramienta
UnitarioUna función o hook aisladorapidísimoVitest / Jest
ComponenteUn componente React (renderiza, responde)rápidoReact Testing Library
End-to-end (E2E)La app entera en un navegador reallentoPlaywright / Cypress

Por qué esta forma

Los unitarios son baratos y rápidos: tené muchos, cubren la lógica. Los E2E son caros y lentos (levantan un navegador), pero son los únicos que prueban que todo junto funciona: tené unos pocos, para los flujos críticos. Los de componente están en el medio. Si invertís la pirámide (muchos E2E, pocos unitarios), tus tests van a ser lentos y frágiles.

Por qué testear, en una frase

Los tests no son para demostrar que el código anda hoy; son para avisarte cuando lo rompas mañana. Cambiás algo, corrés los tests, y en segundos sabés si rompiste algo en otro lado. Sin tests, cada cambio es una apuesta. Con tests, cambiás con confianza. Esa tranquilidad es lo que te compran.

Capítulo 2

Tests unitarios con Vitest

Empezamos por la base de la pirámide: probar lógica pura, aislada. Testeamos el hook useCarrito de la tienda (librito 15): que empiece vacío, que sume bien el total, que quite productos. Vitest es el corredor de tests moderno para proyectos con Vite.

Anatomía de un test

useCarrito.test.ts
import { renderHook, act } from "@testing-library/react";
import { describe, it, expect } from "vitest";
import { useCarrito } from "../useCarrito";

describe("useCarrito", () => {              // agrupa tests relacionados
  it("empieza vacío con total 0", () => {   // un caso concreto
    const { result } = renderHook(() => useCarrito());
    expect(result.current.items).toHaveLength(0);   // la afirmación
    expect(result.current.total).toBe(0);
  });
});

Cada test tiene tres partes (el patrón "AAA"): preparar (crear el hook), actuar (agregar algo), y afirmar (expect(...): lo que debería pasar). Si la afirmación falla, el test falla y te dice exactamente qué esperaba y qué obtuvo.

Probar que el total suma bien

useCarrito.test.ts
it("suma el total al agregar productos", () => {
  const { result } = renderHook(() => useCarrito());
  act(() => { result.current.agregar(pizza); });
  act(() => { result.current.agregar(pizza); });   // 2 pizzas
  act(() => { result.current.agregar(gaseosa); });
  expect(result.current.total).toBe(8500 * 2 + 1800);  // 18800
});

El act envuelve los cambios de estado de React (agregar al carrito). Después afirmamos que el total es exactamente lo esperado. Si mañana alguien rompe el cálculo del total, este test se pone rojo al instante.

Un buen test prueba comportamiento, no implementación

Fijate que testeamos qué hace el carrito (suma bien, quita bien), no cómo lo hace por dentro. Así, si mañana reescribís el interior del hook pero sigue sumando bien, el test sigue pasando. Testear el comportamiento y no los detalles internos hace que los tests no se rompan con cada refactor.

Capítulo 3

Tests de componente con React Testing Library

El nivel del medio: probar un componente de React de verdad. Lo renderizamos en memoria, verificamos que muestre lo correcto, y simulamos que el usuario hace clic. Testeamos la TarjetaProducto de la tienda.

Renderizar y verificar lo que se ve

TarjetaProducto.test.tsx
import { render, screen, fireEvent } from "@testing-library/react";
import { TarjetaProducto } from "../componentes/TarjetaProducto";

it("muestra el nombre y el precio", () => {
  render(<TarjetaProducto producto={pizza} onAgregar={() => {}} />);
  expect(screen.getByText("Pizza muzza")).toBeTruthy();
  expect(screen.getByText(/8.500/)).toBeTruthy();
});

render monta el componente en un DOM de mentira (jsdom). screen.getByText lo busca como lo haría un usuario: por el texto que ve. La filosofía de React Testing Library es justo esa: testear como usa la persona, no los detalles internos del componente.

Simular un clic

TarjetaProducto.test.tsx
it("llama a onAgregar al hacer clic en el botón", () => {
  const onAgregar = vi.fn();                      // una función "espía"
  render(<TarjetaProducto producto={pizza} onAgregar={onAgregar} />);
  fireEvent.click(screen.getByText("Agregar"));
  expect(onAgregar).toHaveBeenCalledWith(pizza);  // se llamó con el producto
});

vi.fn() crea una función espía: no hace nada, pero recuerda si la llamaron y con qué. Simulamos el clic con fireEvent.click, y verificamos que el componente llamó a onAgregar pasándole el producto. Así probás que un componente avisa correctamente hacia arriba (el patrón de props del librito 15).

getByText, getByRole: como un usuario

React Testing Library te empuja a buscar elementos como los encuentra una persona: por su texto, su rol (botón, encabezado), su etiqueta. Evita buscar por clases CSS o ids internos. ¿Por qué? Porque esos detalles cambian sin que cambie lo que el usuario ve, y no querés tests que se rompan por un refactor cosmético. Testeá lo que importa: lo que la persona experimenta.

Capítulo 4

Tests end-to-end con Playwright

La cima de la pirámide: probar la app entera como la usa una persona real, en un navegador de verdad. Playwright abre la tienda, hace clics, y verifica lo que aparece en pantalla. Es el test que te dice "el flujo completo funciona".

Qué hace un test E2E

A diferencia de los anteriores (que corren en memoria), un E2E levanta un navegador real, carga la app buildeada, y la maneja: navega, hace clic, escribe, y verifica el resultado visible. Es lento (segundos), pero es lo más parecido a un usuario de verdad usando tu app.

e2e.test.mjs (recorte)
await p.goto('http://localhost:4188/');
await p.waitForSelector('.tarjeta');

check("se muestran 6 productos", await p.locator('.tarjeta').count() === 6);
check("el carrito arranca vacío", (await p.locator('.carrito p').first()
      .textContent()).includes('Vacío'));

// agregar milanesa x2 y napolitana, como haría un usuario
const btns = p.locator('.tarjeta button');
await btns.nth(3).click(); await btns.nth(3).click(); await btns.nth(2).click();
check("el total es $28.800", (await p.getByTestId('total').textContent()).includes('28.800'));

await p.locator('.carrito .x').first().click();
check("tras quitar, total $9.800", (await p.getByTestId('total').textContent()).includes('9.800'));

El flujo completo, probado de verdad

salida real✓ salida real
== E2E: flujo de compra en la tienda ==
  PASS: se muestran 6 productos
  PASS: el carrito arranca vacío
  PASS: el carrito tiene 2 líneas
  PASS: el total es $28.800
  PASS: tras quitar, total $9.800
Resultado E2E: 5 pasados, 0 fallidos

Este test hizo lo mismo que haría una persona: entrar, ver los productos, agregar al carrito, mirar el total, quitar uno. Si cualquier pieza del flujo se rompe (el frontend, el estado, el cálculo), el E2E lo atrapa. Es la red de seguridad final antes de que un bug llegue al usuario.

Pocos, pero para lo crítico

Los E2E son lentos y más frágiles (dependen de tiempos, del navegador). Por eso: pocos, y para los flujos que no pueden fallar (registrarse, comprar, pagar). No testees cada detalle con E2E; para eso están los unitarios y de componente. Reservá los E2E para "el usuario puede completar una compra de principio a fin".

Capítulo 5

Qué testear (y qué no)

Testear todo es imposible y una pérdida de tiempo; testear nada es jugar con fuego. La habilidad está en testear lo que importa. Un par de guías para decidir bien.

Qué SÍ vale la pena testear

  • La lógica de negocio: cálculos de totales, descuentos, stock, reglas. Es lo que más duele si falla, y lo más fácil de testear (unitario).
  • Los flujos críticos: registro, login, compra, pago. Un E2E por cada uno.
  • Los casos límite: lista vacía, stock en cero, número negativo. Es donde viven los bugs.
  • Los bugs que arreglaste: cuando corregís un bug, escribí un test que lo reproduzca, así no vuelve nunca (se llama "test de regresión").

Qué NO hace falta testear

  • El framework: React ya está testeado; no testees que un useState funciona.
  • Detalles cosméticos: que un botón sea de tal color exacto. Cambian seguido y no aportan.
  • Código trivial: una función de una línea sin lógica no necesita test.

La cobertura, con cuidado

La "cobertura" mide qué porcentaje de tu código ejecutan los tests. Es útil para encontrar zonas sin probar, pero no es una meta en sí: 100% de cobertura con tests malos no sirve, y 70% con tests sobre lo que importa es excelente. Apuntá a cubrir la lógica crítica, no a un número.

El testing te hace ir más rápido

Suena contradictorio (escribir tests es más código), pero a mediano plazo te acelera: cambiás sin miedo, los bugs se atrapan temprano (cuando son baratos de arreglar, no en producción), y no tenés que probar todo a mano cada vez. Un proyecto con buenos tests se puede modificar con confianza; uno sin tests se vuelve, con el tiempo, imposible de tocar sin romper algo.

Fin del librito

Checklist y cierre

Ya sabés testear el frontend moderno en sus tres niveles, y elegir qué probar con cada uno. Con esto, cerrás el círculo de calidad de la colección: del testing de lógica (04) al de la interfaz completa.

Con IA

Escribir tests es de lo que mejor genera la IA: "escribí tests de Vitest para este hook", "hacé un test E2E de Playwright del flujo de compra". Le pasás el componente y te da los casos, incluidos los límite que quizás no pensaste. Revisá que prueben comportamiento (no implementación) y que los casos tengan sentido.

Checklist de testing

  • Muchos unitarios (lógica), algunos de componente, pocos E2E (la pirámide).
  • Testeá comportamiento, no implementación interna.
  • Buscá elementos como un usuario (por texto, rol), no por clases CSS.
  • E2E solo para los flujos críticos (compra, login, pago).
  • Cubrí los casos límite y escribí un test por cada bug que arregles.
  • Corré los tests seguido (idealmente automático en cada push: librito 06, CI/CD).

Lo que te llevás

Testear es lo que convierte un proyecto que "anda hoy" en uno que se puede mantener y crecer sin miedo. Con la pirámide en la cabeza (muchos unitarios, pocos E2E) y las herramientas de este librito, tus apps van a ser mucho más sólidas. Y en un equipo, los tests son lo que deja que muchas personas toquen el mismo código sin romperse entre sí. Es una de las marcas de un programador profesional.
