Algoritmos y estructuras de datos

Saber programar es una cosa; saber elegir cómo resolver un problema para que sea rápido y no se caiga con muchos datos es otra. Eso son los algoritmos y las estructuras de datos: los cimientos de la computación. Es lo que más se pregunta en entrevistas, y lo que separa un programa que anda de uno que anda bien.

Código real y medido

Todos los ejemplos se corrieron de verdad, midiendo el tiempo. Los bloques con ✓ salida real muestran diferencias de velocidad reales (a veces de miles de veces). Ahí se ve, no se cuenta. El código está en ejemplos/.

Qué vas a poder hacer al terminar

Entender la notación Big-O (por qué un programa escala o no), elegir la estructura de datos correcta para cada problema, conocer los algoritmos clásicos de búsqueda y ordenamiento, y entender la recursión. No para reinventarlos, sino para elegir bien y saber qué pasa por debajo.

Requisito

Este librito asume que ya sabés Python básico: listas, diccionarios, bucles y funciones (todo eso está en el INTRO). Si algo no te suena, dale una repasada primero.

Capítulo 1

Qué es un algoritmo (y por qué importa la eficiencia)

Un algoritmo es una secuencia de pasos para resolver un problema. Una receta es un algoritmo. Pero para el mismo problema suele haber varios algoritmos, y no todos son igual de buenos: algunos tardan un instante y otros, una eternidad, con los mismos datos.

El mismo problema, dos caminos

Buscar un nombre en una guía telefónica: podés leer página por página desde el principio (funciona, pero lento), o abrir por el medio y descartar la mitad según la letra (mucho más rápido). Las dos "funcionan"; una es muchísimo mejor. Elegir el buen algoritmo es de lo que se trata este librito.

Por qué importa cuando hay muchos datos

Con 10 elementos, cualquier algoritmo anda bien: la diferencia es imperceptible. El problema aparece con millones de datos, que es lo normal en apps reales. Ahí, un algoritmo malo hace que la app tarde segundos (o se cuelgue) donde uno bueno tarda milisegundos. Lo vas a ver medido en los próximos capítulos, y las diferencias son brutales.

No vas a reinventar la rueda

Aclaración importante: en el día a día NO escribís tus propios algoritmos de ordenamiento ni estructuras de datos; usás los que ya trae el lenguaje (que están hechos por expertos y optimizados). El valor de este librito es entenderlos: para elegir la estructura correcta, leer el código de otros, y no escribir sin querer algo que se arrastra con muchos datos. Entender, no reinventar.

Capítulo 2

Big-O: medir cómo escala un algoritmo

Big-O es la notación para describir cómo crece el tiempo (o la memoria) de un algoritmo a medida que crecen los datos. No mide segundos exactos (eso depende de la máquina); mide la forma en que crece. Es el vocabulario universal para hablar de eficiencia.

Las complejidades que vas a ver

NotaciónNombreCon 10x más datos...Ejemplo
O(1)constantetarda igualacceder a lista[5] o a dict[clave]
O(log n)logarítmicacasi igualbúsqueda binaria
O(n)lineal10x másrecorrer una lista
O(n log n)"n log n"~13x másun buen ordenamiento (sorted)
O(n²)cuadrática100x másdos bucles anidados sobre lo mismo

La idea, sin matemática

Big-O responde: "si le doy 10 veces más datos, ¿cuánto más tarda?". O(n) tarda 10 veces más (proporcional). O(n²) tarda 100 veces más (por eso es peligroso con muchos datos). O(log n) casi no cambia (por eso es tan bueno). O(1) tarda lo mismo sin importar el tamaño (el ideal).

Se ignoran las constantes

Big-O mira solo cómo crece, no los detalles finos. Un algoritmo que hace "2n + 5" pasos es O(n): se ignoran el 2 y el 5, porque con muchos datos lo que domina es la forma (lineal). Por eso O(n) siempre le gana a O(n²) cuando los datos crecen, aunque para pocos datos el detalle importe. Big-O es sobre el comportamiento a gran escala.

Capítulo 3

Búsqueda: lineal vs binaria

Buscar un elemento es la operación más común. Hay dos formas, y la diferencia entre ellas es el ejemplo perfecto de por qué Big-O importa. Lo medimos de verdad sobre un millón de elementos.

Búsqueda lineal: O(n)

La forma obvia: recorrer desde el principio hasta encontrarlo. Simple y funciona con cualquier lista, pero en el peor caso (el elemento está al final, o no está) recorre todo.

busqueda.py
def busqueda_lineal(lista, objetivo):
    for i, x in enumerate(lista):
        if x == objetivo:
            return i
    return -1

Búsqueda binaria: O(log n)

El truco de la guía telefónica: si la lista está ordenada, mirás el medio, y según sea mayor o menor, descartás la mitad. Repetís. Cada paso elimina la mitad de lo que queda.

busqueda.py
def busqueda_binaria(lista, objetivo):   # requiere lista ordenada
    lo, hi = 0, len(lista) - 1
    while lo <= hi:
        medio = (lo + hi) // 2
        if lista[medio] == objetivo:
            return medio
        elif lista[medio] < objetivo:
            lo = medio + 1        # descarta la mitad de abajo
        else:
            hi = medio - 1        # descarta la mitad de arriba
    return -1

La diferencia, medida

salida real✓ salida real
Buscar el último de 1.000.000 de elementos:
  lineal  (O(n)):     46.78 ms  (recorrió ~1.000.000)
  binaria (O(log n)): 0.0243 ms  (solo 20 pasos)
  la binaria fue ~1925x más rápida

Casi 2000 veces más rápida. La lineal miró un millón de elementos; la binaria, solo 20 (porque log₂ de un millón es ~20). Esa es la magia de O(log n): duplicar los datos suma un solo paso.

El precio: hay que estar ordenado

La búsqueda binaria solo funciona si la lista está ordenada. Ordenar cuesta (próximo capítulo), así que si vas a buscar una sola vez, la lineal alcanza. Pero si vas a buscar muchas veces, ordenar una vez y después usar binaria (o mejor, un diccionario, capítulo siguiente) vale enormemente la pena.

Capítulo 4

Ordenamiento

Ordenar es clásico y educativo. Vas a ver un algoritmo simple y lento (para entender), y por qué en la práctica siempre usás el del lenguaje, que es mucho mejor.

Bubble sort: O(n²), el didáctico

El más simple de entender: recorré la lista comparando de a pares y, si están en el orden equivocado, los intercambiás. Repetí hasta que no haya nada que intercambiar. Funciona, pero con dos bucles anidados es O(n²): lento.

ordenar.py
def bubble_sort(lista):
    a = lista[:]
    n = len(a)
    for i in range(n):
        for j in range(n - 1 - i):
            if a[j] > a[j+1]:
                a[j], a[j+1] = a[j+1], a[j]   # intercambiar
    return a

sorted(): O(n log n), el que usás de verdad

Python trae sorted() (y .sort()), que usa un algoritmo muy optimizado (Timsort), O(n log n). La diferencia, medida:

salida real✓ salida real
Ordenar 2000 números:
  bubble sort O(n^2), a mano:     125.3 ms
  sorted() de Python O(n log n):  0.296 ms
  sorted() fue ~423x más rápido

Con solo 2000 números, el de Python es 400 veces más rápido. Con más datos, la diferencia crece sin parar, porque O(n²) escala pésimo comparado con O(n log n).

Nunca escribas tu propio ordenamiento

La lección práctica del capítulo: entendé cómo funciona el ordenamiento (por eso vimos bubble sort), pero en código real usá siempre sorted() o .sort(). Están hechos por expertos, optimizados durante años, y son más rápidos y correctos que cualquier cosa que escribas a mano. Reinventarlo es más lento y más propenso a bugs. Entender, no reinventar.

Capítulo 5

Elegir la estructura de datos correcta

Acá está el conocimiento más práctico de todo el librito. La estructura de datos que elegís determina qué tan rápido es tu programa. Elegir bien es, muchas veces, la diferencia entre milisegundos y segundos. Y se ve medido.

list vs set/dict para "¿está esto acá?"

Pregunta común: "¿este valor está en mi colección?". En una lista, Python recorre todo (O(n)). En un set o un diccionario, va directo (O(1)), porque usan una técnica (hashing) que ubica el valor sin recorrer. La diferencia, medida:

salida real✓ salida real
'¿está x?' 1000 veces sobre 100.000 elementos:
  en lista (O(n)): 517.1 ms
  en set   (O(1)): 0.083 ms
  el set fue ~6268x más rápido

Seis mil veces. Si tu programa chequea pertenencia muchas veces sobre muchos datos y usás una lista, ahí está tu lentitud. Cambiar la lista por un set es, muchas veces, la optimización más grande y más simple que vas a hacer.

La guía rápida

Necesitás...UsáPor qué
Orden y duplicadoslistmantiene el orden, acceso por posición O(1)
Buscar por una clavedictacceso por clave O(1)
Valores únicos / "¿está?"setsin duplicados, pertenencia O(1)
Datos fijos que no cambiantupleinmutable, liviana
Cola (primero en entrar, primero en salir)dequesacar del principio es O(1)
La pregunta clave

Antes de elegir, preguntate: ¿cómo voy a usar estos datos? ¿Buscar por clave? dict. ¿Chequear pertenencia seguido? set. ¿Necesito orden? list. La estructura correcta hace que las operaciones que más repetís sean O(1) en vez de O(n). Es la decisión de diseño que más impacta en el rendimiento, y casi no cuesta nada tomarla bien.

Capítulo 6

Stacks y queues

Dos estructuras conceptuales que aparecen en todos lados, aunque no siempre con ese nombre. Se diferencian en el orden en que sacás las cosas: la pila saca la última que entró; la cola, la primera.

Stack (pila): LIFO — último en entrar, primero en salir

Como una pila de platos: apilás arriba, sacás de arriba. El último que pusiste es el primero que sacás. En Python, una lista con append (apilar) y pop (sacar el último).

salida real✓ salida real
stack: ['a', 'b', 'c']
  pop() saca el ULTIMO: c -> queda ['a', 'b']

Ejemplos reales de stacks: el botón "atrás" del navegador (te devuelve a la última página), el "deshacer" (Ctrl+Z) de cualquier programa, y cómo el propio Python maneja las llamadas a funciones (el "call stack" que ves en los errores).

Queue (cola): FIFO — primero en entrar, primero en salir

Como la fila del banco: el primero que llega es el primero que se atiende. En Python se usa deque (de collections) con append y popleft, porque sacar del principio de una lista normal es lento.

salida real✓ salida real
queue: ['a', 'b', 'c']
  popleft() saca el PRIMERO: a -> queda ['b', 'c']

Ejemplos reales de colas: los pedidos de la tienda (se atienden en orden de llegada), las tareas en espera de un servidor, la cola de impresión. Cada vez que algo se procesa "por orden de llegada", hay una queue.

Reconocer el patrón

No siempre vas a crear un "stack" o una "queue" explícitos, pero reconocer cuándo un problema es LIFO o FIFO te da la solución. "¿Deshacer la última acción?" → stack. "¿Procesar en orden de llegada?" → queue. Ese vocabulario te deja pensar y comunicar soluciones más rápido.

Capítulo 7

Recursión

La recursión es una función que se llama a sí misma. Suena rara y hasta imposible al principio, pero para ciertos problemas es la forma más natural y elegante de resolverlos. La clave: siempre tiene un "caso base" que corta la cadena.

Las dos partes de toda recursión

  • Caso base: la condición que corta, donde la función deja de llamarse. Sin esto, se llama para siempre (como un while sin salida).
  • Caso recursivo: la función se llama a sí misma con un problema más chico, acercándose al caso base.
recursion.py
def factorial(n):
    if n <= 1:                       # caso base: corta
        return 1
    return n * factorial(n - 1)      # caso recursivo: n más chico

print("factorial(5) =", factorial(5))   # 5*4*3*2*1
salida real✓ salida real
factorial(5) = 120   (5*4*3*2*1)
cuenta regresiva: 3... 2... 1... despegue!
suma anidada [1,[2,3,[4,5]],6] = 21

Dónde brilla: estructuras anidadas

La recursión es imbatible para recorrer cosas que se anidan sin profundidad fija: carpetas dentro de carpetas, comentarios con respuestas con respuestas, o una lista con listas adentro. Un bucle normal no sabe cuántos niveles hay; la recursión "entra" en cada nivel sola.

recursion.py · sumar una estructura anidada
def sumar_todo(cosa):
    total = 0
    for x in cosa:
        if isinstance(x, list):
            total += sumar_todo(x)   # si es lista, entrar recursivamente
        else:
            total += x
    return total
print(sumar_todo([1, [2, 3, [4, 5]], 6]))   # 21
Cuidado con la recursión

Dos advertencias. Una: siempre necesita un caso base que se alcance, o revienta con "maximum recursion depth exceeded" (el equivalente al bucle infinito). Dos: para problemas simples (como el factorial), un bucle normal suele ser más eficiente y claro; la recursión brilla en lo anidado. No la uses por elegancia si un for lo resuelve mejor.

Fin del librito

Checklist y cierre

Ya tenés el vocabulario y el criterio de la eficiencia: Big-O, los algoritmos clásicos, y la decisión que más impacta (la estructura de datos correcta). No para reinventar, sino para elegir bien y entender lo que usás.

Lo que te llevás

  • Big-O: O(1) < O(log n) < O(n) < O(n log n) < O(n²). Cuanto más a la derecha, peor escala.
  • Búsqueda: binaria (O(log n)) le gana a lineal (O(n)), si está ordenado.
  • Ordenar: usá siempre sorted(); entendé por qué es mejor que el tuyo.
  • Estructuras: dict/set dan O(1) para buscar; list para orden. La decisión que más rinde.
  • Stack/queue: LIFO (deshacer, atrás) vs FIFO (colas, orden de llegada).
  • Recursión: caso base + caso recursivo; brilla en estructuras anidadas.

No optimices antes de tiempo. Escribí código claro y correcto primero. Si va lento y hay muchos datos, ahí medís (como hicimos acá) para encontrar el cuello de botella, y casi siempre la solución es cambiar una estructura de datos (una lista por un set o un dict) o un algoritmo (lineal por binario). Medir, no adivinar: los números te dicen dónde está el problema real.
