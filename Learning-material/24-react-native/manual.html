Mobile · React Native

React Native: apps móviles con React

Ya sabés React para la web (librito 15). React Native te deja usar ese mismo conocimiento para hacer apps móviles reales, para iOS y Android, con una sola base de código. Si sabés componentes, props, estado y hooks, ya sabés el 80% de React Native. Este librito cubre el otro 20%: lo que cambia al pasar del navegador al celular.

Nota honesta sobre este librito

A diferencia del resto de la colección, el código de acá no está ejecutado: correr una app React Native necesita un emulador de celular o un dispositivo físico, que el entorno donde se armó esto no tiene. El código es correcto e idiomático (el estándar de React Native), pero no lleva el sello "salida real" porque sería deshonesto. Lo probás vos en tu compu siguiendo el capítulo de setup.

Qué vas a poder hacer al terminar

Entender cómo React Native convierte tu código en una app nativa, traducir lo que sabés de la web a móvil (componentes, estilos, listas), navegar entre pantallas, consumir una API, y saber cómo se publica una app en las tiendas.

Requisito

Este librito asume React y TypeScript (libritos 14 y 15). Reconstruimos el catálogo de la tienda en móvil, así que te va a resultar muy familiar: es la misma app, en otro lugar.

Capítulo 1

Qué es React Native

React Native es un framework para hacer apps móviles usando React. La idea genial: escribís una vez, con React, y corre como app nativa en iOS y en Android. No es una página web metida en una app; son componentes nativos de verdad, controlados desde React.

Una base, dos plataformas

Sin React Native, hacer una app para los dos sistemas significaba escribir dos apps: una en Swift (iOS) y otra en Kotlin (Android). React Native te deja escribir una sola, en JavaScript/TypeScript con React, que funciona en ambas. Ahorra la mitad del trabajo, y usás lo que ya sabés.

EnfoqueQué es
Nativo puroSwift para iOS + Kotlin para Android: dos apps, máximo rendimiento
React NativeUna base con React, componentes nativos de verdad. El equilibrio popular
Web en una appMeter una web dentro de una cáscara. Más limitado; no es lo que hace RN

No dibuja en un navegador

La diferencia clave con la web: React Native no usa HTML ni un navegador. Cuando escribís un componente, React Native lo traduce a los componentes nativos reales del sistema (un botón de iOS es un botón de iOS de verdad). Por eso las apps se ven y se sienten nativas, no como una página web disfrazada.

Expo: la forma fácil de empezar

La manera recomendada de arrancar con React Native hoy es Expo: un conjunto de herramientas que te saca de encima casi toda la configuración complicada. Con Expo podés escribir la app y verla al instante en tu propio celular (con una app llamada Expo Go), sin instalar los pesados entornos de iOS/Android. Es a React Native lo que Vite es a React web.

Capítulo 2

De la web a móvil: los componentes

La primera diferencia práctica: en la web usás etiquetas HTML (div, span, img). En React Native usás componentes que importás de la librería. La lógica de React es idéntica; cambian los "ladrillos".

La tabla de traducción

Web (HTML)React NativePara
<div><View>una caja/contenedor
<span> <p> <h1><Text>todo el texto
<img><Image>imágenes
<button><Pressable>algo tocable
<input><TextInput>campos de texto

Comparalo con la web

web (React, librito 15)
<div className="tarjeta">
  <h3>{producto.nombre}</h3>
  <p>${producto.precio}</p>
</div>
React Native
import { View, Text } from "react-native";

<View style={estilos.tarjeta}>
  <Text style={estilos.nombre}>{producto.nombre}</Text>
  <Text>${producto.precio}</Text>
</View>
Todo el texto va en un Text

La regla que más se olvida al empezar: en React Native, cualquier texto DEBE ir dentro de un <Text>. No podés poner texto suelto dentro de un <View> como sí lo harías en un <div>. Si ves el error "Text strings must be rendered within a <Text> component", es esto. Cada palabra que se muestra, en un Text.

Capítulo 3

Estilos: como CSS, pero en objetos

En React Native no hay archivos CSS. Los estilos se escriben como objetos de JavaScript, con propiedades muy parecidas a CSS pero en camelCase. Y la buena noticia: Flexbox, que ya conocés del track de frontend, es la forma principal de acomodar cosas, igual que en la web.

StyleSheet

estilos con StyleSheet
import { StyleSheet } from "react-native";

const estilos = StyleSheet.create({
  tarjeta: {
    backgroundColor: "#ffffff",
    borderRadius: 12,
    padding: 16,
    marginBottom: 12,
  },
  nombre: {
    fontSize: 16,
    fontWeight: "700",
    color: "#1c2430",
  },
});

Las propiedades son las de CSS pero en camelCase: backgroundColor en vez de background-color, fontSize en vez de font-size. Los valores numéricos no llevan px (son puntos independientes de densidad). Se aplican con style={estilos.tarjeta}.

Flexbox, tu viejo conocido

acomodar con Flexbox
const estilos = StyleSheet.create({
  fila: {
    flexDirection: "row",          // en la web el default es row; acá es column
    justifyContent: "space-between",
    alignItems: "center",
  },
});
Dos diferencias de Flexbox con la web

Flexbox funciona casi igual que en el track de frontend, con dos detalles: en React Native, la dirección por defecto es column (en la web es row), porque las pantallas de celular son verticales. Y no hay grid: todo se resuelve con Flexbox. Fuera de eso, justifyContent, alignItems y flex son los mismos que ya sabés.

Capítulo 4

Estado y eventos: idénticos a la web

Acá está la mejor noticia: el estado con useState, los hooks, los custom hooks, el flujo de props, todo funciona exactamente igual que en React web (librito 15). No hay nada nuevo que aprender. Solo cambia cómo se detecta un "toque" en vez de un "clic".

La tarjeta de producto, en React Native

componentes/TarjetaProducto.tsx
import { View, Text, Pressable, StyleSheet } from "react-native";
import type { Producto } from "../tipos";

interface Props {
  producto: Producto;
  onAgregar: (p: Producto) => void;
}

export function TarjetaProducto({ producto, onAgregar }: Props) {
  return (
    <View style={estilos.tarjeta}>
      <Text style={estilos.cat}>{producto.categoria}</Text>
      <Text style={estilos.nombre}>{producto.nombre}</Text>
      <Text style={estilos.precio}>${producto.precio}</Text>
      <Pressable style={estilos.boton} onPress={() => onAgregar(producto)}>
        <Text style={estilos.botonTexto}>Agregar</Text>
      </Pressable>
    </View>
  );
}

Es casi idéntico a la versión web del librito 15. Las únicas diferencias: View/Text en vez de div/h3, Pressable en vez de button, y onPress en vez de onClick. La interface de Props, el patrón de "datos bajan, eventos suben", todo igual.

onPress en vez de onClick

En un celular no hay clic: hay toque. El evento se llama onPress, y va en un componente tocable como Pressable. La lógica que ejecuta es la misma que tendría un onClick en la web. Ese es, literalmente, el único cambio conceptual en el manejo de eventos.

Tu conocimiento de React se transfiere entero

Custom hooks (el useCarrito del librito 15 funciona tal cual), useState, useEffect, props, el flujo de datos: todo es igual. Por eso React Native es tan atractivo si ya sabés React: no aprendés un framework nuevo, aprendés un conjunto de componentes nuevos. El cerebro de la app es el mismo.

Capítulo 5

Listas: FlatList

En la web renderizabas una lista con .map(). En móvil también podés, pero para listas largas (un catálogo, un feed) React Native tiene FlatList: una lista optimizada que solo dibuja lo que está en pantalla, clave para que la app vaya fluida con muchos elementos.

El catálogo de la tienda con FlatList

App.tsx
import { FlatList, View, Text, StyleSheet } from "react-native";
import { CATALOGO } from "./datos";
import { useCarrito } from "./useCarrito";       // el mismo hook del librito 15
import { TarjetaProducto } from "./componentes/TarjetaProducto";

export default function App() {
  const { agregar, total } = useCarrito();
  return (
    <View style={estilos.app}>
      <Text style={estilos.titulo}>Sabores del Barrio</Text>
      <FlatList
        data={CATALOGO}
        keyExtractor={(p) => String(p.id)}
        renderItem={({ item }) => (
          <TarjetaProducto producto={item} onAgregar={agregar} />
        )}
      />
      <Text style={estilos.total}>Total: ${total}</Text>
    </View>
  );
}

Las tres props clave de FlatList

  • data: el array a mostrar (el catálogo).
  • keyExtractor: de dónde sacar la key única de cada item (como la key del .map en web, librito 15).
  • renderItem: cómo dibujar cada elemento (acá, una TarjetaProducto).
Por qué FlatList y no map

Con .map(), React Native dibujaría los 1000 elementos de un catálogo de una, aunque solo 8 entren en la pantalla: lento y gasta memoria. FlatList solo dibuja lo visible y va cargando a medida que scrolleás. Para listas cortas .map alcanza, pero para cualquier lista que pueda crecer, FlatList es lo correcto en móvil.

Capítulo 6

Navegación entre pantallas

Una app tiene varias pantallas: el catálogo, el detalle de un producto, el carrito, el perfil. En la web eso lo maneja un router con URLs. En móvil no hay URLs a la vista; la librería estándar es React Navigation, que maneja el ir y venir entre pantallas con las transiciones nativas (deslizar, el botón atrás).

Stack de navegación

El patrón más común es el "stack" (pila, como el del librito 25): cada pantalla nueva se apila encima, y el botón atrás la saca. React Navigation lo arma así:

navegación básica
import { NavigationContainer } from "@react-navigation/native";
import { createNativeStackNavigator } from "@react-navigation/native-stack";

const Stack = createNativeStackNavigator();

export default function App() {
  return (
    <NavigationContainer>
      <Stack.Navigator>
        <Stack.Screen name="Catalogo" component={PantallaCatalogo} />
        <Stack.Screen name="Detalle" component={PantallaDetalle} />
      </Stack.Navigator>
    </NavigationContainer>
  );
}

Ir de una pantalla a otra

navegar y pasar datos
// desde el catálogo, al tocar un producto, ir al detalle pasándole el id
<Pressable onPress={() => navigation.navigate("Detalle", { id: producto.id })}>
  <Text>{producto.nombre}</Text>
</Pressable>

Cada pantalla recibe un objeto navigation. navigation.navigate("Detalle", {...}) te lleva a esa pantalla, opcionalmente pasándole datos (acá, el id del producto). El botón atrás y las transiciones los maneja React Navigation solo, con el look nativo de cada sistema.

Tipos de navegación

Además del stack, vas a ver el "tab navigator" (las pestañas de abajo, como en Instagram) y el "drawer" (el menú lateral que se desliza). React Navigation los trae todos y se combinan. La idea es la misma: declarás las pantallas y cómo se relacionan, y la librería maneja el resto.

Capítulo 7

Conectar a una API y usar lo nativo

Una app móvil, como una web, casi siempre habla con un backend. La buena noticia: consumir una API es idéntico a la web. Y además, una app puede hacer cosas que la web no: cámara, GPS, notificaciones, guardar datos en el teléfono.

Consumir una API: igual que en la web

fetch, exactamente como en React web
import { useEffect, useState } from "react";
import type { Producto } from "./tipos";

const [productos, setProductos] = useState<Producto[]>([]);

useEffect(() => {
  fetch("https://tutienda.com/api/productos")
    .then((r) => r.json())
    .then((data: Producto[]) => setProductos(data));
}, []);

fetch, useEffect, useState, TanStack Query: todo funciona igual que en la web (librito 15). Tu app móvil se conecta al mismo backend (librito 09, 10) que tu web. Un backend, y dos frentes (web y móvil) que lo consumen igual.

Lo que solo puede el móvil

CapacidadCon qué
Guardar datos en el teléfonoAsyncStorage (como localStorage)
Cámara y fotosexpo-camera, expo-image-picker
Ubicación (GPS)expo-location

Permisos: el usuario decide

Todo lo sensible (cámara, ubicación, notificaciones) requiere pedirle permiso al usuario, y él puede negarlo. Tu app siempre tiene que manejar el caso "el usuario no dio permiso" con elegancia, sin romperse. Es la misma mentalidad de "no confíes en que todo sale bien" del INTRO y del librito de errores, aplicada a lo nativo.

Publicar la app, y cierre

Armaste la app; el último paso es que la gente la baje. Publicar en las tiendas tiene su proceso (y su costo), pero Expo lo simplifica mucho. Un panorama, y el cierre.

De tu compu a las tiendas

  1. Desarrollo: con Expo, ves la app en tu propio celular al instante (app Expo Go), sin compilar nada pesado.
  2. Build: cuando está lista, Expo compila los instaladores nativos (uno para iOS, uno para Android) en la nube, sin que necesites una Mac.
  3. Publicación: subís esos instaladores a la App Store (iOS) y Google Play (Android). Cada una tiene una cuenta de desarrollador con costo (Apple cobra anual; Google, un pago único) y un proceso de revisión.

Actualizaciones sin pasar por la tienda

Una ventaja de React Native con Expo: muchas actualizaciones (las que solo tocan tu código JavaScript, no lo nativo) se pueden mandar directo a los usuarios sin volver a pasar por la revisión de las tiendas (con "EAS Update"). Es como el redeploy de la web (librito 20), pero para tu app.

Checklist mental de React Native

  • Componentes: View, Text, Image, Pressable, TextInput (no HTML).
  • Todo texto dentro de un <Text>.
  • Estilos con StyleSheet y Flexbox (default column, sin grid).
  • onPress en vez de onClick.
  • Listas largas con FlatList.
  • Navegación con React Navigation.
  • APIs con fetch (igual que web); lo nativo con las librerías de Expo.
  • Empezá con Expo; publicás con EAS.
