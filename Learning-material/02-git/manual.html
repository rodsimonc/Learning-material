Manual de estudio

Git, de cero a trabajar en equipo

Git es la herramienta que usa casi todo el que programa para guardar la historia de su código, probar cosas sin miedo y trabajar con otros sin pisarse. Este libro arranca sin dar nada por sabido y termina con vos manejando ramas, conflictos y flujos de equipo. Los bloques con ✓ salida real son lo que devolvió la terminal de verdad.

Cómo está armado

  • Parte 1, fundamentos. Qué resuelve Git, el modelo de los tres estados, y tu primer repo funcionando.
  • Parte 2, ramas y colaboración. Ramas, merge, el temido conflicto (resuelto paso a paso) y cómo deshacer cualquier cosa.
  • Parte 3, GitHub. Remotos, push y pull, y el flujo con Pull Requests que usan los equipos.
  • Parte 4, rescate. Los comandos que te salvan cuando algo se rompe, y una cheatsheet.
Cómo moverte

Índice a la izquierda, o flechas ← → del teclado. El libro recuerda dónde quedaste. Arriba, la barra de progreso y el tema claro/oscuro.

Capítulo 1

¿Qué es Git y qué problema resuelve?

Git es un sistema de control de versiones: guarda fotos del estado de tu proyecto a lo largo del tiempo, y te deja volver a cualquiera de ellas, comparar, y combinar el trabajo de varias personas.

El dolor sin Git

Todos empezamos igual: proyecto_final.py, después proyecto_final_v2.py, después proyecto_final_ESTE_SI.py. Cuando algo se rompe, no sabés qué cambió ni cuándo funcionaba. Y si sos dos personas editando el mismo archivo, uno pisa al otro.

Git resuelve las tres cosas de un saque: historia completa, capacidad de volver atrás, y una forma ordenada de fusionar trabajo de varios.

Snapshots, no diferencias

La idea mental clave: cada vez que guardás (un "commit"), Git saca una foto de todo tu proyecto en ese momento. Podés viajar a cualquier foto cuando quieras. Cada foto tiene un identificador único (un hash como f1cee4b), un autor, una fecha y un mensaje que explica qué cambiaste.

Git no es GitHub

Se confunden todo el tiempo. Git es el programa que corre en tu máquina y maneja la historia. GitHub es un servicio en internet donde subís tus repos para respaldarlos y compartirlos. Podés usar Git sin GitHub perfectamente. GitHub sin Git no existe. La Parte 3 se mete con GitHub; hasta entonces, todo pasa en tu compu.

La idea en una línea

Git es una máquina del tiempo para tu código: guardás fotos con nombre, y podés volver, comparar y combinar.

Capítulo 2

El modelo mental: tres estados

Entender esto de entrada te ahorra el 90% de la confusión con Git. Un archivo en Git pasa por tres lugares antes de quedar guardado en la historia.

Los tres lugares

  • Working directory. Tu carpeta de trabajo, los archivos como los estás editando ahora mismo.
  • Staging area (el "index"). Una sala de espera. Ponés acá los cambios que querés incluir en la próxima foto. Este paso intermedio es lo que te deja armar commits prolijos: elegís qué entra y qué no.
  • Repository. La historia confirmada. Cuando hacés commit, lo que estaba en staging pasa a ser una foto permanente.

El flujo, siempre el mismo

  working directory        staging area           repository
   (editás)      --add-->   (preparás)  --commit->  (historia)

   app.py  ✎                app.py  ✓               foto #3 ✓✓✓

Editás archivos, elegís cuáles preparar con git add, y confirmás la foto con git commit. Ese ciclo lo vas a repetir miles de veces.

Por qué existe el staging

Te deja separar cambios en commits con sentido. Si tocaste dos cosas distintas, podés commitear una ahora (con su mensaje) y la otra después, en vez de mezclar todo en una foto confusa.

Capítulo 3

Tu primer repositorio

Vamos a crear un repo real desde cero y hacer los primeros commits. Todo lo que sigue se ejecutó de verdad.

Configuración, una sola vez

Antes del primer commit, decile a Git quién sos. Esto queda guardado para todos tus repos:

shell
git config --global user.name "Carlos"
git config --global user.email "carlos@ejemplo.com"

Crear el repo

git init✓ salida real
$ git init
Initialized empty Git repository in /home/.../proyecto/.git/

Eso crea una carpeta oculta .git donde Git guarda toda la historia. El resto de tu carpeta sigue igual.

Ver el estado

git status es el comando que más vas a usar. Te dice qué cambió y en qué estado está cada archivo:

git status✓ salida real
$ git status
On branch main
No commits yet
Untracked files:
	app.py
nothing added to commit but untracked files present

app.py aparece como "untracked": Git lo ve pero todavía no lo sigue.

Preparar y confirmar

add + commit✓ salida real
$ git add app.py
$ git commit -m "primer commit"
[main (root-commit) f1cee4b] primer commit
 1 file changed, 1 insertion(+)

Ya tenés tu primera foto. El -m es el mensaje: siempre explicá qué hiciste. Ese f1cee4b es el identificador único del commit.

La historia

git log --oneline✓ salida real
$ git log --oneline
183929e agregar gitignore
f4560de mejorar saludo y agregar README
f1cee4b primer commit
El ciclo que repetís siempre

git status para ver dónde estás, git add para preparar, git commit -m para guardar. Tres comandos, el 80% del uso diario.

Capítulo 4

Ver qué cambió, y qué ignorar

Antes de commitear conviene mirar exactamente qué tocaste. Y hay archivos que nunca querés guardar. Git te da herramientas para las dos cosas.

status y diff

La versión corta de status (-s) es más rápida de leer: M es modificado, ?? es sin seguir. Y git diff te muestra línea por línea qué cambió:

status -s + diff✓ salida real
$ git status -s
 M app.py
?? README.md

$ git diff app.py
@@ -1 +1 @@
-print('hola')
+print('hola mundo')

Las líneas con - se van, las + entran. Leer el diff antes de commitear es un hábito que atrapa muchos errores.

.gitignore: lo que no se guarda

Hay cosas que jamás van al repo: contraseñas, archivos de configuración local, dependencias (node_modules), archivos generados. Las listás en un archivo .gitignore y Git las ignora.

.gitignore
node_modules/
.env              # secretos y claves, NUNCA al repo
__pycache__/
*.log
dist/
resultado✓ salida real
$ git status -s
(vacío = todo limpio, notas.txt ignorado)
Ojo, esto lastima

Si ya commiteaste un secreto, borrarlo en un commit nuevo no alcanza: sigue en la historia. Hay que reescribir la historia y, sobre todo, rotar ese secreto (cambiarlo). Poné el .gitignore antes del primer commit, no después.

Capítulo 5

Ramas: probar sin romper

Una rama es una línea de trabajo paralela. Te deja desarrollar algo nuevo sin tocar la versión que funciona, y volver a fusionarlo cuando esté listo. Es lo que hace a Git tan potente para equipos.

Por qué

Tu rama principal (main) debería tener siempre código que funciona. Cuando arrancás una feature, creás una rama, trabajás ahí tranquilo, y solo cuando está lista la traés a main. Si la feature se cae, main nunca se enteró.

Crear y moverse

git switch -c feature/login✓ salida real
$ git switch -c feature/login
Switched to a new branch 'feature/login'

switch -c crea la rama y te para en ella (el -c es "create"). Desde acá, cada commit va a esta rama, no a main. Para volver: git switch main.

switch y restore, los nuevos

Vas a ver mucho git checkout por internet: era el comando viejo que hacía de todo. Git lo dividió en dos más claros: git switch para cambiar de rama, git restore para descartar cambios. Los dos funcionan; usá los nuevos.

Nombrar ramas

Una convención común: feature/login, fix/error-pago, docs/readme. El prefijo dice de qué tipo es, y el resto qué toca. Prolijo y fácil de escanear.

Capítulo 6

Fusionar ramas con merge

Cuando tu rama está lista, la traés de vuelta a main con git merge. Hay dos formas en que Git lo hace, y conviene reconocerlas.

Fast-forward: el caso simple

Si main no cambió desde que te fuiste, Git simplemente adelanta el puntero. No hay nada que combinar, solo mover main hasta donde llegó tu rama.

merge fast-forward✓ salida real
$ git switch main
$ git merge feature/login
Updating 183929e..458d38c
Fast-forward
 app.py | 1 +
 1 file changed, 1 insertion(+)

Merge commit: cuando las dos ramas avanzaron

Si main también recibió commits mientras trabajabas, Git combina las dos líneas y crea un commit especial de merge, con dos padres. Lo vas a ver en el gráfico de historia como una bifurcación que se vuelve a unir:

git log --oneline --graph --all✓ salida real
*   51d8f8c resolver conflicto de color: rojo
|\
| * a425c80 color azul
* | fdb0aab color rojo
|/
* 458d38c agregar login
* 183929e agregar gitignore
* f1cee4b primer commit

Ese diamante en el grafo es el merge: dos ramas que se separaron y se reunieron. Cuando las dos tocaron lo mismo, aparece un conflicto. Ese es el próximo capítulo.

Capítulo 7

Conflictos, sin miedo

Un conflicto pasa cuando dos ramas cambian la misma línea del mismo archivo, y Git no sabe cuál elegir. Suena aterrorífico la primera vez. Es de las cosas más simples de Git una vez que lo ves una vez.

Cómo se ve

Dos ramas cambiaron config.py: una puso el color en rojo, la otra en azul. Al mergear:

git merge feature/color✓ salida real
$ git merge feature/color
Auto-merging config.py
CONFLICT (add/add): Merge conflict in config.py
Automatic merge failed; fix conflicts and then commit the result.

Git no rompió nada. Paró y te pasó la decisión. Abrís el archivo y encontrás los marcadores:

config.py con el conflicto✓ salida real
<<<<<<< HEAD
color = "rojo"
=======
color = "azul"
>>>>>>> feature/color

Cómo se resuelve

Arriba (HEAD) está lo que tenía tu rama actual. Abajo, lo que trae la otra. Tu tarea: editar el archivo para que quede como debe, borrando los marcadores. Elegís uno, el otro, o una mezcla. Dejás config.py así:

config.py resuelto
color = "rojo"

Después le decís a Git que lo resolviste y confirmás el merge:

resolver✓ salida real
$ git add config.py
$ git commit -m "resolver conflicto de color: rojo"
commit de merge creado
La clave

Un conflicto es Git preguntándote, no Git fallando. Editás, borrás los marcadores <<< === >>>, hacés add y commit. Nada más.

Capítulo 8

Deshacer casi cualquier cosa

La gran ventaja de Git: rara vez perdés trabajo de verdad. Estos son los comandos para volver atrás, según qué querés deshacer.

Descartar cambios sin commitear: restore

git restore✓ salida real
$ git restore app.py
app.py vuelto al último commit

Tira a la basura lo que editaste desde el último commit. Cuidado, esto sí se pierde (no estaba guardado todavía).

Guardar para después: stash

Estás a mitad de algo y necesitás cambiar de rama ya. stash guarda tus cambios a un costado y te deja la carpeta limpia. Después los recuperás con pop:

stash✓ salida real
$ git stash
Saved working directory and index state WIP on main
$ git stash pop
Changes not staged for commit:
	modified:   app.py
Dropped refs/stash@{0}

reset y revert: deshacer commits

ComandoQué haceCuándo
git reset --softDeshace el commit pero deja los cambios preparadosRehacer el último commit
git reset --hardDeshace el commit y borra los cambiosTirar todo lo último (peligroso)
git revertCrea un commit nuevo que deshace otroDeshacer algo ya compartido
Regla de oro

reset --hard reescribe la historia: úsalo solo en commits que todavía no compartiste. Si ya pusheaste, usá revert, que deshace agregando un commit y no rompe a los demás.

Capítulo 9

Remotos: subir a GitHub

Hasta acá todo vivió en tu máquina. Un "remoto" es una copia del repo en internet (GitHub) que usás para respaldar y compartir. Estos son los comandos del día a día.

Los cuatro que necesitás

ComandoQué hace
git clone <url>Baja un repo de GitHub a tu máquina, con toda su historia.
git pushSube tus commits locales al remoto.
git pullBaja los commits nuevos del remoto y los fusiona con lo tuyo.
git fetchBaja los cambios del remoto pero sin fusionar todavía. Para mirar antes de integrar.

Conectar un repo local a GitHub

Creás el repo vacío en GitHub, y desde tu carpeta:

shell
git remote add origin https://github.com/usuario/proyecto.git
git push -u origin main       # la primera vez, -u recuerda el destino

origin es el nombre por convención del remoto principal. Después de la primera vez, alcanza con git push y git pull.

El ritmo diario trabajando con otros

  1. git pull al empezar, para arrancar con lo último.
  2. Trabajás, hacés commits en tu rama.
  3. git push para subir tu rama.
  4. Abrís un Pull Request (próximo capítulo).
Autenticación

GitHub ya no acepta contraseña para push. Usás un token de acceso personal (PAT) o una clave SSH. Se configura una vez y listo. Nunca pongas el token en el código; va en la configuración de Git o del sistema.

Capítulo 10

El flujo con Pull Requests

Un Pull Request (PR) es cómo se integra trabajo en equipo: proponés que tu rama se fusione a main, otros la revisan, y recién ahí se mergea. Es el corazón del trabajo colaborativo en GitHub.

El flujo completo, paso a paso

  1. Rama. Creás feature/algo desde main y trabajás ahí.
  2. Push. Subís tu rama a GitHub con git push -u origin feature/algo.
  3. Abrís el PR. En GitHub, pedís fusionar tu rama a main. Escribís qué hiciste y por qué.
  4. Revisión. Un compañero lee tu código, comenta, pide cambios. Vos seguís pusheando a la misma rama y el PR se actualiza solo.
  5. Merge. Cuando está aprobado, se mergea a main. Muchos equipos corren tests automáticos antes de permitirlo (eso es CI, otro librito).
  6. Limpieza. Se borra la rama, ya cumplió.

Por qué se trabaja así

El PR le da a todo cambio un momento de revisión antes de entrar a main. Se atrapan bugs, se comparte conocimiento, y queda registro de por qué se hizo cada cosa. Nadie mergea directo a main en un equipo serio.

Un buen PR

Chico y enfocado. Un PR que toca 40 archivos no lo revisa nadie bien. Título claro, descripción de qué y por qué, y si aplica, cómo probarlo. Facilitarle la vida al que revisa acelera todo.

Capítulo 11

Commits y ramas que se entienden

Git no te obliga a ser prolijo, pero tu yo del futuro y tus compañeros te lo van a agradecer. Estas son las costumbres que separan un repo legible de un pantano.

Commits atómicos

Un commit, una idea. Si arreglaste un bug y de paso renombraste diez variables, son dos commits. Así, si el bug fix rompe algo, lo podés revertir sin llevarte puesto el renombrado.

Buenos mensajes

La convención más usada hoy es Conventional Commits: un prefijo que dice el tipo, y una descripción corta en presente.

ejemplos
feat: agregar login con Google
fix: corregir cálculo de impuestos en pedidos
docs: actualizar README con pasos de instalación
refactor: extraer validación de email a su función
test: agregar tests del carrito

La primera línea, corta (menos de 50 caracteres). Si hace falta más, dejás una línea en blanco y explayás abajo el porqué, que es lo que no se ve en el código.

Reglas simples que evitan dolor

  • Commiteá seguido. Commits chicos son fáciles de entender y de revertir.
  • main siempre funcionando. El trabajo en progreso va en ramas.
  • Pulleá antes de empezar, así arrancás con lo último y evitás conflictos.
  • Nunca commitees secretos ni node_modules. Para eso está el .gitignore.
Cierre

Comandos de rescate y cheatsheet

Los comandos que te salvan cuando algo salió mal, y una hoja de referencia para tener a mano.

Cuando entrás en pánico

SituaciónComando
"Perdí un commit"git reflog lista todo lo que hiciste, hasta lo "borrado". Casi nada se pierde de verdad.
"Me equivoqué de rama al commitear"git cherry-pick <hash> copia ese commit a la rama correcta.
"¿Quién cambió esta línea?"git blame archivo muestra autor y commit de cada línea.
"¿Cuándo entró este bug?"git bisect hace una búsqueda binaria en la historia para encontrarlo.

Cheatsheet del día a día

lo esencial
git status                 # ¿en qué estoy?
git add archivo            # preparar un archivo
git add -A                 # preparar todo
git commit -m "mensaje"    # confirmar
git log --oneline          # ver la historia
git switch -c rama         # crear y cambiar de rama
git switch main            # volver a main
git merge rama             # fusionar
git pull                   # traer del remoto
git push                   # subir al remoto
git restore archivo        # descartar cambios
git stash / git stash pop  # guardar / recuperar a medias

Lo que te llevás

Sabés guardar historia, trabajar en ramas, resolver conflictos, deshacer casi todo, y colaborar con PRs. El resto es práctica. Usá Git en todo lo que hagas, aunque trabajes solo. Se vuelve automático rápido.
