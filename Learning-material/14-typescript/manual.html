Lenguajes · TypeScript

TypeScript, de 0

JavaScript te deja escribir "5" * verdadero y recién te enterás del problema cuando explota en producción. TypeScript es JavaScript con tipos: le agrega una red de seguridad que atrapa esos errores mientras escribís, no cuando ya es tarde. En este librito vas de no saber qué es un tipo a usar genéricos, con código compilado y probado de verdad.

Código real y probado

Todo el código se compiló con tsc (el compilador de TypeScript). Los bloques con ✓ salida real son lo que devolvió: tanto el código que corre como los errores que atrapó. El código está en ejemplos/.

Qué vas a poder hacer al terminar

Tipar variables y funciones, describir objetos con interfaces, usar union types y genéricos, entender los errores de tsc, y saber por qué medio mundo del frontend moderno (React incluido) se pasó a TypeScript.

Capítulo 1

Por qué existe TypeScript

JavaScript no tiene tipos: una variable puede ser un número y un segundo después un texto. Eso lo hace flexible y rápido de escribir, pero también deja pasar errores tontos que solo se descubren corriendo el programa, muchas veces frente al usuario.

El problema en JavaScript

JavaScript · esto no falla hasta que corre
function precioConIva(precio) { return precio * 1.21; }

precioConIva("1000");   // devuelve "100010001...1" (concatena!) o NaN
usuario.nombr;          // undefined, nadie te avisa del typo
lista[0].toFixed(2);    // si la lista está vacía: revienta en producción

La solución de TypeScript

TypeScript es un "superset" de JavaScript: todo tu JS ya es TypeScript válido. Le sumás anotaciones de tipo, y un compilador (tsc) revisa que todo cierre antes de correr. Al final, TypeScript se convierte en JavaScript común (los tipos se borran) para correr en el navegador o en Node. Los tipos son para vos y tu editor, no para la máquina.

Por eso lo vas a ver en todos lados

React, Node, las librerías serias, casi todo el frontend profesional usa TypeScript hoy. En equipos y proyectos que crecen, atrapar errores en el editor en vez de en producción ahorra muchísimo tiempo y bugs. No es una moda: es la respuesta a un problema real de JavaScript.

Capítulo 2

Tipos básicos e inferencia

Tipar es decir de qué tipo es cada cosa. Se hace con : tipo después del nombre. Y muchas veces ni hace falta: TypeScript lo deduce solo.

Los tipos que más vas a usar

tipos básicos
let nombre: string = "Carlos";
let edad: number = 30;
let activo: boolean = true;
let etiquetas: string[] = ["oferta", "nuevo"];   // array de strings

Inferencia: TypeScript adivina

Si asignás un valor al declarar, no hace falta escribir el tipo: TypeScript lo infiere. let edad = 30 ya es number, y si después intentás edad = "treinta", te lo marca.

inferencia
let edad = 30;          // TypeScript sabe que es number
// edad = "treinta";    // error: string no va en un number
No sobre-tipes

Gracias a la inferencia, no anotes lo obvio. let n = 5 ya está claro; escribir let n: number = 5 es ruido. Se tipan sobre todo los parámetros de funciones y las formas de datos (lo que viene). El buen TypeScript es el mínimo necesario para que el compilador te cubra.

Capítulo 3

Funciones tipadas

Acá TypeScript brilla. Tipás lo que entra (los parámetros) y lo que sale (el retorno), y el compilador te obliga a usar la función bien en todos lados.

función tipada
function precioConIva(precio: number, iva: number = 0.21): number {
  return precio * (1 + iva);
}

Los parámetros son number, el iva tiene un valor por defecto, y la función devuelve number. Si llamás precioConIva("1000"), no compila.

Probado de verdad

tsc + node · el código correcto corre✓ salida real
$ tsc ejemplos.ts --strict && node ejemplos.js
precio con IVA: 1210
estado: Ya cobrado
primer producto: Muzzarella
El tipo de retorno es documentación

Anotar el retorno (: number) tiene doble beneficio: quien usa la función sabe qué recibe sin leer el código, y si por error hacés que devuelva otra cosa, TypeScript te avisa. Es documentación que el compilador verifica que sea cierta.

Capítulo 4

Interfaces: la forma de un objeto

La mayoría de los datos con los que trabajás son objetos: un usuario, un producto, un pedido. Una interface describe qué campos tiene y de qué tipo. Es de lo más útil de TypeScript.

interface
interface Producto {
  id: number;
  nombre: string;
  precio: number;
  stock?: number;        // el ? lo hace opcional
}

const pizza: Producto = { id: 1, nombre: "Muzzarella", precio: 8500 };

Ahora pizza tiene una forma garantizada. Tu editor te autocompleta pizza.nombre, y si te olvidás el precio o escribís mal un campo, no compila.

Lo que atrapa

errores reales de tsc✓ salida real
error TS2741: Property 'precio' is missing in type
  '{id,nombre}' but required in type 'Producto'.
  -> te falta una propiedad obligatoria

error TS2551: Property 'nombr' does not exist on type 'Producto'.
  Did you mean 'nombre'?
  -> typo, y hasta te sugiere la corrección
Interfaces y las APIs

Cuando consumís una API (librito 01), una interface describe la forma de lo que llega: interface Usuario {...}. Así, todo tu código que usa esos datos está protegido: si la respuesta cambia o te confundís un campo, TypeScript te avisa. Es el puente perfecto entre el backend y el frontend.

Capítulo 5

Union types: uno de varios valores

A veces un valor solo puede ser una de unas pocas opciones: un estado es "pendiente", "pagado" o "entregado", nada más. Un union type lo expresa, y TypeScript te obliga a respetarlo.

union type
type Estado = "pendiente" | "pagado" | "entregado";

function describir(e: Estado): string {
  return e === "pagado" ? "Ya cobrado" : "En curso";
}

describir("pagado");      // OK
// describir("cancelado"); // error: no está en las opciones
error real✓ salida real
error TS2322: Type '"cancelado"' is not assignable to type 'Estado'.
  -> "cancelado" no es un estado válido

Narrowing: TypeScript te sigue el razonamiento

Cuando chequeás un valor con un if, TypeScript "achica" el tipo dentro de esa rama (narrowing). Si preguntás if (typeof x === "string"), adentro sabe que x es string y te deja usar sus métodos. Sigue tu lógica.

Union types = menos estados imposibles

Al limitar un valor a sus opciones reales, hacés imposible que exista un estado inválido. Un pedido no puede quedar en "cancelaod" por un typo. Modelar con unions es una de las formas más simples de que "los estados imposibles no compilen".

Capítulo 6

Genéricos: tipos que se adaptan

Los genéricos suenan intimidantes y son una idea simple: una función o tipo que funciona con cualquier tipo, sin perder de vista cuál es. Es lo que hace que lista.map() sepa qué devuelve.

El problema que resuelven

Imaginá una función que devuelve el primer elemento de una lista. Sirve para listas de números, de productos, de lo que sea. Sin genéricos, tendrías que elegir un tipo o usar any (que apaga TypeScript). Con genéricos, la función conserva el tipo que le pasaste.

genérico
function primero<T>(lista: T[]): T | undefined {
  return lista[0];
}

const p = primero<Producto>([pizza]);  // p es Producto | undefined
const n = primero([1, 2, 3]);          // n es number | undefined

Esa T es un "tipo variable": se completa con lo que le pases. Si le das productos, devuelve un producto; si le das números, un número. Un solo código, tipado correcto en cada uso.

Ya los usás sin saberlo

Array<Producto>, Promise<Usuario> (del async del librito 06 de JS), el useState<número> de React: todos son genéricos. Entender la idea acá hace que todo eso deje de ser magia. No vas a escribir genéricos complejos seguido, pero los vas a leer todo el tiempo.

Capítulo 7

TypeScript en un proyecto real

Un par de cosas prácticas para arrancar bien: cómo se configura, el modo estricto, y el escape de emergencia que conviene evitar.

tsconfig.json y modo estricto

Un proyecto TypeScript tiene un tsconfig.json con la configuración del compilador. Lo más importante que podés poner: "strict": true. Activa todos los chequeos serios, incluido el que te obliga a manejar los null y undefined. Empezá siempre en estricto; aflojarlo después es fácil, apretarlo en un proyecto grande es un dolor.

el chequeo de undefined, en acción✓ salida real
error TS2322: Type 'number | undefined' is not assignable to type 'number'.
  -> const x: number = lista[0]   (la lista puede venir vacía)

TypeScript te obliga a contemplar que la lista puede estar vacía antes de usar el valor. Ese chequeo solo elimina una de las causas de error más comunes de JavaScript: el famoso "undefined is not a function".

any: el escape que apaga todo

evitá esto
let dato: any = traerAlgo();   // any = "no me revises esto"
dato.loQueSea.total;           // compila, y puede explotar corriendo
any anula el sentido de TypeScript

Poner any apaga el compilador para ese valor: volvés a JavaScript sin red. A veces es un parche momentáneo, pero cada any es un agujero en tu protección. Si no sabés el tipo de algo, casi siempre hay una opción mejor (unknown, que obliga a chequear antes de usar). Usá any como último recurso, no como costumbre.

Fin del librito

Con IA, checklist y cierre

TypeScript es de lo que mejor combina con la IA: como el compilador verifica todo, el código que te genera se valida solo. Si tiene un error de tipo, no compila, y lo ves al toque.

TypeScript con IA

  • Convertir JS a TS: pegá tu JavaScript y pedí la versión tipada. Sale casi listo.
  • Tipar una respuesta de API: pegá un JSON de ejemplo y pedí "dame la interface TypeScript de esto". Instantáneo.
  • Entender un error: pegá el error de tsc y pedí que te lo explique y lo arregle. Los errores de tipos a veces son crípticos y la IA los traduce bien.

Checklist

  • Tipá parámetros de funciones y formas de datos; dejá que infiera lo obvio.
  • Describí tus objetos con interfaces.
  • Usá union types para valores de opciones fijas.
  • Entendé los genéricos aunque no los escribas: los vas a leer siempre.
  • Arrancá con "strict": true.
  • Evitá any: es apagar la red de seguridad.
