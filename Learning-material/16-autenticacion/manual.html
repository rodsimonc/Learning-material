Autenticación y usuarios, de 0

Casi toda app necesita saber quién es cada usuario: registrarse, iniciar sesión, y que cada uno vea solo lo suyo. Hacerlo bien es clave, porque acá se juega la seguridad de las cuentas. En este librito armás un sistema de auth completo y probado: registro, login con tokens, roles y refresh.

Capítulo 1

Autenticar vs autorizar

Dos palabras que se confunden y son distintas. Autenticar es saber quién sos. Autorizar es saber qué podés hacer. Un sistema de usuarios hace las dos.

AutenticaciónAutorización
¿Quién sos?¿Qué podés hacer?
Login con email y contraseñaEste usuario es admin, puede entrar al panel
Verifica identidadVerifica permisos

El flujo completo

de registrarse a usar la app
1. Registro:  el usuario crea su cuenta (email + contraseña)
2. Login:     manda sus datos, el server verifica y le da un token
3. Uso:       en cada pedido, manda el token; el server lo valida
4. Autorización: el server chequea el rol para acciones sensibles
Todo pasa por el servidor

Como en el resto de la colección: la identidad y los permisos se verifican siempre en el backend. El frontend puede esconder un botón de admin, pero eso es cosmético; la seguridad real es que el servidor rechace la acción si el token no corresponde. Nunca confíes en que el frontend "no muestra" algo.

Capítulo 2

Guardar contraseñas: bcrypt

La regla más importante de todas: nunca guardes contraseñas en texto plano. Si te filtran la base (pasa todo el tiempo), todas las cuentas quedan expuestas, y peor, la gente reusa contraseñas. La solución es el hashing.

Hashear, no encriptar

Un hash transforma la contraseña en algo irreversible: de secreto123 sale un texto del que no se puede volver atrás. Guardás el hash, no la contraseña. Cuando el usuario ingresa, hasheás lo que escribió y comparás los hashes. Nunca sabés la contraseña real, ni vos ni nadie que te robe la base.

auth.py · con bcrypt
import bcrypt

def hash_pw(pw: str) -> str:
    return bcrypt.hashpw(pw.encode(), bcrypt.gensalt()).decode()

def verificar_pw(pw: str, hashed: str) -> bool:
    return bcrypt.checkpw(pw.encode(), hashed.encode())

Probado de verdad

el hash no es la contraseña✓ salida real
hash guardado:  $2b$12$3w84pFwQLMe0UqPcpNbGx...
verifica 'secreto123': True
verifica 'otra':       False
bcrypt, no SHA ni MD5

Usá bcrypt (o argon2, scrypt), no SHA256 ni MD5 a secas. Bcrypt está hecho a propósito para ser lento y llevar "sal" (el gensalt), lo que lo hace resistente a ataques de fuerza bruta. Un hash rápido como SHA es fácil de romper con diccionarios. Este es de esos detalles donde la opción cómoda es la insegura.

Capítulo 3

Registro y login

Con el hashing resuelto, los dos endpoints base. Registro crea la cuenta guardando el hash; login verifica y, si está bien, entrega un token.

auth.py
@app.post("/registro")
def registro(r: Registro):
    if r.email in USUARIOS:
        raise HTTPException(409, "el email ya está registrado")
    USUARIOS[r.email] = {"email": r.email, "pw": hash_pw(r.password),
                         "rol": r.rol}
    return {"email": r.email, "rol": r.rol}

@app.post("/login")
def login(l: Login):
    u = USUARIOS.get(l.email)
    if not u or not verificar_pw(l.password, u["pw"]):
        raise HTTPException(401, "credenciales invalidas")
    return { "access_token": ..., "refresh_token": ... }
prueba real✓ salida real
registro -> {'email': 'carlos@x.com', 'rol': 'cliente'}
registro duplicado -> 409: el email ya está registrado
login con clave incorrecta -> 401: credenciales invalidas
Error genérico a propósito

Fijate que si el email no existe o la clave está mal, devolvemos el mismo error: "credenciales invalidas". Si dijéramos "ese email no existe", le estaríamos confirmando a un atacante qué emails están registrados. El mensaje vago es intencional: no le des pistas a quien prueba.

Capítulo 4

Los tokens: JWT

Después del login, el usuario necesita una forma de probar quién es en cada pedido, sin mandar la contraseña cada vez. Eso es el token. El estándar más usado es el JWT (JSON Web Token).

Qué es un JWT

Un JWT es un texto firmado que lleva datos adentro (quién sos, tu rol, cuándo expira). El server lo firma con una clave secreta; cualquiera puede leer su contenido, pero nadie puede falsificarlo sin la clave. En cada pedido, el frontend lo manda en el header Authorization: Bearer <token>, y el server verifica la firma.

auth.py · crear y verificar
def crear_token(email, rol, tipo, minutos):
    payload = {"sub": email, "rol": rol, "tipo": tipo,
               "exp": ahora + timedelta(minutes=minutos)}
    return jwt.encode(payload, SECRET, algorithm="HS256")

def decodificar(token):
    try:
        return jwt.decode(token, SECRET, algorithms=["HS256"])
    except jwt.ExpiredSignatureError:
        raise HTTPException(401, "token expirado")
el contenido de un token real✓ salida real
access (recortado): eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJ...
contenido: {'sub': 'carlos@x.com', 'rol': 'cliente', 'tipo': 'access'}
El JWT se lee, no se esconde

El contenido de un JWT no está encriptado, solo firmado: cualquiera puede leer lo que lleva. Por eso nunca metas datos sensibles adentro (contraseñas, datos privados). Lleva solo lo justo para identificar: el id o email, y el rol. La firma garantiza que no se pueda alterar, no que sea secreto.

Capítulo 5

Proteger endpoints

Con los tokens listos, protegemos las rutas: las que requieren estar logueado leen el token, lo validan, y sacan de ahí quién es el usuario. En FastAPI esto se hace elegante con una dependencia.

auth.py · la dependencia que protege
def usuario_actual(cred = Depends(seguridad)) -> dict:
    datos = decodificar(cred.credentials)
    if datos.get("tipo") != "access":
        raise HTTPException(401, "se requiere un access token")
    return datos

@app.get("/perfil")
def perfil(u: dict = Depends(usuario_actual)):
    return {"email": u["sub"], "rol": u["rol"]}

Cualquier endpoint que ponga Depends(usuario_actual) queda protegido: si no llega un token válido, ni entra a la función. Y adentro, ya tenés al usuario identificado.

prueba real✓ salida real
GET /perfil sin token  -> 401
GET /perfil con token  -> {'email': 'carlos@x.com', 'rol': 'cliente'}
Access token corto

El access token dura poco (15 minutos en el ejemplo). ¿Por qué? Si te lo roban, el daño tiene fecha de vencimiento cercana. Pero no querés que el usuario loguee cada 15 minutos, y ahí entra el refresh token del capítulo 7.

Capítulo 6

Autorización: roles y permisos

No todos los usuarios son iguales: un cliente ve lo suyo, un admin entra al panel. El rol viaja en el token, y el server lo chequea antes de dejar pasar a las acciones sensibles.

auth.py · exigir un rol
def requiere_rol(rol: str):
    def check(u: dict = Depends(usuario_actual)) -> dict:
        if u["rol"] != rol:
            raise HTTPException(403, f"requiere rol '{rol}'")
        return u
    return check

@app.get("/admin")
def admin(u: dict = Depends(requiere_rol("admin"))):
    return {"mensaje": f"bienvenido admin {u['sub']}"}
prueba real✓ salida real
GET /admin con usuario cliente -> 403: requiere rol 'admin'
GET /admin con usuario admin   -> {'mensaje': 'bienvenido admin jefe@x.com'}
401 vs 403

Dos códigos que conviene no confundir: 401 (no autenticado) es "no sé quién sos, logueate"; 403 (prohibido) es "sé quién sos, pero no tenés permiso para esto". El dashboard de la tienda (librito 13) usa justo esto: solo el rol admin entra.

Capítulo 7

Refresh tokens: sesiones largas y seguras

El access token dura poco por seguridad, pero nadie quiere loguearse cada 15 minutos. El refresh token resuelve la tensión: dura mucho, y sirve para pedir un access nuevo sin volver a poner la contraseña.

Los dos tokens

Access tokenRefresh token
Corto (minutos)Largo (días)
Va en cada pedidoSolo para renovar el access
Si se roba, expira prontoSe guarda con más cuidado
auth.py
@app.post("/refresh")
def refresh(r: Refresh):
    datos = decodificar(r.refresh_token)
    if datos.get("tipo") != "refresh":
        raise HTTPException(401, "se requiere un refresh token")
    return {"access_token": crear_token(datos["sub"], datos["rol"],
                                        "access", ACCESS_MIN)}
prueba real✓ salida real
POST /refresh (con refresh token) -> nuevo access token
Dónde guardar los tokens

Como viste en el librito 09: el refresh token, idealmente en una cookie HttpOnly (que el JavaScript no puede leer, así se protege de robos por XSS). El access token puede ir en memoria. Guardar tokens en localStorage es común pero más expuesto. Cuanto más largo vive un token, con más cuidado se guarda.

Capítulo 8

OAuth (login social) y reset de contraseña

Dos cosas que casi toda app termina necesitando: el "iniciar sesión con Google" y el "olvidé mi contraseña". Los conceptos, para que sepas cómo encararlos.

OAuth: login con Google, GitHub, etc.

Con OAuth, en vez de manejar la contraseña vos, delegás la identidad en un proveedor grande (Google). El flujo: el usuario va a Google, se autentica ahí, y Google le devuelve a tu app una prueba de quién es. Vos nunca ves su contraseña de Google. Ventaja: menos fricción y una cosa menos que asegurar. En la práctica se usa una librería (Authlib) o un servicio (el Auth de Supabase, que ya lo trae).

Reset de contraseña

el flujo seguro
1. El usuario pide reset con su email
2. Generás un token único con vencimiento corto y lo guardás
3. Le mandás un email con un link que lleva ese token (librito 18)
4. El link abre un formulario; al enviar, validás el token
5. Si es válido y no venció, actualizás la contraseña (nuevo hash)
El detalle del email genérico, otra vez

Cuando alguien pide un reset, respondé siempre lo mismo ("si el email existe, te mandamos un link"), exista o no la cuenta. Igual que en el login, no confirmes qué emails están registrados. Y el token de reset: único, de un solo uso, y que venza rápido (una hora). Es una llave temporal a la cuenta.

Fin del librito

Checklist y cierre

Armaste un sistema de autenticación completo: registro seguro, login con tokens, protección por rol y sesiones renovables. Este es el resumen para no olvidarte nada crítico.

Checklist de auth

  • Contraseñas hasheadas con bcrypt (o argon2), nunca en texto plano.
  • Errores genéricos en login y reset: no revelar qué emails existen.
  • JWT firmado con una clave secreta en variable de entorno.
  • Sin datos sensibles dentro del token (se puede leer).
  • Access token corto + refresh token largo.
  • Endpoints sensibles protegidos y con chequeo de rol en el servidor.
  • Refresh token en cookie HttpOnly cuando se pueda.
  • Token de reset único, de un solo uso y con vencimiento corto.

Lo que te llevás

La autenticación es de lo más delicado que vas a construir, y ahora sabés hacerla bien: proteger las contraseñas, manejar sesiones con tokens, y controlar el acceso.
