Testing, de cero a tests que te cubren

Los tests son código que prueba tu código. Te dan la confianza de cambiar cosas sin romper lo que ya andaba. Este libro va de no haber escrito un test en tu vida a cubrir una función, manejar errores y medir cobertura, en pytest (Python) y jest (Node). Los bloques con ✓ salida real son corridas de verdad.

  • Parte 3, más allá. Mocks, tests de integración y cobertura.
  • Parte 4, a producción. TDD, buenas prácticas y cheatsheet.

Capítulo 1

Por qué vale la pena testear

Testear parece tiempo perdido hasta la primera vez que un test atrapa un bug antes de que llegue a producción. Ahí cambia la cabeza.

Qué te da

  • Confianza para cambiar. Con tests, tocás código viejo sin miedo: si rompés algo, un test se pone rojo al instante.
  • Atrapar regresiones. Una regresión es cuando arreglás A y sin querer rompés B. Los tests de B te avisan.
  • Documentación viva. Un buen test muestra cómo se usa una función y qué se espera de ella.
  • Menos debugging manual. En vez de probar a mano en el navegador cada vez, corrés los tests y listo.

La pirámide de tests

No todos los tests son iguales. Se organizan en una pirámide: muchos abajo, pocos arriba.

          /\
         /e2e\        pocos: prueban todo junto, como un usuario real. Lentos.
        /------\
       /  integ  \    algunos: prueban que varias piezas funcionen juntas.
      /------------\
     /     unit     \ muchos: prueban una función aislada. Rápidos y baratos.
    /----------------\
  • Unit. Prueban una función sola, sin base de datos ni red. Rapidísimos. La base de todo.
  • Integración. Prueban que varias piezas se entiendan: tu API contra una base real, por ejemplo.
  • End-to-end (e2e). Simulan a un usuario usando la app entera. Los más valiosos y los más caros de mantener.
La estrategia

Muchos tests unitarios (rápidos, precisos), algunos de integración, y pocos e2e para los flujos críticos. Este libro se enfoca en los unitarios, que son donde más rinde empezar.

Capítulo 2

Cómo es un test por dentro

Todo test, en cualquier lenguaje, tiene la misma forma de tres pasos. Si entendés esto, entendés todos los frameworks.

Arrange, Act, Assert

  1. Arrange (preparar). Armás los datos que necesita la prueba.
  2. Act (actuar). Llamás a la función que querés probar.
  3. Assert (afirmar). Verificás que el resultado sea el esperado. Si no lo es, el test falla.
los tres pasos
def test_subtotal_suma_bien():
    items = [(100, 2), (50, 1)]        # 1. arrange
    resultado = subtotal(items)        # 2. act
    assert resultado == 250            # 3. assert

El corazón: el assert

Un assert es una afirmación que tiene que ser verdadera. Si subtotal(items) no da 250, el assert falla y el framework te marca el test en rojo con el detalle. Un test sin assert no prueba nada.

Un test, una cosa

Cada test debería verificar una sola cosa, y su nombre debería decir qué. test_carrito_vacio_da_cero es mejor que test_carrito. Cuando falle, el nombre solo ya te dice qué se rompió.

Capítulo 3

pytest desde cero

pytest es el framework de testing más usado en Python. Simple: escribís funciones que empiezan con test_ y usás assert. Nada de ceremonia.

El código a probar

carrito.py
def subtotal(items):
    """items: lista de (precio, cantidad)."""
    return sum(precio * cant for precio, cant in items)

def aplicar_descuento(monto, porcentaje):
    if not 0 <= porcentaje <= 100:
        raise ValueError("porcentaje debe estar entre 0 y 100")
    return monto * (1 - porcentaje / 100)

Los tests

test_carrito.py
from carrito import subtotal

def test_subtotal_suma_bien():
    assert subtotal([(100, 2), (50, 1)]) == 250

def test_subtotal_carrito_vacio():
    assert subtotal([]) == 0

Correrlos

Instalás con pip install pytest y corrés pytest -v. El -v muestra cada test:

pytest -v✓ salida real
============== test session starts ==============
collected 6 items

test_carrito.py::test_subtotal_suma_bien PASSED          [ 16%]
test_carrito.py::test_subtotal_carrito_vacio PASSED      [ 33%]
test_carrito.py::test_descuento[100-0-100] PASSED        [ 50%]
test_carrito.py::test_descuento[100-10-90] PASSED        [ 66%]
test_carrito.py::test_descuento[100-100-0] PASSED        [ 83%]
test_carrito.py::test_descuento_invalido_lanza_error PASSED [100%]

============== 6 passed in 0.02s ==============

Verde y a otra cosa. pytest encuentra solo los archivos test_*.py y las funciones test_*. Los tests con corchetes ([100-10-90]) vienen del próximo truco.

Capítulo 4

jest desde cero

jest es el framework de testing más usado en el mundo JavaScript. La estructura es un poco más explícita que pytest, pero la idea es idéntica.

El código y los tests

carrito.js
function subtotal(items) {
  return items.reduce((acc, [precio, cant]) => acc + precio * cant, 0);
}
function aplicarDescuento(monto, porcentaje) {
  if (porcentaje < 0 || porcentaje > 100) throw new Error("porcentaje invalido");
  return monto * (1 - porcentaje / 100);
}
module.exports = { subtotal, aplicarDescuento };
carrito.test.js
const { subtotal } = require("./carrito");

test("subtotal suma bien", () => {
  expect(subtotal([[100, 2], [50, 1]])).toBe(250);
});

test("carrito vacio da 0", () => {
  expect(subtotal([])).toBe(0);
});

En jest, test("nombre", fn) define un test, y expect(x).toBe(y) es el assert. Los "matchers" como toBe, toEqual, toThrow son las distintas afirmaciones que podés hacer.

Correrlos

npx jest✓ salida real
Test Suites: 1 passed, 1 total
Tests:       6 passed, 6 total
Snapshots:   0 total
Time:        0.553 s
Ran all test suites.

jest encuentra solo los archivos *.test.js. Mismo resultado que pytest, otra sintaxis.

Capítulo 5

Un test, muchos casos

Casi nunca alcanza con probar un solo valor. Querés probar el caso normal, el borde, el vacío, el límite. Copiar y pegar el test cambiando el número es feo. Los dos frameworks tienen una solución elegante.

pytest: parametrize

Con un decorador, corrés el mismo test con muchos juegos de datos. Cada uno cuenta como un test aparte:

python
import pytest
from carrito import aplicar_descuento

@pytest.mark.parametrize("monto,pct,esperado", [
    (100, 0,   100),   # sin descuento
    (100, 10,  90),    # caso normal
    (100, 100, 0),     # borde: 100% off
])
def test_descuento(monto, pct, esperado):
    assert aplicar_descuento(monto, pct) == esperado

Eso generó los tres tests con corchetes que viste en la salida del capítulo 3: test_descuento[100-10-90]. Un test, tres casos, y si uno falla sabés cuál.

jest: test.each

javascript
test.each([
  [100, 0,   100],
  [100, 10,  90],
  [100, 100, 0],
])("descuento(%i, %i) = %i", (monto, pct, esperado) => {
  expect(aplicarDescuento(monto, pct)).toBe(esperado);
});
Pensá en los bordes

Los bugs viven en los extremos: el cero, el vacío, el negativo, el máximo, el uno. Cuando escribas casos, no pruebes solo el "camino feliz". El valor de una tabla de casos es que te obliga a pensar en los raros.

Capítulo 6

Testear que algo falle a propósito

A veces lo correcto es que tu función lance un error. Si le pasan un descuento de 150%, tiene que quejarse. Testear que el error ocurra es tan importante como testear el caso bueno.

pytest: pytest.raises

python
import pytest
from carrito import aplicar_descuento

def test_descuento_invalido_lanza_error():
    with pytest.raises(ValueError):
        aplicar_descuento(100, 150)   # 150% no existe, debe fallar

El test pasa si adentro del with se lanza un ValueError. Si la función no falla cuando debería, el test se pone rojo. Lo viste pasar en la salida del capítulo 3.

jest: toThrow

javascript
test("descuento invalido lanza error", () => {
  expect(() => aplicarDescuento(100, 150)).toThrow();
});

Fijate el detalle: le pasás una función (() => ...) a expect, no el resultado. jest la ejecuta y verifica que tire error.

Probá también lo que NO debe pasar

Un buen set de tests cubre las tres zonas: entradas válidas (funciona), entradas inválidas (falla bien), y bordes (el límite exacto). Las tres juntas te dan confianza real.

Capítulo 7

Leer un test que falla

El momento en que un test se pone rojo es donde te devuelve la inversión. Pero solo si sabés leer lo que te dice. La buena noticia: pytest y jest son muy claros.

Un fallo real

Escribimos un test que espera 250 pero el código da 200. Esto es lo que muestra pytest, tal cual:

pytest (test que falla)✓ salida real
=================== FAILURES ===================
_________________ test_con_bug _________________

    def test_con_bug():
>       assert subtotal([(100, 2)]) == 250
E       assert 200 == 250
E        +  where 200 = subtotal([(100, 2)])

test_falla.py:4: AssertionError
=============== short test summary info ===============
FAILED test_falla.py::test_con_bug - assert 200 == 250

Cómo se lee

Todo lo que necesitás está ahí. La línea que falló (assert ... == 250). El valor real contra el esperado (assert 200 == 250). De dónde salió el 200 (where 200 = subtotal(...)). Y la ubicación exacta (test_falla.py:4).

Con eso ya sabés si el bug está en el código o en el test. Acá el código devolvió 200 cuando esperábamos 250: o la función tiene un bug, o el test espera mal. Investigás esas cuatro líneas, no toda la app.

Un test rojo es una buena noticia

Significa que el test hizo su trabajo: atrapó algo antes que un usuario. El objetivo no es que nunca fallen, es que fallen acá y ahora, en tu máquina, y no en producción.

Capítulo 8

Mocks: aislar lo que no controlás

Tu función llama a una API de pagos externa. No querés cobrarle a nadie de verdad cada vez que corrés los tests, ni depender de que esa API esté online. Un mock es un doble de mentira que reemplaza esa dependencia.

Por qué

Un test unitario tiene que ser rápido, repetible y no depender del mundo exterior. Si tu código llama a la red, a la base o al reloj, esas partes se reemplazan por mocks que devuelven lo que vos decidas. Así probás tu lógica, no la de terceros.

pytest

python
from unittest.mock import patch

def test_procesar_pago_ok():
    # reemplazamos la llamada real a la API por una falsa
    with patch("pagos.cobrar_api", return_value={"ok": True}):
        resultado = procesar_pago(100)
    assert resultado == "confirmado"

jest

javascript
jest.mock("./pagos");
const pagos = require("./pagos");

test("procesar pago ok", () => {
  pagos.cobrarApi.mockReturnValue({ ok: true });   // doble falso
  expect(procesarPago(100)).toBe("confirmado");
});
No abuses del mock

Si mockeás todo, terminás probando tus mocks y no tu código. Mockeá solo lo externo y lento (red, base, servicios de terceros). La lógica tuya se prueba de verdad, sin doble.

Capítulo 9

Tests de integración

Los unitarios prueban piezas sueltas. Los de integración prueban que esas piezas se entiendan entre sí: tu API respondiendo de verdad, tu código hablando con una base real.

Probar una API

En vez de mockear, levantás la app en modo de prueba y le pegás como lo haría un cliente. Si construiste la API del librito de APIs, esto le cae justo.

python (FastAPI + TestClient)
from fastapi.testclient import TestClient
from main import app

client = TestClient(app)

def test_leer_usuario():
    r = client.get("/usuarios/42")
    assert r.status_code == 200
    assert r.json()["nombre"] == "Carlos"

def test_usuario_inexistente_da_404():
    r = client.get("/usuarios/999")
    assert r.status_code == 404
javascript (Express + supertest)
const request = require("supertest");
const app = require("./server");

test("GET /usuarios/42 devuelve 200", async () => {
  const r = await request(app).get("/usuarios/42");
  expect(r.status).toBe(200);
  expect(r.body.nombre).toBe("Carlos");
});

Estos tests prueban el circuito completo: ruteo, lógica, formato de respuesta y códigos de estado. Son los que te avisan cuando una pieza dejó de encajar con otra.

Base de datos en los tests

Para tests de integración con base, se usa una base de prueba separada (o SQLite en memoria) que se crea y se borra en cada corrida. Así los tests no pisan datos reales y arrancan siempre limpios.

Capítulo 10

Cobertura: cuánto de tu código se prueba

La cobertura (coverage) mide qué porcentaje de tu código ejecutan los tests. Es una brújula útil, con una trampa que conviene conocer.

Medirla

En Python, pytest --cov. Te dice qué líneas se corrieron y cuáles quedaron sin tocar:

pytest --cov=carrito✓ salida real
Name         Stmts   Miss  Cover   Missing
------------------------------------------
carrito.py       6      0   100%
------------------------------------------
TOTAL            6      0   100%
6 passed in 0.03s

100%: los tests ejecutaron las 6 líneas. La columna Missing te lista las líneas sin cubrir, así sabés qué te falta testear. En jest es jest --coverage.

La trampa

100% no es 100% seguro

La cobertura mide si una línea se ejecutó, no si la probaste bien. Podés ejecutar una línea sin un solo assert que verifique su resultado. Un 100% con tests flojos vale menos que un 70% con tests que verifican de verdad. Usá la cobertura para encontrar zonas sin tocar, no como nota final.

Un objetivo razonable en la práctica: 70 a 80% en el código importante, con foco en la lógica que duele si se rompe. Perseguir el 100% a toda costa suele ser tiempo mal gastado.

Cierre

TDD, buenas prácticas y cheatsheet

Una técnica popular, las costumbres que hacen tests mantenibles, y una hoja de referencia.

TDD: el test primero

Test-Driven Development le da vuelta el orden: escribís el test antes que el código. El ciclo es rojo, verde, refactor.

  1. Rojo. Escribís un test de algo que todavía no existe. Falla, obvio.
  2. Verde. Escribís el mínimo código para que pase.
  3. Refactor. Mejorás el código con la red de seguridad del test puesta.

No hace falta usar TDD siempre, pero probarlo te enseña a escribir código más testeable y a pensar qué tiene que hacer una función antes de escribirla.

Buenas prácticas

  • Tests rápidos y aislados: que no dependan del orden ni de datos de otro test.
  • Nombres que describen: cuando falla, el nombre solo dice qué se rompió.
  • Un motivo de fallo por test. Muchos asserts sin relación esconden qué falló.
  • Corré los tests seguido, y en cada push (eso es CI, el próximo librito).

Cheatsheet

pytest
pytest                # corre todos
pytest -v             # muestra cada test
pytest archivo.py     # un archivo
pytest -k "descuento" # solo los que matchean el nombre
pytest --cov=paquete  # con cobertura
jest
npx jest              # corre todos
npx jest --watch      # re-corre al guardar
npx jest carrito      # los que matchean
npx jest --coverage   # con cobertura
