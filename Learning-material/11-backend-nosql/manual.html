Backend · Bases de datos NoSQL

Backend NoSQL, de 0 hasta el deploy

No todos los datos entran cómodos en tablas. Las bases NoSQL guardan la información de otra forma, más flexible, y para muchos proyectos son la mejor opción. En este librito armás un backend con MongoDB desde cero, hasta dejar una base funcionando en internet. Todo por pasos, con código real y probado, en Python y en Node.

Código real y probado

El CRUD de este libro se corrió contra un MongoDB de verdad. Los bloques con ✓ salida real son lo que devolvió el programa. El código completo está en ejemplos/: backend en Python (FastAPI + pymongo) y en Node (Express + driver de MongoDB).

Qué vas a poder hacer al terminar

Pensar tus datos como documentos, hacer un CRUD contra MongoDB, escribir consultas y agregaciones, saber cuándo NoSQL le gana a SQL y cuándo no, y publicar una base en MongoDB Atlas gratis para que tu app la use en producción.

Cómo moverte

Capítulo 1

Qué es NoSQL y por qué existe

NoSQL agrupa las bases que no usan el modelo de tablas relacionales. El nombre significa "no solo SQL". Nacieron para resolver cosas donde el modelo relacional se ponía incómodo: datos que cambian de forma, escala enorme, y velocidad de desarrollo.

El contraste con lo relacional

En una base relacional, el esquema es rígido: definís las columnas antes y toda fila las respeta. Eso da consistencia, pero cuesta cuando tus datos no son todos iguales o cambian seguido. NoSQL afloja esa rigidez: cada registro puede tener su propia forma.

Relacional (SQL)Documental (NoSQL)
Tablas con columnas fijasColecciones de documentos flexibles
Esquema definido de antemanoEsquema flexible, por documento
Datos repartidos en varias tablasDatos relacionados juntos en un documento
Se une con JOINSe embebe o se referencia
No es "mejor", es distinto

NoSQL no reemplaza a SQL, es otra herramienta. Hay proyectos donde uno brilla y el otro sufre, y viceversa. El capítulo 10 es justo sobre cómo elegir. Por ahora, entendé que existen dos grandes formas de guardar datos.

Capítulo 2

Los tipos de bases NoSQL

NoSQL es una familia, no una sola cosa. Hay cuatro tipos principales, cada uno pensado para una forma distinta de datos. Conviene conocerlos para saber de qué se habla.

TipoCómo guardaEjemplo
DocumentalDocumentos tipo JSON, agrupados en coleccionesMongoDB
Clave-valorPares clave→valor, como un diccionario giganteRedis
ColumnarPor columnas, para muchísimos datosCassandra
GrafoNodos y relaciones, para redesNeo4j

Nos enfocamos en documental (MongoDB)

El tipo documental es el más usado para backends de aplicaciones, y MongoDB es su representante estrella. Un documento es prácticamente un objeto JSON, así que si venís del frontend o de las APIs, ya lo tenés medio aprendido. El resto del libro es MongoDB.

Redis, mención aparte

Redis (clave-valor) lo vas a cruzar seguido, pero para otra cosa: como caché rapidísima delante de tu base principal, o para sesiones y colas. No suele ser la base principal de tu app, sino un complemento. Bueno saber que existe.

Capítulo 3

Pensar en documentos

El salto mental de SQL a MongoDB es pasar de filas en tablas a documentos en colecciones. Una vez que hace clic, es muy natural, sobre todo si ya trabajaste con JSON.

Documento y colección

Un documento es un objeto tipo JSON: pares clave-valor, que pueden incluir listas y objetos anidados. Una colección es un grupo de documentos del mismo tema (el equivalente a una tabla). Cada documento tiene un _id único que MongoDB genera solo.

un documento en la colección usuarios
{
  "_id": "6a9b7c6c119cffb180f0d21c",
  "email": "carlos@x.com",
  "nombre": "Carlos",
  "direcciones": [
    { "calle": "San Martín 123", "ciudad": "Córdoba" },
    { "calle": "Belgrano 456", "ciudad": "Rosario" }
  ]
}

La gran diferencia: datos anidados

Mirá las direcciones: van adentro del usuario, como una lista de objetos. En SQL eso serían otra tabla y un JOIN. Acá, los datos que se usan juntos viven juntos, en un solo documento. Lo leés de una y ya tenés todo.

Esquema flexible, con criterio

MongoDB no te obliga a que todos los documentos de una colección tengan los mismos campos. Es potente para datos que varían, pero no es excusa para el caos: en la práctica mantenés una forma consistente para poder trabajar. La flexibilidad es una herramienta, no una invitación al desorden.

Capítulo 4

Usar MongoDB: local y en la nube

Para desarrollar necesitás una base MongoDB corriendo. Tenés dos caminos, y conviene conocer los dos.

Local, para desarrollar

Instalás MongoDB Community en tu compu y lo corrés con el comando mongod. Queda escuchando en 127.0.0.1:27017, la dirección local por defecto. Tu backend se conecta ahí. Es lo que usamos para probar los ejemplos de este libro.

las dos URLs de conexión que vas a usar
Local:  mongodb://127.0.0.1:27017
Atlas:  mongodb+srv://usuario:clave@cluster0.xxxx.mongodb.net

Atlas, para producción

MongoDB Atlas es la versión gestionada en la nube (del capítulo 12 hacemos el deploy ahí). Tiene un plan gratis que alcanza de sobra para aprender y para proyectos chicos. La idea: desarrollás contra tu Mongo local y desplegás contra Atlas, cambiando solo la URL de conexión.

Compass, para mirar

MongoDB Compass es una app visual para explorar tu base: ver las colecciones, los documentos, correr consultas con clics. Muy útil para entender qué hay guardado sin escribir código. Descarga aparte, gratis.

Capítulo 5

Las operaciones básicas

MongoDB no usa SQL: se maneja con métodos y filtros que son objetos. Son cuatro operaciones, las mismas del CRUD, con otra sintaxis. Todo esto corrió contra un MongoDB real.

Las cuatro, con su equivalente

MongoDBQué haceEn SQL sería
insertOneAgrega un documentoINSERT
findBusca documentosSELECT
updateOneModifica un documentoUPDATE
deleteOneBorra un documentoDELETE

Filtros y operadores

Buscás pasando un objeto que describe lo que querés. Para condiciones hay operadores como $gt (mayor que), $lt (menor), $in (está en una lista). Mirá una búsqueda real sobre una colección de productos:

consultas reales✓ salida real
== precio > 20  →  find({"precio": {"$gt": 20}}) ==
{'nombre': 'Teclado', 'precio': 25}
{'nombre': 'Monitor', 'precio': 200}

== con stock y tag "gaming"  →  find({"stock": {"$gt": 0}, "tags": "gaming"}) ==
{'nombre': 'Teclado'}
{'nombre': 'Monitor'}

Fijate en la última: "tags": "gaming" busca dentro de una lista. Como el documento guarda tags como array, MongoDB matchea si "gaming" está entre ellos. Ese tipo de consulta sobre datos anidados es donde el modelo documental se siente natural.

Capítulo 6

Construir el CRUD paso a paso (Python)

Ahora el backend de verdad: una API con FastAPI y pymongo que crea, lee, actualiza y borra tareas en MongoDB. Este es el ejemplos/backend/app.py, corrido contra un Mongo real.

backend/app.py (recorte)
cliente = MongoClient(MONGO_URL)
tareas = cliente["miapp"]["tareas"]   # base "miapp", colección "tareas"

@app.post("/tareas")
def crear(t: TareaIn):
    r = tareas.insert_one(t.model_dump())
    return a_salida(tareas.find_one({"_id": r.inserted_id}))

@app.get("/tareas")
def listar():
    return [a_salida(d) for d in tareas.find()]

@app.put("/tareas/{tid}")
def actualizar(tid: str, t: TareaIn):
    r = tareas.update_one({"_id": oid(tid)}, {"$set": t.model_dump()})
    if r.matched_count == 0: raise HTTPException(404, "no existe")
    return a_salida(tareas.find_one({"_id": oid(tid)}))

El $set en el update dice "cambiá solo estos campos". El oid() convierte el id de texto que llega por la URL al ObjectId que MongoDB usa internamente. Y a_salida() pasa el _id a texto para el JSON de respuesta.

Probado de verdad

prueba real✓ salida real
== crear dos documentos ==
{'id': '6a9b7c6c119cffb180f0d21c', 'titulo': 'Aprender NoSQL', 'hecha': False}
{'id': '6a9b7c6c119cffb180f0d21d', 'titulo': 'Deploy a Atlas', 'hecha': False}
== actualizar la 1 (PUT) ==
{'id': '6a9b7c6c119cffb180f0d21c', 'titulo': 'Aprender NoSQL', 'hecha': True}
== borrar la 2 ==
{'borrada': '6a9b7c6c119cffb180f0d21d'}
== listar final ==
[{'id': '6a9b7c6c119cffb180f0d21c', 'titulo': 'Aprender NoSQL', 'hecha': True}]
== id que no existe ==
404 {'detail': 'no existe'}

Notá el id: en Mongo es ese ObjectId largo hexadecimal, no el 1, 2, 3 que autogenera SQL. Es único a nivel global, lo que ayuda cuando la base está repartida en varios servidores.

Capítulo 7

El mismo CRUD en Node

Con Node la cosa se siente todavía más natural, porque los documentos de MongoDB son objetos JavaScript. Express más el driver oficial de MongoDB. Este es el ejemplos/backend/server.js, corrido de verdad.

backend/server.js (recorte)
app.post("/tareas", async (req, res) => {
  const { titulo, hecha = false } = req.body;
  const r = await tareas.insertOne({ titulo, hecha });
  const d = await tareas.findOne({ _id: r.insertedId });
  res.json(aSalida(d));
});

app.put("/tareas/:id", async (req, res) => {
  const _id = oid(req.params.id);
  const { titulo, hecha = false } = req.body;
  const r = await tareas.updateOne({ _id }, { $set: { titulo, hecha } });
  if (r.matchedCount === 0) return res.status(404).json({ detail: "no existe" });
  res.json(aSalida(await tareas.findOne({ _id })));
});

El código es casi calcado del de Python: mismos métodos (insertOne, findOne, updateOne), mismos filtros como objetos. Lo único distinto es que en Node son asíncronos, de ahí el await.

Probado de verdad

prueba real (curl)✓ salida real
== crear ==   id=6a9b7cc87ba1029c62c3ff26
== listar ==
[{"id":"6a9b7cc87ba1029c62c3ff26","titulo":"Aprender NoSQL","hecha":false},
 {"id":"6a9b7cc87ba1029c62c3ff27","titulo":"Deploy Atlas","hecha":false}]
== put ==
{"id":"6a9b7cc87ba1029c62c3ff26","titulo":"Aprender NoSQL","hecha":true}
== id invalido ==
400
El id inválido devuelve 400

Si mandás un id con formato que no es un ObjectId válido, el backend responde 400 (petición mal formada), distinto del 404 (no existe). Validar la forma del id antes de consultar es un detalle chico que evita errores feos.

Capítulo 8

Modelar: embeber o referenciar

La decisión más importante en MongoDB es cómo organizás los datos relacionados. Tenés dos opciones, y elegir bien es lo que separa un buen diseño de uno que sufre.

Embeber: los datos adentro

Ponés los datos relacionados dentro del documento. Un pedido con sus items adentro, como una lista. Ventaja: lo leés todo de una, sin unir nada. Ideal cuando los datos se usan siempre juntos y no crecen sin límite.

embebido
{ "_id": "...", "cliente": "Carlos",
  "items": [ {"prod": "Teclado", "cant": 1},
             {"prod": "Mouse",   "cant": 2} ] }

Referenciar: guardar el id

Guardás solo el _id del otro documento, como la clave foránea de SQL. Ideal cuando los datos se comparten (muchos pedidos del mismo cliente) o crecen mucho (los miles de comentarios de un post no van embebidos).

referenciado
{ "_id": "...", "cliente_id": "6a9b...21c", "total": 55 }
La regla práctica

Embebé lo que se lee junto y es acotado (la dirección de un usuario, los items de un pedido). Referenciá lo que se comparte o crece sin techo (usuarios, catálogos, listas grandes). Un error clásico de quien viene de SQL es referenciar todo por costumbre y perder la ventaja de Mongo; el opuesto es embeber algo que crece hasta reventar el documento.

Capítulo 9

Índices y agregación

Dos herramientas para que Mongo sea rápido y para sacar cuentas: los índices, iguales en idea a los de SQL, y el pipeline de agregación, la forma de resumir datos.

Índices

Como en SQL, un índice acelera las búsquedas por un campo. Sin él, Mongo recorre todos los documentos. Se crea sobre los campos por los que filtrás seguido.

crear un índice
tareas.create_index("titulo")
# Mongo también indexa el _id automáticamente

Agregación: resumir datos

Cuando querés cuentas (promedios, totales, agrupar), usás el pipeline de agregación: una serie de etapas que transforman los datos. Es el equivalente al GROUP BY de SQL. Un ejemplo real, el precio promedio de una colección de productos:

agregación real✓ salida real
aggregate([{"$group": {"_id": None, "promedio": {"$avg": "$precio"}}}])
→ [{'_id': None, 'promedio': 80.0}]

El $group junta documentos y $avg saca el promedio del campo precio. Podés encadenar etapas: filtrar con $match, después agrupar con $group, después ordenar con $sort. Es la herramienta pesada de Mongo para reportes y estadísticas.

Capítulo 10

SQL vs NoSQL: cuándo cada uno

La pregunta del millón. No hay ganador absoluto: hay proyectos para cada uno. Esta es la guía honesta para decidir sin dogmas.

Elegí relacional (SQL) cuando

  • Los datos tienen relaciones claras y muchas: usuarios, pedidos, productos, facturas que se cruzan.
  • Necesitás consistencia fuerte y transacciones: un banco, un sistema de pagos, un inventario donde las cuentas tienen que cerrar siempre.
  • Vas a hacer consultas complejas que cruzan varias entidades.
  • La estructura de los datos es estable y bien conocida.

Elegí documental (NoSQL) cuando

  • Tus datos son documentos naturales que se leen juntos: un perfil, un post con sus datos, un catálogo.
  • La estructura varía o cambia seguido y no querés migraciones a cada rato.
  • Priorizás velocidad de desarrollo y de lectura sobre relaciones complejas.
  • Necesitás escalar horizontalmente a muchísimos datos con facilidad.
La verdad práctica

Para la mayoría de las apps de negocio con datos relacionados, Postgres (SQL) es la apuesta segura por defecto. NoSQL brilla en casos concretos: contenido flexible, catálogos, datos de eventos, prototipos rápidos. Y muchos proyectos serios usan los dos: Postgres para lo transaccional, Mongo o Redis para lo demás. Elegir la herramienta por el problema, no por la moda.

Capítulo 11

Seguridad en NoSQL

"NoSQL" no significa "sin riesgos". Tiene su propia versión de la inyección y un par de descuidos clásicos que causaron filtraciones enormes. Todo evitable.

Inyección NoSQL

Aunque no haya SQL, si pasás la entrada del usuario directo a un filtro, un atacante puede meter operadores de Mongo. Por ejemplo, mandar un objeto {"$gt": ""} donde esperabas un texto, y hacer que la condición siempre dé verdadero, saltando un login. La defensa: validar y tipar la entrada (con Pydantic en Python, con validación de esquema en Node) antes de que toque la consulta, y no pasar objetos crudos del usuario como filtro.

El error que llenó titulares

Miles de bases MongoDB quedaron expuestas en internet por un descuido: dejarlas accesibles sin contraseña. Las versiones viejas venían sin auth por defecto y mucha gente las publicó tal cual. Tu base nunca va sin usuario y contraseña, y nunca abierta a todo internet. En Atlas esto viene bien configurado, que es otra razón para usar un servicio gestionado.

Los musts, iguales que en SQL

  • La cadena de conexión (con la clave) en variable de entorno, nunca en el código ni en Git.
  • Usuario de base con solo los permisos necesarios.
  • Acceso restringido por IP o red, no abierto a todo internet.
  • Validar toda entrada del usuario en el backend antes de consultar.
Capítulo 12

Deploy de una base funcional (Atlas)

Tu Mongo local no sirve para producción: nadie más puede llegar. MongoDB Atlas te da una base en la nube, gratis para empezar, funcionando siempre. Estos son los pasos.

Los pasos

  1. Creás una cuenta gratis en MongoDB Atlas y un cluster nuevo. Elegí el plan gratis (M0): alcanza para aprender y para proyectos chicos.
  2. Creás un usuario de base con su contraseña. Anotala bien, es parte de la conexión.
  3. Configurás el acceso de red: qué IPs pueden conectarse. Para tu backend en un hosting, permitís su IP; para probar, tu IP actual. Evitá el "abierto a todos" salvo pruebas rápidas.
  4. Atlas te da la cadena de conexión (empieza con mongodb+srv://). Ese es el dato clave.
  5. Ponés esa cadena en la variable de entorno MONGO_URL de tu backend. En local, un .env fuera de Git; en el hosting, su panel de variables.
  6. Tu código lee MONGO_URL en vez de la dirección local. Nada más cambia.
leer la URL del entorno
import os
MONGO_URL = os.getenv("MONGO_URL", "mongodb://127.0.0.1:27017")
cliente = MongoClient(MONGO_URL)
# en local usa el Mongo de tu máquina; en producción, el de Atlas.

Fijate que es el mismo patrón exacto del librito SQL: el código lee la conexión de una variable de entorno, con un valor local por defecto. Cambiás el entorno, no el código. Ese hábito te sirve con cualquier base y cualquier hosting.

La cadena es un secreto

Igual que en SQL: tiene la contraseña de tu base, así que nunca en el código, nunca en Git, nunca en el frontend. Solo en variables de entorno del servidor. Si se filtra, rotá la clave del usuario de base enseguida desde el panel de Atlas.

Capítulo 13

NoSQL con ayuda de IA

La IA es una gran compañera para MongoDB, sobre todo en las dos cosas que más cuestan: modelar los documentos y armar pipelines de agregación.

Para qué es excelente

  • Decidir embeber o referenciar: "Tengo usuarios, posts y comentarios. ¿Cómo modelo esto en MongoDB, embebido o referenciado, y por qué?" Te da un análisis con los trade-offs.
  • Armar agregaciones: los pipelines son verbosos y difíciles de recordar. "Dame el aggregate para el total vendido por mes." Justo donde la IA ahorra tiempo real.
  • Traducir de SQL a Mongo: si venís de SQL, pedí la versión Mongo de una consulta que ya sabés escribir en SQL.
  • Diseñar el documento: "Dame la forma de un documento para un producto de ecommerce con variantes y stock."

Cómo pedirlo bien

Dale la forma de tus documentos actuales (pegá un ejemplo en JSON) y qué querés lograr. Aclarale que es MongoDB y qué driver usás (pymongo, driver de Node). Con eso, el código sale usable.

Revisá el modelado, no solo el código

La IA te da código que anda, pero el modelado (embeber vs referenciar) tiene consecuencias a largo plazo que ella no siempre pesa bien para tu caso. Entendé por qué propone lo que propone, y pensá cómo va a crecer tu app. Un mal modelo elegido al principio es caro de cambiar después.

Fin del librito

Checklist y cierre

Fuiste de no saber qué es NoSQL a tener un backend con CRUD real contra MongoDB y saber desplegarlo en la nube. Este es el resumen para tener a mano.

Checklist de un backend NoSQL

  • Datos pensados como documentos, agrupados en colecciones con sentido.
  • Modelado decidido con criterio: embeber lo acotado, referenciar lo compartido o creciente.
  • CRUD completo con insertOne, find, updateOne, deleteOne.
  • Filtros y operadores ($gt, $in) para las consultas.
  • Entrada del usuario validada y tipada antes de tocar la consulta.
  • Índices en los campos que filtrás seguido.
  • Base con usuario y contraseña, nunca abierta a internet.
  • Cadena de conexión en variable de entorno, fuera de Git.
  • Producción en Atlas (o gestionado) con su acceso de red configurado.
