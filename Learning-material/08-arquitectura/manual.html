Arquitectura de software

La arquitectura son las decisiones de fondo sobre cómo se organiza un sistema: las que son caras de cambiar después. Este libro te da el vocabulario y los criterios para entender monolitos, microservicios, capas y escalado, y para decidir con cabeza en vez de copiar lo que está de moda.

Un libro de criterio, no de recetas

A diferencia de los otros libritos, este tiene menos código y más decisiones. La arquitectura se trata de trade-offs: casi nunca hay una opción "correcta", hay opciones con distintos costos. El objetivo es que sepas cuáles son.

Cómo está armado

  • Parte 1, fundamentos. Qué es la arquitectura, y las dos ideas que la sostienen: acoplamiento y cohesión.
  • Parte 2, estructurar una app. Capas y separación de responsabilidades.
  • Parte 3, escalar. Monolito vs microservicios, comunicación, bases y escalado.
  • Parte 4, decidir. Patrones útiles y cómo elegir sin sobre-diseñar.
Capítulo 1

Qué es la arquitectura de software

Una definición práctica: la arquitectura es el conjunto de decisiones importantes que son difíciles de cambiar más adelante. Elegir un nombre de variable no es arquitectura. Elegir si tu sistema es un monolito o veinte servicios, sí.

Por qué importa

El código lo reescribís un martes cualquiera. La arquitectura, una vez que tenés miles de usuarios encima, es una operación a corazón abierto. Las buenas decisiones tempranas te dan un sistema que crece sin dolor; las malas, uno que se vuelve más lento y frágil con cada feature.

Atributos de calidad

La arquitectura no se juzga por si "funciona", sino por qué tan bien cumple ciertas propiedades. Las que más pesan:

AtributoLa pregunta que responde
Escalabilidad¿Aguanta 100x más usuarios sin reescribirse?
Mantenibilidad¿Se puede entender y cambiar sin romper todo?
Disponibilidad¿Sigue andando cuando una parte falla?
Rendimiento¿Responde rápido bajo carga?
Seguridad¿Protege los datos y limita el daño de una brecha?

El truco es que se pelean entre sí. Más disponibilidad suele costar más complejidad. Más rendimiento a veces resigna mantenibilidad. Arquitectar es elegir qué priorizar para tu caso.

La frase que resume todo

"It depends". Depende. Cualquiera que te dé una respuesta arquitectónica sin preguntar por tu contexto (cuántos usuarios, qué equipo, qué presupuesto) te está vendiendo una moda, no una solución.

Capítulo 2

Acoplamiento y cohesión

Si te llevás dos ideas de todo el libro, que sean estas. Casi toda decisión de arquitectura se puede leer como "bajar el acoplamiento" y "subir la cohesión".

Acoplamiento: qué tan atadas están las partes

Dos módulos están muy acoplados cuando cambiar uno obliga a cambiar el otro. Alto acoplamiento es malo: tocás una cosa y se rompen tres que no esperabas. El objetivo es bajo acoplamiento: que las partes se conozcan lo mínimo, y se hablen por interfaces claras.

Cohesión: qué tan enfocada está cada parte

Un módulo es cohesivo cuando todo lo que tiene adentro pertenece junto, sirve a un mismo propósito. Baja cohesión es un archivo "utils" que hace de todo. El objetivo es alta cohesión: cada parte hace una cosa y la hace bien.

  MAL                              BIEN
  alto acoplamiento                bajo acoplamiento
  baja cohesión                    alta cohesión

  [A]===[B]                        [A]---[B]
   ‖  X  ‖    todo enredado         |     |    conexiones limpias
  [C]===[D]                        [C]---[D]    cada caja, un propósito

Esta pareja aparece en cada nivel: entre funciones, entre clases, entre módulos, entre servicios. Un buen diseño, a cualquier escala, es alta cohesión adentro y bajo acoplamiento afuera.

La prueba práctica

Preguntate: "si cambio esto, ¿cuántas otras cosas tengo que tocar?". Si la respuesta es "muchas", tenés demasiado acoplamiento. "Si busco la lógica de pagos, ¿está en un solo lugar?". Si está desparramada, te falta cohesión.

Capítulo 3

Arquitectura en capas

La forma más común de organizar una aplicación: separarla en capas horizontales, donde cada una tiene un rol y solo habla con la de al lado. Es el punto de partida de casi todo backend.

Las tres capas clásicas

  ┌─────────────────────────────┐
  │  Presentación (API / UI)    │  recibe requests, devuelve respuestas
  ├─────────────────────────────┤
  │  Lógica de negocio          │  las reglas: qué se puede y qué no
  ├─────────────────────────────┤
  │  Acceso a datos             │  hablar con la base de datos
  └─────────────────────────────┘
              │
        ┌───────────┐
        │ Base datos│
        └───────────┘
  • Presentación. El borde: la API REST del librito de APIs, o la interfaz. Recibe la request, valida el formato, y delega. No tiene reglas de negocio.
  • Lógica de negocio. El cerebro. "Un pedido no se puede confirmar sin stock", "el descuento máximo es 30%". Acá viven las reglas, sin saber nada de HTTP ni de SQL.
  • Acceso a datos. Traduce entre la lógica y la base. La lógica pide "guardá este pedido"; esta capa sabe el SQL.

Por qué conviene

Cada capa se puede entender, testear y cambiar por separado. Cambiás de base de datos tocando solo la capa de datos. Agregás una app móvil sumando presentación, sin tocar la lógica. Es acoplamiento bajo y cohesión alta aplicados a la app entera.

La regla de oro de las capas

Las dependencias van en una sola dirección: presentación conoce a lógica, lógica conoce a datos, nunca al revés. La capa de datos no debe saber que existe una API arriba. Si la lógica de negocio importa algo de HTTP, algo se mezcló.

Capítulo 4

Separar responsabilidades

Dentro de las capas hay patrones probados para no terminar con un archivo de 3000 líneas que hace todo. Los nombres varían, la idea es siempre la misma: darle a cada cosa un lugar.

MVC, el patrón clásico

Model-View-Controller separa en tres:

  • Model: los datos y las reglas sobre ellos.
  • View: lo que ve el usuario (o el JSON que devuelve la API).
  • Controller: recibe la acción del usuario, coordina al model y elige la view.

Es la base de frameworks como Django, Rails y muchos más.

Servicios y repositorios

Dos piezas que ordenan la capa de lógica y datos:

  • Un service concentra una operación de negocio completa: PedidoService.confirmar() chequea stock, calcula total, guarda. El controller solo lo llama.
  • Un repository esconde el acceso a datos detrás de métodos con sentido: pedidos.guardar(p), pedidos.buscar_por_usuario(id). La lógica no ve SQL, ve un repositorio.
  Controller  →  Service        →  Repository  →  Base
  (recibe)       (regla negocio)   (persistencia)
El principio detrás de todo

Single Responsibility: cada clase o módulo debería tener una sola razón para cambiar. Si tu clase de usuario maneja login, manda mails y arma reportes, tiene tres razones para cambiar y va a doler. Separalas.

Capítulo 5

Monolito vs microservicios

El debate más ruidoso de la arquitectura moderna, y el más malentendido. No hay ganador: hay una elección según tu tamaño y tu equipo.

Las dos formas

  MONOLITO                        MICROSERVICIOS
  ┌───────────────┐               ┌─────┐ ┌─────┐ ┌─────┐
  │  usuarios     │               │users│ │pagos│ │envío│
  │  pagos        │               └──┬──┘ └──┬──┘ └──┬──┘
  │  envíos       │                  │       │       │
  │  (una app,    │               ┌──┴──┐ ┌──┴──┐ ┌──┴──┐
  │   una base)   │               │ db  │ │ db  │ │ db  │
  └───────────────┘               └─────┘ └─────┘ └─────┘
  todo junto                      cada servicio, su app y su base

El monolito es una sola aplicación con todo adentro. Los microservicios parten el sistema en servicios chicos e independientes, cada uno con su base, que se comunican por red (con las APIs del primer librito).

Los trade-offs

MonolitoMicroservicios
EmpezarSimple y rápidoComplejo desde el día uno
DesplegarUna cosa, fácilMuchas piezas, orquestación
EscalarTodo junto o nadaCada servicio por separado
EquiposSe pisan en el mismo códigoCada equipo, su servicio
DebuggingTodo en un lugarRastrear entre servicios y red
FallaSe cae todoSe cae una parte (si está bien hecho)
El consejo que da casi todo el que lo vivió

Empezá con un monolito. Los microservicios resuelven problemas de escala y de organización que no tenés hasta que sos grande, y a cambio te cobran una complejidad enorme de entrada. Muchas startups se hundieron manteniendo veinte servicios para diez usuarios. Un "monolito bien modularizado" te lleva muy lejos, y si un día necesitás partirlo, se parte.

Capítulo 6

Cómo se hablan los servicios

Apenas tenés más de una pieza, aparece la pregunta de cómo se comunican. Hay dos estilos, y elegir bien evita muchos dolores.

Sincrónico: pedir y esperar

Un servicio le pega a otro y espera la respuesta, como una llamada telefónica. Es lo que hacen REST y gRPC (primer librito). Simple y directo, pero acopla: si el servicio de pagos está lento, el que lo llamó también se cuelga esperando.

  [pedidos] ──llama y espera──▶ [pagos]
            ◀─── responde ────

Asincrónico: dejar un mensaje

Un servicio deja un mensaje en una cola y sigue con su vida. Otro lo procesa cuando puede, como mandar un mail en vez de llamar. Se usa una cola de mensajes (RabbitMQ, Kafka, SQS) en el medio.

  [pedidos] ──deja mensaje──▶ [ cola ] ──▶ [envíos]
   sigue sin esperar                        procesa cuando puede

Desacopla fuerte: si el servicio de envíos se cae, los mensajes se acumulan en la cola y se procesan cuando vuelve. Nada se pierde. El costo es más complejidad y que las cosas pasan "en algún momento", no al instante.

Cuándo cada uno

Sincrónico cuando necesitás la respuesta ya para seguir (validar un pago antes de confirmar). Asincrónico cuando la tarea puede esperar y no querés que una falla arrastre a las demás (mandar el mail de confirmación, generar un reporte). Los sistemas reales mezclan los dos.

Capítulo 7

Bases de datos cuando crece la cosa

La base suele ser el primer cuello de botella cuando una app se hace popular. Estas son las técnicas para que aguante, de la más simple a la más pesada.

Cache: no le pegues a la base si no hace falta

Lo primero y lo que más rinde. Guardás en memoria (Redis) los datos que se piden mucho y cambian poco. La base descansa, las respuestas vuelan.

  app ──▶ ¿está en cache (Redis)? ──sí──▶ devuelve rápido
                  │no
                  ▼
                base ──▶ guarda en cache y devuelve

Réplicas de lectura

La mayoría de las apps leen mucho más de lo que escriben. Ponés copias de la base solo para leer: las escrituras van a la principal, las lecturas se reparten entre las réplicas. Escala las lecturas sin tocar el código de negocio.

Sharding: partir los datos

Cuando ni las réplicas alcanzan, partís los datos entre varias bases: usuarios de la A a la M en una, de la N a la Z en otra. Escala mucho, pero complica todo (las consultas que cruzan shards son un dolor). Es artillería pesada, para cuando de verdad la necesitás.

El orden importa

Cache primero, réplicas después, sharding al final y solo si no queda otra. Cada paso agrega complejidad. Muchísimas apps viven felices para siempre con una sola base bien indexada (librito de SQL) y un cache. No saltes al sharding porque suena impresionante.

Capítulo 8

Escalar la aplicación

Aparte de la base, la app misma tiene que aguantar más carga. Hay dos formas de crecer, y una propiedad que hace posible la buena.

Vertical vs horizontal

  • Vertical: una máquina más grande, con más CPU y RAM. Simple, pero tiene techo y un solo punto de falla.
  • Horizontal: más máquinas iguales, con la carga repartida entre ellas. Escala casi sin límite y tolera fallas: si una se cae, las demás siguen.
  VERTICAL                 HORIZONTAL
  ┌──────────┐             ┌──┐ ┌──┐ ┌──┐ ┌──┐
  │  server  │             │s1│ │s2│ │s3│ │s4│
  │  más     │             └──┘ └──┘ └──┘ └──┘
  │  grande  │                ▲
  └──────────┘             load balancer reparte

El load balancer

Cuando tenés varias copias de la app, un balanceador de carga adelante reparte las requests entre ellas. El usuario le pega a una sola dirección; el balanceador decide qué copia atiende.

Stateless: la clave que lo hace posible

Para que cualquier copia atienda cualquier request, las copias no pueden guardar estado propio. Si el server A recuerda que estás logueado y el balanceador te manda al B, se rompe. Por eso el estado va afuera: la sesión en Redis, los datos en la base. Las copias de la app son intercambiables. Es la misma idea "stateless" del librito de APIs, ahora como base del escalado.

Capítulo 9

Algunos patrones que vas a cruzar

Nombres que aparecen en toda discusión de arquitectura. No para usarlos todos, sino para entenderlos cuando alguien los menciona.

API Gateway

Una única puerta de entrada delante de tus servicios. El cliente le pega al gateway, y este rutea al servicio que corresponde, y de paso centraliza autenticación, rate limiting y logs. Evita que cada cliente tenga que conocer veinte direcciones.

  cliente ──▶ [API Gateway] ──▶ [users]
                    ├────────▶ [pagos]
                    └────────▶ [envíos]

Event-driven

En vez de que los servicios se llamen entre sí, emiten "eventos" ("pedido confirmado") a los que otros reaccionan. El servicio de pedidos no sabe quién escucha; envíos, facturación y mails reaccionan por su cuenta. Máximo desacoplamiento, sobre la comunicación asincrónica del capítulo 6.

CQRS, en una línea

Separar el modelo de escritura del de lectura, cuando tienen necesidades muy distintas. Potente y complejo. Sabé que existe; rara vez lo vas a necesitar temprano.

Los patrones son herramientas, no metas

El objetivo nunca es "usar CQRS" o "hacer event-driven". El objetivo es resolver un problema real. Si no tenés el problema que el patrón resuelve, el patrón solo te suma complejidad. Aprendelos para reconocer cuándo aplican, no para meterlos a la fuerza.

Capítulo 10

Cómo tomar decisiones de arquitectura

Ya tenés el vocabulario. Ahora, el criterio para usarlo sin caer en las trampas más comunes.

Empezá simple

El error más caro es diseñar para una escala que no tenés. Microservicios, sharding, event-driven: todo eso resuelve problemas de sistemas grandes. Arrancá con lo más simple que funcione (un monolito en capas, una base), y agregá complejidad solo cuando un problema real te la pida. Es más fácil partir un monolito ordenado que unir veinte servicios mal pensados.

Optimizá para el cambio, no para la perfección

No vas a acertar todo de entrada, y está bien. Una buena arquitectura no es la que adivinó el futuro: es la que se deja cambiar cuando el futuro llega. Bajo acoplamiento y alta cohesión (capítulo 2) son justamente lo que te da esa flexibilidad.

Documentá el porqué

Cuando tomes una decisión importante, anotá por qué la tomaste y qué alternativas descartaste (un ADR, Architecture Decision Record, es una nota corta para esto). Tu yo del futuro, o el que herede el sistema, va a agradecer saber el razonamiento, no solo el resultado.

Las dos trampas gemelas

Sobre-diseñar: agregar complejidad para problemas que no tenés. Sub-diseñar: no separar nada y terminar con un plato de fideos. El punto justo se encuentra con experiencia, pero la regla base ayuda: agregá estructura cuando el dolor la justifique, no antes ni mucho después.

Próximos pasos

  1. Tomá una app tuya y dibujá sus capas. ¿La lógica está separada del HTTP y del SQL, o todo mezclado?
  2. Buscá el acoplamiento: ¿qué cambio te obliga a tocar muchas partes? Ahí hay algo para desacoplar.
  3. Leé arquitecturas reales: muchas empresas publican cómo están armadas. Ver decisiones concretas enseña más que la teoría.
  4. La próxima vez que sientas la tentación de un patrón complejo, preguntate qué problema real resuelve para vos hoy.
Lo que te llevás

Tenés el vocabulario y el criterio: acoplamiento y cohesión, capas, monolito vs microservicios, cómo escalar bases y apps, y sobre todo, cuándo NO complicar. La mejor arquitectura para empezar casi siempre es la más simple que resuelve tu problema de hoy. La complejidad se gana cuando el dolor la pide.
