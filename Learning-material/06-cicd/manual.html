CI/CD con GitHub Actions

CI/CD automatiza lo aburrido y peligroso: correr los tests en cada cambio y desplegar sin hacerlo a mano. Este libro va de "¿qué es un pipeline?" a un workflow que testea cada push y despliega solo. Es el que une Git, testing y Docker en un solo flujo.

Sobre los ejemplos

Los workflows YAML de este libro son válidos y están listos para pegar en un repo. Las salidas de consola son ilustrativas: representan lo que verías en la pestaña Actions de GitHub, no una captura de esta sesión, porque un pipeline corre en la infraestructura de GitHub.

Capítulo 1

Qué es CI/CD

CI/CD son dos prácticas que se encadenan: integrar los cambios seguido y con red de seguridad, y entregarlos a producción de forma automática. Detrás hay una idea simple: que la computadora haga los pasos repetitivos que la gente se olvida o hace mal.

CI: Continuous Integration

Cada vez que alguien sube código, un servidor automático lo baja, instala dependencias, corre los tests y avisa si algo se rompió. En minutos sabés si tu cambio rompió algo, antes de mergearlo. Nadie tiene que acordarse de correr los tests: pasan solos en cada push.

CD: Continuous Delivery / Deployment

La continuación: si los tests pasan, el código se empaqueta y se despliega. En Delivery queda listo para desplegar con un botón. En Deployment se despliega solo, sin intervención. La diferencia es si hay un humano apretando el botón final.

Por qué cambia el trabajo

  • Los bugs se atrapan en minutos, no en producción.
  • Desplegar deja de ser un evento estresante de viernes a la tarde y pasa a ser rutina.
  • Todos integran seguido, así que los merges son chicos y los conflictos, raros.
  • El proceso queda documentado en código: cualquiera ve qué corre y cómo se despliega.
Cómo cierra con los otros libritos

CI/CD es el pegamento. Corre los tests que aprendiste a escribir, sobre el repo que manejás con Git, construye la imagen Docker, y la despliega. Tiene sentido pleno después de esos tres.

Capítulo 2

Las piezas de un pipeline

GitHub Actions tiene un vocabulario propio, pero son cuatro conceptos y se entienden rápido. Todo vive en archivos YAML dentro de .github/workflows/ de tu repo.

Los cuatro conceptos

PiezaQué es
WorkflowUn proceso automatizado completo, definido en un archivo YAML. "Correr los tests", por ejemplo.
Trigger (on)El evento que lo dispara: un push, un pull request, un horario.
JobUn grupo de pasos que corren juntos en una máquina limpia (un "runner"). Un workflow puede tener varios jobs, en paralelo o en secuencia.
StepUn paso individual dentro de un job: un comando, o una "action" reutilizable.

Cómo se anidan

workflow (archivo .yml)
 └─ on: push                    # trigger
 └─ job: test
     └─ step: bajar el código
     └─ step: instalar Python
     └─ step: correr pytest
 └─ job: deploy                 # otro job, corre si test pasó
     └─ step: ...

Runners y actions

Cada job corre en un runner: una máquina virtual limpia que GitHub te presta, gratis dentro de un límite generoso. Y las actions son pasos empaquetados que reusás en vez de escribir todo a mano: actions/checkout baja tu código, actions/setup-node instala Node. Es el "no reinventes la rueda" del CI.

Capítulo 3

Tu primer workflow: tests en cada push

El caso más común y el más valioso: que cada push corra los tests. Creás un archivo en .github/workflows/ y GitHub se encarga del resto.

El workflow, para Python

.github/workflows/tests.yml
name: Tests
on: [push, pull_request]        # se dispara en cada push y PR

jobs:
  test:
    runs-on: ubuntu-latest      # máquina limpia que da GitHub
    steps:
      - uses: actions/checkout@v4          # baja tu código
      - uses: actions/setup-python@v5
        with:
          python-version: "3.11"
      - run: pip install -r requirements.txt
      - run: pytest -v                     # corre los tests

La versión Node

.github/workflows/tests.yml
name: Tests
on: [push, pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: "20"
      - run: npm install
      - run: npm test

Qué pasa cuando pusheás

Apenas subís el archivo y hacés push, GitHub levanta un runner, corre los pasos, y te muestra el resultado en la pestaña Actions y al lado de cada commit:

pestaña Actions (ilustrativo)
✓ Tests · push a main
  ✓ test (12s)
    ✓ Set up job
    ✓ actions/checkout@v4
    ✓ actions/setup-python@v5
    ✓ pip install -r requirements.txt
    ✓ pytest -v          6 passed in 0.12s
  Todos los checks pasaron
El tilde verde

Ese check verde aparece al lado del commit y del PR. Si los tests fallan, aparece una cruz roja y GitHub te manda un mail. Muchos equipos configuran que no se pueda mergear un PR hasta que el check esté verde.

Capítulo 4

Probar en varias versiones a la vez

Si tu librería tiene que andar en Python 3.10, 3.11 y 3.12, no querés tres workflows. Una matriz corre el mismo job con cada combinación, en paralelo.

matriz de versiones
jobs:
  test:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        python-version: ["3.10", "3.11", "3.12"]
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: ${{ matrix.python-version }}
      - run: pip install -r requirements.txt
      - run: pytest

Eso lanza tres jobs en paralelo, uno por versión. En minutos sabés si tu código anda en las tres. La matriz puede combinar dimensiones: versiones de lenguaje por sistemas operativos, por ejemplo, y GitHub corre todas las combinaciones.

resultado (ilustrativo)
✓ test (3.10)   14s
✓ test (3.11)   13s
✓ test (3.12)   15s
La sintaxis ${{ }}

Esas llaves dobles son expresiones de GitHub Actions: leen variables del contexto, como el valor actual de la matriz o un secreto. Las vas a ver por todos lados en los workflows.

Capítulo 5

Secrets y variables

Tu pipeline casi siempre necesita algo sensible: una clave de API, un token para desplegar, la contraseña de la base de tests. Eso nunca va en el YAML. GitHub tiene un lugar seguro para guardarlo.

Dónde viven

En el repo, en Settings, Secrets and variables, Actions, cargás los secretos por nombre. GitHub los guarda cifrados y los inyecta en el workflow cuando corre, sin mostrarlos nunca en los logs.

Cómo se usan

yaml
steps:
  - run: ./deploy.sh
    env:
      API_TOKEN: ${{ secrets.API_TOKEN }}    # viene del almacén cifrado
      DATABASE_URL: ${{ secrets.DATABASE_URL }}
Nunca los imprimas

Si hacés echo $API_TOKEN, queda en los logs del workflow, que otros pueden ver. GitHub intenta enmascarar los secretos conocidos en el output, pero no confíes en eso: simplemente no los imprimas. Y jamás los pongas como texto plano en el YAML, que vive en el repo.

Hay dos tipos: secrets para lo sensible (cifrados, no se ven), y variables para configuración no secreta (una URL pública, un nombre de entorno), que sí se ven.

Capítulo 6

Más rápido: caché y artefactos

Cada job arranca en una máquina limpia, así que reinstala todo cada vez. Dos herramientas evitan trabajo repetido y te dejan pasar cosas entre jobs.

Caché: no reinstalar lo que no cambió

Bajar dependencias en cada corrida es lento. La caché guarda esa carpeta entre corridas mientras el archivo de dependencias no cambie. Las actions de setup ya lo traen incorporado:

yaml
- uses: actions/setup-node@v4
  with:
    node-version: "20"
    cache: "npm"          # cachea node_modules automáticamente

La primera corrida instala normal; las siguientes reusan la caché y arrancan mucho más rápido.

Artefactos: guardar resultados

Un artefacto es un archivo que producís en el workflow y querés conservar o pasar a otro job: un reporte de cobertura, un build compilado, un binario. Se sube y después se puede descargar o usar:

yaml
- run: npm run build          # genera /dist
- uses: actions/upload-artifact@v4
  with:
    name: build
    path: dist/
Caché vs artefacto

La caché es para acelerar (dependencias que se pueden regenerar). El artefacto es para conservar o transportar un resultado que te importa. No los confundas: la caché puede desaparecer, el artefacto queda guardado el tiempo que definas.

Capítulo 7

CD: construir y publicar la imagen

Con los tests en verde, el siguiente paso es empaquetar la app. Acá se junta con Docker: el pipeline construye la imagen y la sube a un registry, listo para desplegar.

Jobs encadenados

Queremos que el build corra solo si los tests pasaron. Eso se logra con needs: un job espera a otro.

.github/workflows/deploy.yml
on:
  push:
    branches: [main]          # solo desplegar desde main

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: pip install -r requirements.txt
      - run: pytest

  build-y-push:
    needs: test               # espera a que test pase
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: docker/login-action@v3
        with:
          username: ${{ secrets.DOCKER_USER }}
          password: ${{ secrets.DOCKER_TOKEN }}
      - uses: docker/build-push-action@v6
        with:
          push: true
          tags: usuario/mi-api:latest

Fijate dos cosas: el needs: test garantiza que no se construya nada roto, y el trigger acotado a main hace que solo se despliegue lo que ya se mergeó, no cada rama de trabajo.

Capítulo 8

Deploy automático

El último eslabón: que la imagen construida llegue a producción sola. Cómo se hace depende del proveedor, pero el patrón es el mismo.

El patrón general

Después del build, un job final le avisa al proveedor que hay una versión nueva. Muchos proveedores dan una action oficial o un webhook de deploy:

yaml
  deploy:
    needs: build-y-push
    runs-on: ubuntu-latest
    steps:
      - run: curl -X POST ${{ secrets.DEPLOY_HOOK_URL }}
        # el proveedor recibe el aviso y actualiza la app

El flujo completo, de punta a punta

  1. Pusheás a una rama y abrís un PR. El workflow de tests corre.
  2. Con el check verde y la revisión hecha, se mergea a main.
  3. El push a main dispara el pipeline de deploy: corre los tests de nuevo, construye la imagen, la sube al registry.
  4. El job de deploy le avisa al proveedor, que baja la imagen nueva y la pone a andar.

Desde que mergeás hasta que está en producción, sin que nadie toque nada. Eso es CI/CD completo.

Empezá de a poco

No armes todo el pipeline el día uno. Primero solo los tests en cada push, que es donde está el 80% del valor. Después el build. El deploy automático al final, cuando ya confiás en tus tests. Un deploy automático sin buenos tests es una forma rápida de romper producción.

Cierre

Buenas prácticas, cheatsheet y glosario

Buenas prácticas

  • Pipelines rápidos. Si el CI tarda 40 minutos, la gente deja de esperarlo. Cacheá dependencias y paralelizá con jobs.
  • Falla rápido y claro. El pipeline tiene que decir en el título qué se rompió, sin tener que abrir logs.
  • Tests obligatorios para mergear. Configurá el branch protection para que no entre nada rojo a main.
  • Secretos siempre en el almacén, nunca en el YAML.
  • Deploy solo desde main, y solo si los tests pasaron (needs).
  • Fijá las versiones de las actions (@v4), no uses ramas móviles.

Cheatsheet de un workflow

estructura mínima
name: Nombre
on: [push]                 # cuándo corre
jobs:
  nombre-del-job:
    runs-on: ubuntu-latest # dónde corre
    needs: otro-job        # (opcional) espera a otro
    strategy:
      matrix: { version: ["a","b"] }   # (opcional) varias combinaciones
    steps:
      - uses: actions/checkout@v4       # action reutilizable
      - run: comando                    # comando propio
        env:
          SECRETO: ${{ secrets.SECRETO }}

TérminoQué es
CIIntegración continua: testear cada cambio automáticamente.
CDEntrega o despliegue continuo: llevar los cambios a producción automáticamente.

Lo que te llevás

Sabés qué es CI/CD, escribir un workflow que testea cada push, usar matrices, secrets y caché, y armar un pipeline que construye y despliega. Empezá agregando el workflow de tests a un repo tuyo: es dos minutos y cambia cómo trabajás.
