Capítulo 1

¿Qué es una API?

Una API es un contrato para que dos programas se hablen. Uno ofrece algo (datos, una acción), el otro lo pide, y la API define exactamente cómo se hace ese pedido y qué se recibe a cambio.

Las siglas son Application Programming Interface. Interfaz es la palabra clave: es el punto de contacto entre dos sistemas que no necesitan saber nada del otro por dentro.

La analogía del restaurante

Estás en una mesa y querés comer. No entrás a la cocina a cocinar. Le decís al mozo lo que querés, el mozo lo lleva a la cocina, y te vuelve con el plato. Vos no sabés cómo está organizada la cocina ni te importa. Solo usás el menú (lo que se puede pedir) y al mozo (el que lleva y trae).

La API es el mozo más el menú. La cocina es el servidor: la base de datos, la lógica, todo lo que no ves. Vos, en la mesa, sos el cliente. Mientras el mozo respete el contrato, la cocina puede cambiar de cocinero, de heladera o de proveedor sin que a vos te afecte.

Cliente y servidor

Casi toda API vive en esta relación de dos roles:

  • El cliente es quien hace el pedido. Tu app de celular, una página web, un script de Python, otro servidor.
  • El servidor es quien tiene lo que se pide y responde. Corre en algún lado, escuchando pedidos.

Un mismo programa puede ser cliente de una API y servidor de otra. Tu backend le responde al navegador (es servidor), y a la vez le pide la cotización del dólar a otro servicio (ahí es cliente).

El contrato es lo importante

Lo que hace útil a una API no es el código, es el acuerdo. El contrato dice: a esta dirección le mandás esto, con este formato, y te devuelve esto otro. Mientras ambos lados respeten el contrato, todo funciona aunque estén escritos en lenguajes distintos, en máquinas distintas, del otro lado del mundo.

Un cliente en Python le puede pegar a un servidor en Go que guarda datos en una base escrita en C. A nadie le importa. El contrato es lo único compartido. Vas a ver esto literalmente en la Parte 3, cuando un cliente Python le hable a un servidor Node y funcione sin drama.

La idea en una línea

Una API es una puerta con reglas claras: golpeás de cierta forma, y del otro lado te contestan de cierta forma. Todo el resto del libro es aprender las distintas maneras de golpear esa puerta.

Capítulo 2

HTTP, el que sostiene casi todo

Cinco de los seis estilos de este libro corren sobre HTTP. Si entendés HTTP, ya entendés la mitad de todo lo que viene. Es el idioma que hablan el navegador y los servidores web.

HTTP es un protocolo de pedido y respuesta. El cliente manda un request, el servidor devuelve un response, y ahí termina. Cada intercambio es independiente: el servidor no recuerda el anterior. A eso se le dice stateless, sin estado. Si el servidor tiene que saber quién sos, se lo decís en cada pedido (con un token, por ejemplo).

Anatomía de un request

Un pedido HTTP tiene cuatro partes. Este es uno real, del capítulo de REST más adelante:

requestlas 4 partes de un pedido
POST /usuarios/42/pedidos HTTP/1.1        # 1. método + ruta
Host: api.tienda.com                       # 2. headers (metadatos)
Authorization: Bearer eyJhbGci...
Content-Type: application/json

{ "producto_id": 991, "cantidad": 2 }      # 3. body (los datos que mandás)

El método dice qué querés hacer

MétodoQué significaEjemplo
GETLeer, traer algo. No modifica nada.ver un usuario
POSTCrear algo nuevo.registrar un pedido
PUTReemplazar un recurso entero.editar todo el perfil
PATCHModificar solo una parte.cambiar el email
DELETEBorrar.eliminar un pedido

Los headers llevan metadatos

No son los datos en sí, son datos sobre el pedido. Los que más vas a ver: Content-Type (en qué formato va el body, casi siempre application/json), Authorization (quién sos), Accept (en qué formato querés la respuesta).

Anatomía de un response

La respuesta tiene un código de estado, headers y un body:

response
HTTP/1.1 201 Created                       # código de estado
Content-Type: application/json
Content-Length: 50

{ "id": 43, "producto_id": 991, "cantidad": 2 }

Los códigos de estado, por familia

El primer dígito te dice todo. Memorizá las familias, no los números sueltos.

FamiliaSignificaLos que vas a ver
2xxSalió bien200 OK, 201 Created, 204 No Content
3xxRedirección301 movido, 304 no cambió
4xxError tuyo (del cliente)400 mal pedido, 401 sin auth, 403 prohibido, 404 no existe, 429 demasiados pedidos
5xxError del servidor500 explotó, 502 gateway, 503 no disponible
Ojo

La diferencia entre 4xx y 5xx importa mucho cuando debugueás. Un 401 o 404 lo arreglás vos cambiando el pedido. Un 500 es problema del otro lado: reintentar puede tener sentido, cambiar tu request no.

Stateless, y por qué te conviene

Que el servidor no recuerde nada entre pedidos suena incómodo, pero es lo que permite escalar. Como cada request se basta a sí mismo, podés tener diez copias del servidor y da igual cuál te atienda. No hay que sincronizar memoria entre ellas. Por eso las APIs web aguantan millones de usuarios.

Capítulo 3

Cómo viajan los datos

Los programas guardan datos en memoria de formas que no se pueden mandar por la red tal cual. Antes de viajar, los datos se convierten a texto (o a bytes) con una estructura acordada. Eso es serializar. Del otro lado se hace al revés: deserializar.

JSON, el que domina hoy

JSON (JavaScript Object Notation) ganó porque es simple de leer para una persona y trivial de parsear para una máquina. Casi toda API moderna lo usa. Tiene seis tipos y nada más: objetos, arrays, strings, números, booleanos y null.

json
{
  "nombre": "Carlos",              # string
  "edad": 34,                      # número
  "activo": true,                  # booleano
  "apodo": null,                   # null
  "lenguajes": ["Python", "JS"],   # array
  "trabajo": { "rol": "dev" }      # objeto anidado
}

Se mapea casi uno a uno con las estructuras de cualquier lenguaje. Un objeto JSON es un dict en Python y un object en JavaScript. Por eso es tan cómodo.

XML, el veterano

Antes de JSON, casi todo era XML. Usa etiquetas anidadas, como HTML. Es más verboso y más pesado, pero soporta cosas que JSON no trae de fábrica, como validación estricta de esquema y atributos. Lo vas a cruzar en SOAP y en sistemas viejos.

xml
<usuario>
  <nombre>Carlos</nombre>
  <edad>34</edad>
  <lenguajes>
    <lenguaje>Python</lenguaje>
    <lenguaje>JS</lenguaje>
  </usuario>

El mismo dato que arriba, pero pesa el doble. Cada campo se nombra dos veces, al abrir y al cerrar.

Protobuf, el binario

Protocol Buffers no es texto, es binario. No lo podés leer de un vistazo, pero pesa muchísimo menos y se serializa más rápido. Necesitás el esquema (.proto) para entenderlo, porque los nombres de los campos no viajan, viajan números. Es lo que usa gRPC, y lo vemos en su capítulo.

FormatoLegible por humanosPesoDónde
JSONSíMedioREST, GraphQL, webhooks
XMLSí, verbosoAltoSOAP, legacy
ProtobufNo (binario)BajogRPC, alto rendimiento
Regla práctica

Texto (JSON, XML) cuando querés debuguear fácil y que cualquiera integre rápido. Binario (protobuf) cuando la performance y el ancho de banda mandan, y controlás las dos puntas.

Capítulo 4

Autenticación: quién sos y qué podés hacer

Como HTTP no recuerda nada entre pedidos, cada request tiene que probar quién lo manda. Hay tres formas que cubren casi todo lo que vas a ver, de la más simple a la más armada.

Antes que nada: HTTPS

Todo lo de este capítulo asume HTTPS, no HTTP pelado. Sin la S, tu token o tu clave viajan en texto plano y cualquiera en el camino los lee. En producción, HTTPS no es opcional.

1. API Key

La más simple. El servicio te da una clave larga, y la mandás en cada pedido, normalmente en un header. Identifica a tu aplicación, no a un usuario final. Sirve para servicios que consumís vos: una API del clima, de mapas, de traducción.

shell
curl https://api.clima.com/hoy \
  -H "X-API-Key: tu_clave_secreta_aca"

Simple, pero si se filtra la clave, quien la tenga es vos. Nunca la pongas en el código del frontend ni la subas a un repo.

2. Token Bearer (JWT)

El estándar hoy para APIs con usuarios. Primero te logueás (usuario y clave, una sola vez) y el servidor te devuelve un token. Después mandás ese token en cada pedido, en el header Authorization. El más común es el JWT (JSON Web Token).

shell
curl https://api.tienda.com/mis-pedidos \
  -H "Authorization: Bearer eyJhbGciOiJIUzI1NiJ9.eyJ1c2VyIjo0Mn0..."

Lo interesante del JWT: el token lleva adentro la info de quién sos, firmada. El servidor la verifica sin ir a la base de datos, solo chequeando la firma. Tiene fecha de vencimiento, así que si se filtra, sirve por un rato y no para siempre.

3. OAuth 2.0

Es lo que hay detrás de "Iniciá sesión con Google". No le das tu clave de Google a la app: Google te muestra una pantalla, vos autorizás, y la app recibe un token con permisos limitados. Nunca ve tu contraseña.

El flujo, simplificado:

  1. La app te manda a la pantalla de login del proveedor (Google, GitHub).
  2. Te logueás ahí y autorizás qué permisos das ("leer tu email", nada más).
  3. El proveedor le devuelve a la app un token de acceso.
  4. La app usa ese token para pedir solo lo que autorizaste.

Es más complejo de implementar, pero es lo correcto cuando una app necesita acceder a datos tuyos que viven en otro servicio.

Autenticación no es autorización

Dos cosas distintas que se confunden. Autenticación es probar quién sos (el 401 es "no sé quién sos"). Autorización es si tenés permiso para esto puntual (el 403 es "sé quién sos, pero no podés"). Un usuario logueado bien autenticado igual recibe 403 si intenta borrar algo que no es suyo.

Capítulo 5

Tu primer llamado a una API real

Basta de teoría. Vamos a pegarle a una API pública de verdad, tres veces: con curl, con Python y con Node. La API es jsonplaceholder.typicode.com, gratis y sin necesidad de clave, pensada justo para practicar.

Lo más básico: curl

curl es una herramienta de terminal para hacer pedidos HTTP. Es la forma más rápida de probar una API sin escribir un programa. Un GET es literalmente escribir la URL:

shell✓ salida real
$ curl -s https://jsonplaceholder.typicode.com/todos/1
respuesta
{
  "userId": 1,
  "id": 1,
  "title": "delectus aut autem",
  "completed": false
}

Eso es todo. Le pediste el "todo" número 1 y te devolvió un JSON. Ese mismo intercambio es el que hacen por debajo todas las librerías.

Con Python: la librería requests

requests es el estándar de facto en Python para consumir APIs. Fijate que siempre chequeamos el status_code antes de confiar en la respuesta.

consume.py
import requests
API = "https://jsonplaceholder.typicode.com"

r = requests.get(f"{API}/todos/1", timeout=10)
print("status:", r.status_code)          # siempre chequear el status
print("json:", r.json())

# crear un recurso (POST) con body JSON
nuevo = {"title": "estudiar APIs", "completed": False, "userId": 1}
r = requests.post(f"{API}/posts", json=nuevo, timeout=10)
print("POST status:", r.status_code)
print("creado:", r.json())
salida✓ salida real
status: 200
json: {'userId': 1, 'id': 1, 'title': 'delectus aut autem', 'completed': False}
POST status: 201
creado: {'title': 'estudiar APIs', 'completed': False, 'userId': 1, 'id': 101}

El GET devolvió 200 y el POST devolvió 201 Created con el recurso nuevo, incluyendo el id que le asignó el servidor. Exactamente lo que vimos en el capítulo de HTTP, ahora contra un servidor real.

Con Node: fetch nativo

Desde Node 18, fetch viene incluido, sin instalar nada. Es la misma API que usás en el navegador. Acá manejamos el error si el status no es 2xx:

consume.js
const API = "https://jsonplaceholder.typicode.com";
(async () => {
  const r = await fetch(`${API}/todos/1`);
  if (!r.ok) throw new Error(`HTTP ${r.status}`);   // manejar errores
  console.log("status:", r.status);
  console.log("json:", await r.json());
})();
salida✓ salida real
status: 200
json: { userId: 1, id: 1, title: 'delectus aut autem', completed: false }
El patrón que se repite siempre

Armás la URL, elegís el método, mandás el pedido, chequeás el status, y parseás el JSON. Cambia la librería y la sintaxis, pero los pasos son estos cinco en todos lados. Ya sabés consumir APIs.

Capítulo 6

Cuando algo sale mal

En el ejemplo anterior todo salió 200. En la vida real las APIs fallan, te frenan, y te devuelven los datos de a pedazos. Manejar eso bien es lo que separa un script de juguete de uno que aguanta.

Chequeá siempre el status

El error más común de principiante es asumir que la respuesta vino bien. Si pedís un JSON y el servidor devolvió un 500 con una página de error en HTML, tu .json() explota con un mensaje que no dice nada. Chequeá el status primero.

python
r = requests.get(url, timeout=10)
if r.status_code == 200:
    datos = r.json()
elif r.status_code == 404:
    print("no existe")
elif r.status_code >= 500:
    print("problema del servidor, quizás reintentar")
else:
    print("algo más:", r.status_code, r.text)

Timeouts: no esperes para siempre

Si el servidor se cuelga y no ponés un timeout, tu programa queda esperando indefinidamente. Poné siempre un límite. En requests es el parámetro timeout; en fetch se usa un AbortController.

Rate limits: cuando te frenan

Casi toda API pública te limita cuántos pedidos podés hacer por minuto. Si te pasás, te devuelve 429 Too Many Requests. Suele venir con un header Retry-After que te dice cuántos segundos esperar.

La forma correcta de reaccionar a un 429 o a un 5xx es reintentar con espera creciente, el patrón que se llama exponential backoff: esperás 1 segundo, después 2, después 4, y así. No martillees el servidor de inmediato.

backoff simple
import time, requests

def pedir_con_reintentos(url, intentos=4):
    for i in range(intentos):
        r = requests.get(url, timeout=10)
        if r.status_code != 429 and r.status_code < 500:
            return r
        espera = 2 ** i          # 1, 2, 4, 8 segundos
        time.sleep(espera)
    return r

Paginación: los datos vienen de a partes

Si una API tiene 10.000 resultados, no te los manda todos juntos. Te da una "página" y te dice cómo pedir la siguiente. Hay dos estilos comunes:

  • Por offset: pedís ?page=2&limit=50 o ?offset=50&limit=50. Simple, pero se rompe si los datos cambian mientras paginás.
  • Por cursor: la respuesta trae un next_cursor, y lo mandás en el próximo pedido. Más robusto, es lo que usan las APIs grandes.

El patrón para traer todo es un loop: pedís una página, procesás, y mientras haya "siguiente", seguís pidiendo.

Ojo con la idempotencia

Reintentar un GET es seguro, no cambia nada. Reintentar un POST puede crear el recurso dos veces. Si vas a reintentar operaciones que escriben, la API tiene que soportar una "clave de idempotencia" para que el segundo intento no duplique. Lo vas a ver de nuevo en el capítulo de webhooks.

Capítulo 7 · REST

REST

El estándar de facto de la web. Todo es un recurso con su propia URL, y usás los verbos de HTTP para operar sobre él. Si vas a hacer una sola API en tu vida, probablemente sea REST.

La idea

REST no es un protocolo, es un estilo de diseño sobre HTTP. Cada cosa (un usuario, un pedido, una factura) es un recurso con una dirección, y el método HTTP dice qué querés hacer con él. GET /usuarios/42 lo lee, POST /usuarios crea uno, DELETE /usuarios/42 lo borra. Nada de estado de sesión guardado en el servidor: cada pedido lleva todo lo que necesita.

Ganó porque es predecible (si conocés una API REST conocés casi todas), se cachea gratis con la infraestructura web que ya existe, y cualquier lenguaje sabe hablar HTTP y JSON.

Construirla en Python (FastAPI)

FastAPI es hoy la forma más cómoda de hacer una API REST en Python. Define validación de datos sola y documenta la API automáticamente.

main.py
from fastapi import FastAPI, HTTPException
from pydantic import BaseModel

app = FastAPI()
usuarios = {42: {"id": 42, "nombre": "Carlos", "email": "carlos@ejemplo.com"}}

class UsuarioNuevo(BaseModel):
    nombre: str
    email: str

@app.get("/usuarios/{uid}")
def leer_usuario(uid: int):
    if uid not in usuarios:
        raise HTTPException(404, "no existe")
    return usuarios[uid]

@app.post("/usuarios", status_code=201)
def crear_usuario(u: UsuarioNuevo):
    nuevo_id = max(usuarios) + 1
    usuarios[nuevo_id] = {"id": nuevo_id, **u.model_dump()}
    return usuarios[nuevo_id]

Se levanta con uvicorn main:app --port 8001. Le pegamos con curl:

La misma API en Node (Express)

Express es el framework web más usado de Node. La estructura es la misma: rutas, métodos, y un handler por cada una.

server.js
const express = require("express");
const app = express();
app.use(express.json());

const usuarios = { 42: { id: 42, nombre: "Carlos", email: "carlos@ejemplo.com" } };

app.get("/usuarios/:id", (req, res) => {
  const u = usuarios[req.params.id];
  if (!u) return res.status(404).json({ detail: "no existe" });
  res.json(u);
});

app.post("/usuarios", (req, res) => {
  const nuevoId = Math.max(...Object.keys(usuarios).map(Number)) + 1;
  usuarios[nuevoId] = { id: nuevoId, ...req.body };
  res.status(201).json(usuarios[nuevoId]);
});

app.listen(8002, () => console.log("REST en :8002"));
tests✓ salida real
### GET /usuarios/42
HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8

{"id":42,"nombre":"Carlos","email":"carlos@ejemplo.com"}

### POST /usuarios
HTTP/1.1 201 Created
Content-Type: application/json; charset=utf-8

{"id":43,"nombre":"Ana","email":"ana@ejemplo.com"}

Misma API, mismo comportamiento, distinto lenguaje. El cliente que le pega no nota la diferencia: ese es el punto de un contrato REST.

Usalo cuando

Exponés una API pública o para terceros, el modelo entra bien en recursos (CRUD), y querés aprovechar caché HTTP y herramientas estándar.

Evitalo cuando

El cliente termina haciendo 8 llamadas para armar una pantalla, necesitás tiempo real, o el contrato tiene que ser estricto y tipado. Ahí miran GraphQL o gRPC.

Capítulo 8 · GraphQL

GraphQL

Vos pedís exactamente los campos que querés, ni uno más. Un solo endpoint, y la respuesta tiene la forma de tu pregunta. Nació en Facebook para apps con pantallas complejas.

La idea

El dolor que resuelve: en REST, para armar una pantalla a veces pegás a /usuarios/42, después a /usuarios/42/pedidos, después a /pedidos/7/items. Tres viajes. Y encima cada uno te trae campos que no usás. GraphQL manda una sola query que describe todo el árbol que necesitás, y el server responde con esa estructura y nada más.

Un solo endpoint (/graphql), casi siempre por POST, y un schema fuertemente tipado que documenta la API sola.

Construirla en Python (Strawberry)

app.py
import strawberry
from strawberry.fastapi import GraphQLRouter
from fastapi import FastAPI
from typing import List

@strawberry.type
class Item:
    producto: str
    cantidad: int

@strawberry.type
class Pedido:
    fecha: str
    items: List[Item]

@strawberry.type
class Usuario:
    nombre: str
    pedidos: List[Pedido]

@strawberry.type
class Query:
    @strawberry.field
    def usuario(self, id: int) -> Usuario:
        return Usuario(nombre="Carlos",
            pedidos=[Pedido(fecha="2026-08-01",
                items=[Item(producto="Teclado", cantidad=1)])])

schema = strawberry.Schema(Query)
app = FastAPI()
app.include_router(GraphQLRouter(schema), prefix="/graphql")
query enviada + respuesta✓ salida real
# query
{ usuario(id: 42) { nombre pedidos { fecha items { producto cantidad } } } }

# respuesta (misma forma que la query)
{"data": {"usuario": {"nombre": "Carlos", "pedidos": [
  {"fecha": "2026-08-01", "items": [{"producto": "Teclado", "cantidad": 1}]}
]}}}

La misma API en Node (Apollo)

Apollo Server es el estándar de GraphQL en Node. Definís el schema como texto y los "resolvers" que saben cómo traer cada campo.

server.js
const { ApolloServer } = require("@apollo/server");
const { startStandaloneServer } = require("@apollo/server/standalone");

const typeDefs = `#graphql
  type Item { producto: String, cantidad: Int }
  type Pedido { fecha: String, items: [Item] }
  type Usuario { nombre: String, pedidos: [Pedido] }
  type Query { usuario(id: Int!): Usuario }
`;

const resolvers = {
  Query: {
    usuario: (_, { id }) => ({
      nombre: "Carlos",
      pedidos: [{ fecha: "2026-08-01", items: [{ producto: "Teclado", cantidad: 1 }] }],
    }),
  },
};

const server = new ApolloServer({ typeDefs, resolvers });
startStandaloneServer(server, { listen: { port: 8004 } });

Acá se ve la magia: dos queries, un solo endpoint

Sin tocar el server, el cliente decide cuánto quiere. Esto es lo que REST no te da:

mismo endpoint, dos pedidos distintos✓ salida real
--- query 1: pido TODO ---
{ usuario(id: 42) { nombre pedidos { fecha items { producto cantidad } } } }
{"data":{"usuario":{"nombre":"Carlos","pedidos":[{"fecha":"2026-08-01",
  "items":[{"producto":"Teclado","cantidad":1}]}]}}}

--- query 2: pido SOLO el nombre ---
{ usuario(id: 42) { nombre } }
{"data":{"usuario":{"nombre":"Carlos"}}}

La segunda query pide solo nombre, y la respuesta trae solo nombre. El frontend cambia lo que necesita sin que nadie toque el backend.

Usalo cuando

Tenés muchos clientes distintos (web, móvil) con necesidades de datos diferentes, o las pantallas combinan datos de varias fuentes.

El precio

El caché HTTP ya no aplica igual (todo es POST al mismo endpoint), una query mal armada puede pedir medio universo, y el backend con sus resolvers tiene más curva. Para una API simple CRUD, REST es menos trabajo.

Capítulo 9 · gRPC

gRPC

No pensás en recursos ni URLs: llamás a una función remota como si fuera local. Binario, tipado y rápido. Es el default para que los servicios internos se hablen entre sí.

La idea

gRPC es un estilo RPC (Remote Procedure Call). Definís métodos ("dame el usuario 42") en un archivo .proto, y una herramienta te genera el código de cliente y servidor en el lenguaje que uses. Va sobre HTTP/2 y serializa con Protocol Buffers, el formato binario del capítulo 3, que pesa mucho menos que JSON.

El contrato es una sola fuente de verdad: el .proto. Los dos lados lo comparten, y si alguien cambia un campo, rompe al compilar, no en producción.

El contrato: un solo .proto para los dos lenguajes

usuarios.proto
syntax = "proto3";
package usuarios;

service Usuarios {
  rpc GetUsuario (UsuarioReq) returns (Usuario);
}
message UsuarioReq { int32 id = 1; }
message Usuario { int32 id = 1; string nombre = 2; string email = 3; }

Los números (= 1, = 2) no son valores, son las posiciones que ocupa cada campo en el binario. Eso es lo que viaja, no los nombres.

Servidor y cliente en Python

Primero generás los stubs desde el proto: python -m grpc_tools.protoc -I. --python_out=. --grpc_python_out=. usuarios.proto. Después implementás:

server.py
import grpc
from concurrent import futures
import usuarios_pb2, usuarios_pb2_grpc

class UsuariosServicer(usuarios_pb2_grpc.UsuariosServicer):
    def GetUsuario(self, request, context):
        return usuarios_pb2.Usuario(id=request.id,
            nombre="Carlos", email="carlos@ejemplo.com")

s = grpc.server(futures.ThreadPoolExecutor(max_workers=4))
usuarios_pb2_grpc.add_UsuariosServicer_to_server(UsuariosServicer(), s)
s.add_insecure_port("[::]:9001")
s.start(); s.wait_for_termination()
client.py
import grpc, usuarios_pb2, usuarios_pb2_grpc

with grpc.insecure_channel("127.0.0.1:9001") as canal:
    stub = usuarios_pb2_grpc.UsuariosStub(canal)
    resp = stub.GetUsuario(usuarios_pb2.UsuarioReq(id=42))   # como una función local
    print("nombre:", resp.nombre)
salida✓ salida real
id: 42
nombre: Carlos
email: carlos@ejemplo.com

Cliente en Node contra el mismo contrato

Node carga el .proto en tiempo de ejecución. Acá el server corre en Node, pero podría ser el de Python: el contrato es idéntico.

client.js
const grpc = require("@grpc/grpc-js");
const protoLoader = require("@grpc/proto-loader");
const proto = grpc.loadPackageDefinition(
  protoLoader.loadSync("usuarios.proto")).usuarios;

const client = new proto.Usuarios("127.0.0.1:9002",
  grpc.credentials.createInsecure());
client.GetUsuario({ id: 42 }, (err, resp) => {
  console.log("nombre:", resp.nombre);
});
salida✓ salida real
id: 42
nombre: Carlos
email: carlos@ejemplo.com

Mismo .proto, mismo resultado en los dos lenguajes. Así conviven los microservicios: cada equipo elige su lenguaje, el contrato los une.

Usalo cuando

Comunicás microservicios internos y la performance cuenta, necesitás streaming, o querés contratos tipados que se validan al compilar.

Evitalo cuando

El cliente es un navegador (no consume gRPC directo, necesita un proxy), o querés que terceros integren fácil con curl. Para eso está REST.

Capítulo 10 · WebSockets

WebSockets

HTTP es pedí y esperá. WebSockets abre un canal que queda abierto en las dos direcciones: el server te empuja datos sin que preguntes, y vos le mandás cuando quieras.

La idea

En HTTP normal, para saber si hay algo nuevo tenés que volver a preguntar (polling), lo cual es lento y desperdicia. WebSockets arranca con un "upgrade" sobre HTTP y a partir de ahí la conexión queda abierta. Un chat, un ticker de precios, la posición de un delivery en el mapa, un documento colaborativo: todo eso vive acá.

Servidor y cliente en Python (websockets)

server.py
import asyncio, json, websockets

async def handler(ws):
    # apenas se conecta, el server EMPUJA un saludo (nadie lo pidió)
    await ws.send(json.dumps({"tipo": "bienvenida", "texto": "conectado"}))
    async for msg in ws:                       # escucha lo que llega
        data = json.loads(msg)
        await ws.send(json.dumps({"tipo": "eco", "recibido": data["texto"]}))

async def main():
    async with websockets.serve(handler, "127.0.0.1", 9101):
        await asyncio.Future()

asyncio.run(main())
client.py
import asyncio, json, websockets

async def main():
    async with websockets.connect("ws://127.0.0.1:9101") as ws:
        print("<- server:", await ws.recv())        # llega solo
        for texto in ["hola", "como va"]:
            await ws.send(json.dumps({"tipo": "mensaje", "texto": texto}))
            print("<- server:", await ws.recv())

asyncio.run(main())
salida✓ salida real
<- server: {"tipo": "bienvenida", "texto": "conectado"}
-> yo:     hola
<- server: {"tipo": "eco", "recibido": "hola"}
-> yo:     como va
<- server: {"tipo": "eco", "recibido": "como va"}

Fijate el primer mensaje: el server lo mandó apenas te conectaste, sin que el cliente pidiera nada. Eso es lo que HTTP no puede hacer.

La misma idea en Node (ws)

server.js
const { WebSocketServer } = require("ws");
const wss = new WebSocketServer({ port: 9102 });

wss.on("connection", (ws) => {
  ws.send(JSON.stringify({ tipo: "bienvenida", texto: "conectado" })); // empuje inicial
  ws.on("message", (raw) => {
    const data = JSON.parse(raw);
    ws.send(JSON.stringify({ tipo: "eco", recibido: data.texto }));
  });
});
salida✓ salida real
<- server: {"tipo":"bienvenida","texto":"conectado"}
-> yo:     hola
<- server: {"tipo":"eco","recibido":"hola"}
-> yo:     como va
<- server: {"tipo":"eco","recibido":"como va"}
Usalo cuando

Necesitás tiempo real de verdad (chat, juegos, colaboración) y el flujo es de ida y vuelta constante.

Alternativa más liviana

Si solo el server empuja y el cliente nunca responde por el mismo canal (un feed de notificaciones), Server-Sent Events es más simple. WebSockets tiene el costo de mantener cada conexión viva y manejar reconexiones.

Capítulo 11 · Webhooks

Webhooks

Al revés que todo lo demás. En vez de que vos preguntes, exponés una URL y el servicio ajeno te hace un POST cuando pasa algo que te interesa. El evento llega solo.

La idea

Un webhook no es un protocolo nuevo, es un patrón sobre HTTP. En vez de que tu app le pregunte a Stripe cada 5 segundos "¿ya pagó?", registrás una URL tuya, y Stripe le pega un POST a esa URL en el momento exacto en que el pago se confirma. Es la forma normal de reaccionar a cosas que pasan en sistemas de terceros: pagos, un push a GitHub, un mail abierto, un mensaje entrante.

El cambio de mentalidad: acá tu app es el servidor. Vos recibís el pedido. El "cliente" es el proveedor externo.

Receptor y emisor en Python

Tu endpoint recibe el evento. El emisor simula al proveedor (Stripe) posteándote. La clave es la firma HMAC: el proveedor firma el cuerpo con un secreto compartido, y vos verificás que sea real.

receiver.py
import hmac, hashlib
from fastapi import FastAPI, Request, HTTPException

SECRET = b"clave_secreta_compartida"
app = FastAPI()

def firma_valida(cuerpo, firma):
    esperada = hmac.new(SECRET, cuerpo, hashlib.sha256).hexdigest()
    return hmac.compare_digest(esperada, firma)

@app.post("/webhooks/pagos")
async def recibir(request: Request):
    cuerpo = await request.body()
    firma = request.headers.get("X-Firma", "")
    if not firma_valida(cuerpo, firma):        # regla 1: verificar la firma
        raise HTTPException(400, "firma invalida")
    evento = await request.json()
    print(f"[receiver] evento OK: {evento['tipo']}")
    return {"recibido": True}                    # regla 2: responder rápido 200
sender.py (el "proveedor")
import hmac, hashlib, json, requests
SECRET = b"clave_secreta_compartida"
evento = {"tipo": "pago.exitoso", "monto": 2500, "moneda": "usd"}
cuerpo = json.dumps(evento).encode()
firma = hmac.new(SECRET, cuerpo, hashlib.sha256).hexdigest()

# evento legítimo (firma correcta) y evento falso (firma inventada)
requests.post(URL, data=cuerpo, headers={"X-Firma": firma})
requests.post(URL, data=cuerpo, headers={"X-Firma": "0000"})
salida✓ salida real
legitimo    -> 200 {'recibido': True}
falsificado -> 400 {'detail': 'firma invalida'}
[receiver] evento OK: pago.exitoso monto=2500

El pedido con firma correcta pasa. El falsificado se rechaza con 400 antes de tocar tu lógica. Sin esa verificación, cualquiera que conozca tu URL podría inventarte pagos.

El mismo patrón en Node

receiver.js
const express = require("express");
const crypto = require("crypto");
const app = express();
const SECRET = "clave_secreta_compartida";
app.use(express.raw({ type: "application/json" }));   // body crudo para firmar

function firmaValida(cuerpo, firma) {
  const esperada = crypto.createHmac("sha256", SECRET).update(cuerpo).digest("hex");
  return firma.length === esperada.length &&
         crypto.timingSafeEqual(Buffer.from(esperada), Buffer.from(firma));
}

app.post("/webhooks/pagos", (req, res) => {
  if (!firmaValida(req.body, req.header("X-Firma") || ""))
    return res.status(400).json({ detail: "firma invalida" });
  const evento = JSON.parse(req.body);
  console.log(`[receiver] evento OK: ${evento.tipo}`);
  res.json({ recibido: true });
});
salida✓ salida real
legitimo    -> 200 { recibido: true }
falsificado -> 400 { detail: 'firma invalida' }
[receiver] evento OK: pago.exitoso monto=2500
Dos reglas que se aprenden a los golpes

Uno: verificá siempre la firma. Dos: respondé rápido con 200 y procesá el trabajo pesado aparte, porque si tardás, el proveedor reintenta y te llega el evento repetido. Por eso tu handler tiene que ser idempotente: el mismo evento dos veces no debe cobrar dos veces.

Capítulo 12 · SOAP

SOAP

El veterano rígido. Un protocolo formal, todo en XML, con un contrato (el WSDL) que define cada operación antes de escribir una línea. Rara vez lo elegís de cero, pero cuando integrás con un banco, aparece.

La idea

SOAP es anterior a REST y sigue vivo donde importa la formalidad: bancos, seguros, sistemas gubernamentales, ERPs viejos. Cada mensaje va envuelto en un "envelope" XML. El contrato lo define un archivo WSDL que describe operaciones, tipos y errores, y a partir de él muchos lenguajes te generan el cliente solo. Trae estándares para seguridad a nivel mensaje y transacciones.

El contrato: el WSDL

Este es el corazón de SOAP. Define un servicio de cotizaciones con una operación GetCotizacion:

cotizaciones.wsdl (recortado)
<portType name="CotizacionesPort">
  <operation name="GetCotizacion">
    <input message="tns:GetCotizacionRequest"/>
    <output message="tns:GetCotizacionResponse"/>
  </operation>
</portType>
<message name="GetCotizacionRequest">
  <part name="moneda" type="xsd:string"/>
</message>
<message name="GetCotizacionResponse">
  <part name="valor" type="xsd:float"/>
</message>

Servidor en Node, cliente en Python: cross-language real

Levantamos el servicio con el paquete soap de Node, guiado por ese WSDL. Después lo consumimos desde Python con zeep, que lee el mismo WSDL y arma el cliente solo. Dos lenguajes, un contrato.

server.js
const soap = require("soap");
const wsdl = require("fs").readFileSync("cotizaciones.wsdl", "utf8");

const service = {
  CotizacionesService: { CotizacionesPort: {
    GetCotizacion: (args) => {
      const tabla = { USD: 1350.5, EUR: 1465.2 };
      return { valor: tabla[args.moneda] ?? 0 };
    },
  }},
};
// soap.listen(server, "/cotiz", service, wsdl);
client.py (zeep genera el cliente desde el WSDL)
from zeep import Client

client = Client("http://127.0.0.1:8007/cotiz?wsdl")
valor = client.service.GetCotizacion(moneda="USD")
print("valor devuelto:", valor)
salida✓ salida real
valor devuelto: 1350.5

Qué viaja por debajo

Todo ese confort esconde XML pesado. Este es el request de ida y la respuesta, crudos:

POST /cotiz + respuesta✓ salida real
# request (body)
<soap:Envelope xmlns:soap="...envelope/" xmlns:tns="http://ejemplo.com/cotiz">
  <soap:Body>
    <tns:GetCotizacion><moneda>USD</moneda></tns:GetCotizacion>
  </soap:Body>
</soap:Envelope>

# respuesta  (HTTP 200)
<soap:Envelope xmlns:soap="...envelope/" xmlns:tns="http://ejemplo.com/cotiz">
  <soap:Body>
    <tns:GetCotizacionResponse><tns:valor>1350.5</tns:valor></tns:GetCotizacionResponse>
  </soap:Body>
</soap:Envelope>

Compará ese envelope con el JSON de tres líneas del capítulo de REST. Esa verbosidad es el costo de SOAP, y también la razón por la que un sistema de pagos de hace 15 años sigue funcionando sin sorpresas.

Usalo cuando

Integrás con banca, seguros o legacy que ya habla SOAP, o necesitás seguridad y transacciones formales a nivel mensaje.

Evitalo cuando

Arrancás algo nuevo sin obligación de compatibilidad, o trabajás con móvil y web donde el peso importa. Ahí REST o GraphQL.

Capítulo 13

Cómo elegir el estilo correcto

Ya viste los seis funcionando. Ahora la parte que importa en el trabajo real: decidir cuál usar. Primero la tabla completa, después cinco preguntas que resuelven casi todo.

Los seis, lado a lado

EstiloTransporteFormatoModeloContratoTiempo realMejor para
RESTHTTP/1.1JSONRecursos + verbosInformal (OpenAPI)NoAPIs públicas, CRUD
SOAPHTTP, otrosXMLOperacionesEstricto (WSDL)NoBanca, legacy
GraphQLHTTP (1 endpoint)JSONQuery de camposEstricto (schema)ParcialFrontends con datos variados
gRPCHTTP/2ProtobufLlamada a funciónEstricto (.proto)SíMicroservicios internos

Cinco preguntas

  • ¿API pública o para que terceros integren fácil? REST. Es lo que todos esperan.
  • ¿El frontend necesita datos muy distintos según la pantalla? GraphQL. Cada cliente pide lo suyo.
  • ¿Comunicación interna entre servicios con foco en performance? gRPC. Binario, tipado, con streaming.
  • ¿Tiempo real con ida y vuelta? WebSockets. Si solo empuja el server, mirá Server-Sent Events.
  • ¿Reaccionar a algo que pasa en un servicio ajeno? Webhooks. Registrás tu URL y el evento llega.

Y la sexta, la que no se elige: si integrás con banca o un sistema viejo que lo pide, es SOAP.

No son excluyentes

Un sistema real mezcla varios. REST para la API pública, gRPC entre los servicios internos, WebSockets para el chat, webhooks para escuchar a Stripe. Conviven todo el tiempo. La pregunta nunca es "cuál", es "cuál para esta parte".

Capítulo 14

Lo que separa un ejemplo de una API real

Los ejemplos de este libro funcionan, pero les falta todo lo que hace a una API confiable en producción. Esta es la checklist de lo que agregás cuando va en serio.

Versioná desde el día uno

Apenas alguien consume tu API, no podés cambiarla sin romperle el código. Por eso se versiona: /v1/usuarios. Cuando necesitás un cambio incompatible, sacás /v2 y mantenés /v1 andando un tiempo. Nunca rompas a quien ya depende de vos sin aviso.

Documentá con un estándar, no en un Word

Para REST, el estándar es OpenAPI (antes Swagger): un archivo que describe cada endpoint, sus parámetros y respuestas. Genera documentación navegable sola, y clientes en muchos lenguajes. FastAPI, del capítulo 7, lo genera automáticamente en /docs. GraphQL, gRPC y SOAP ya traen su contrato incorporado (schema, .proto, WSDL).

Errores útiles

Devolvé el status correcto (no un 200 con {"error": "..."} adentro) y un cuerpo que explique qué pasó y cómo arreglarlo. Un buen error ahorra horas a quien integra.

json
HTTP/1.1 422 Unprocessable Entity
{
  "error": "validacion",
  "campo": "email",
  "detalle": "el email no tiene formato válido"
}

Seguridad, lo mínimo no negociable

  • HTTPS siempre. Sin excepción en producción.
  • Validá toda entrada. Nunca confíes en lo que manda el cliente. Es la puerta de entrada de casi todos los ataques.
  • Rate limiting. Poné un tope de pedidos por cliente para que nadie te tire el servicio.
  • Secretos fuera del código. Claves y tokens en variables de entorno, jamás en el repo.
  • CORS. Si un navegador consume tu API desde otro dominio, configurá qué orígenes permitís.

Testeá la API, no solo la función

Escribí tests que le peguen a tus endpoints como lo haría un cliente, y chequeen status y cuerpo. En Python, pytest con el TestClient de FastAPI. En Node, supertest con Express. Es lo que hicimos a mano en cada capítulo de la Parte 3, pero automatizado y corriendo en cada cambio.

Deploy, en una línea de idea

Tu API tiene que correr en algún lado accesible. El camino típico hoy: la empaquetás en un contenedor con Docker (así corre igual en tu máquina y en el servidor), y la subís a un proveedor (AWS, Railway, Render, Fly). Adelante suele haber un reverse proxy (nginx) que maneja HTTPS y reparte la carga entre varias copias.

El orden en que lo agregás

No hace falta todo el día uno. Primero que funcione y esté versionado. Después documentación y validación. Después rate limiting, tests y monitoreo. La API perfecta que nunca sale no le sirve a nadie.
